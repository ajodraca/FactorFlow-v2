**The substantive result of this review is that the migration-ownership change
is correct and closes a real gap.** Verified independently against
`component-design-market-data-store.md` (v6, approved) section 2.3 rather than
against the parent summary:

- The design's `0003_coverage.sql` block defines exactly `coverage_segment`
  (with `coverage_data_type_known`, `coverage_range_ordered`, the GiST
  `coverage_no_overlap` exclusion constraint and `idx_coverage_instrument`) and
  `acquisition_state` (with its `(instrument_id, data_type)` primary key and
  the two known-value checks). `CAP-001-E5-S1` v2 names that exact set.
- The design's `0004_runs.sql` block defines exactly `acquisition_run` (four
  named checks), the single-active, FIFO-requested and recent-run indexes, and
  `run_instrument_result` (composite key, both foreign keys, two known-value
  checks, failure index). `CAP-001-E5-S1` v2 names that exact set.
- Before this change, `CAP-001-E5-S1` v1 declared that `0004_runs.sql` created
  `acquisition_state`, which contradicts the design, and **no story in the
  backlog created `0003_coverage.sql` at all**. A grep across all 36 stories at
  the prior commit finds no owner for that migration, while `CAP-001-E4-S3`,
  `CAP-001-E6-S1` and `CAP-001-E6-S2` all read or write `coverage_segment`. That
  was an unowned migration — a CRITICAL-class gap had it been reviewed in that
  state — and this revision closes it in the only assignment that keeps the
  story order acyclic.
- `CAP-001-E5-S1-tasks.md` (v1, 2026-09-11) had already recorded the conflict in
  its "Resolved Conflicts" section and asked for exactly this correction. The
  revision is the requested repair, not a new decision.

Independently verified, the 36-story dependency graph is **acyclic**. Extracting
only the bullet-listed dependencies from every story's `### Dependencies`
section and running a DFS returns no cycle. `CAP-001-E5-S1` sits at
`E1-S1, E1-S2, E4-S1 -> E5-S1 -> {E4-S3, E5-S2, E5-S3, E5-S4, E6-S1, E7-S1,
E7-S3}` and participates in no cycle. The four apparent back-edges the graph
shows (`E1-S4`/`E1-S5`, `E3-S1`/`E3-S2`, `E3-S5`/`E4-S6`, `E4-S4`/`E4-S5`) are
prose sentences of the form "Consumed by X" or "X fills the slot this story
defines", not declared dependencies; each of those stories declares "None" or a
strictly earlier story.

The new `E5-S1 -> E4-S1` edge was checked for necessity as well as correctness.
Neither `0003` nor `0004` references an observation table — `coverage_segment`
and `run_instrument_result` reference `instrument` only, and
`acquisition_state.last_run_id` is deliberately a bare `uuid` with no foreign
key into `0004`. The dependency is therefore a *numbering* dependency on the
forward-only migrator, which is exactly how `CAP-001-E5-S1` states it
("migration `0002_observations.sql`, which must precede the two migrations this
story owns"). `migrations/0002_observations.sql` is already present in the
working tree and `CAP-001-E4-S1` is at `docs-sync`, so the prerequisite is
satisfied today.

design's SQL blocks statement for statement, table for table, constraint name
for constraint name, and index for index. I compared the design text directly
rather than reading the story for plausibility, which is the practice v6

not introduce ungrounded scope: the backlog already spreads that component's
migrations across epics (`0001` in `CAP-001-E1-S1`, `0002` in

ordered prerequisite to the run journal", with coverage *computation* left to

Two alignment findings. `CAP-001-E5` v2's three new `### From Capability`

there was no cycle, because `0003` had no owner at all. The conclusion is right;
the stated reason is a counterfactual — FINDING-9.
