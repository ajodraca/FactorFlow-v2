# Runnable Foundation and Schema

**EPIC ID:** CAP-001-E1
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Establish the product's first running system: the single PostgreSQL schema holding instruments, observations, coverage and runs; forward-only numbered migrations that bring an existing store to the running version or refuse to start; runtime configuration that loads the provider credential from the environment without ever exposing it; and the application shell every screen renders inside, with its navigation and persistent status region. This EPIC delivers the operational baseline and the interface frame every later EPIC and every later capability inherits.
**Actors:** Owner-operator (deploying and starting the product), schema-migrator, runtime-config, market-data-store, owner-web-app, ingestion-api
**Estimate:** L
**Out of Scope:** Acquiring any data (E3, E4); the individual screens rendered inside the shell, which their owning EPICs deliver (E2, E5, E6, E7); the health endpoint's most-recent-run content, which needs run records (E7); backup and restore procedure (open question in market-data-store section 14); a separate DDL credential (schema-migrator section 14)
**Dependencies:** None. This EPIC is startable now. Its only cross-capability dependencies are `tech-stack.md` and `STD-UI`, both typed `conforms-to` in capability section 5.1, which are designed against rather than waited on. Every other EPIC in this capability depends on E1, both for the schema and for the shell their screens render inside.
**Links:** system-design.md sections 3 (steps 32-39), 4.1, 4.2 (`/api/health`), 5.2, 5.3, 5.10, 5.11, 5.12, 5.15; component-design-market-data-store.md sections 2.2, 2.3, 2.5; component-design-schema-migrator.md sections 2.5, 4, 6; component-design-runtime-config.md sections 2.2b, 4; component-design-owner-web-app.md sections 2.1, 2.2, 2.3; ux-design.md sections 0, 2

## Goals

- Deliver one transactional PostgreSQL store holding all capability state, per charter constraint C2.
- Make schema evolution forward-only and safe: a newer build applies numbered migrations to an existing store without losing or rewriting acquired history.
- Make an inconsistent start impossible: when the store cannot be brought forward, the product reports the failure and never serves or writes data.
- Load runtime configuration and the provider credential from the environment, so that no credential appears in the repository, in logs, or in any rendered view.
- Enforce append-only point-in-time history at the schema level, since this is the one constraint that cannot be repaired retrospectively.
- Deliver the application shell every screen renders inside, so that the EPICs delivering those screens have a frame to build into rather than each inventing one.
- Make a product that cannot serve legible to its owner, rather than presenting a blank interface.

## Non-Functional Requirements

- **Security:** The provider credential and database password are supplied at runtime from the environment only. Connection failure messages are constructed from known-safe fields rather than by formatting the driver exception, because a `psycopg` connection error can include the connection string (schema-migrator section 4).
- **Security:** The API binds to the loopback interface only; the container publishes its port to `127.0.0.1` and to no other interface. The absence of authentication is sound solely because of that binding (system design 5.11).
- **Data integrity:** No `UPDATE` or `DELETE` may be introduced against observation history by any migration, story or query path (C5, system design 5.3).
- **Performance:** Four migration files against an empty database complete in well under a second; the dominant cost is `CREATE EXTENSION btree_gist`. No container start-time SLA is stated anywhere in the capability.
- **Concurrency:** Migration is serialised by a PostgreSQL advisory lock held for the duration, so a long migration delays API start rather than corrupting the store.
- **Observability:** Structured logging only, in both processes. No direct console output (SA-LOG-001), and no restricted value in any log record.
- **Accessibility:** WCAG 2.1 AA per STD-UI-24. Every status in the shell carries a text label plus icon or shape, so the interface is readable in greyscale (STD-UI-8).
- **Vocabulary:** Navigation labels use the product vocabulary STD-UI-1 fixes: Coverage, Instruments, Runs, Settings. Not "Jobs", not "Sync", not "Import".
- **Spacing and type:** The shell uses only values from the spacing scale (STD-UI-29) and selects no density tier, inheriting the current default, which ux-design section 0 records as a port-time placeholder.

## EPIC Acceptance Criteria

### From Capability

- [AC-13] The provider credential MUST be supplied at runtime from the environment, and MUST NOT appear in the repository, in log output, or in any view the product renders.
- [AC-14] The owner interface MUST NOT be reachable from a non-loopback network interface.
- [AC-15] Deploying a newer version of the product onto an existing data store MUST bring the stored data forward without losing or rewriting previously acquired history.
- [AC-16] When the stored data cannot be brought forward to the running version, the product MUST report the failure and MUST NOT serve or write data.
- [AC-18] The owner-operator MUST be able to determine whether the product is running, without inspecting the data store directly. The most-recent-run half of this criterion is delivered by E7, which owns the run records it reports.

### Derived

- [DAC-E1-1] The schema MUST hold all capability state in one PostgreSQL database, with no part of it split across another store. (traces to: AC-15)
- [DAC-E1-2] `applied_migrations` MUST be created by the migrator before the first migration file runs, rather than by a migration file, because the migrator reads it to decide what to apply. (traces to: AC-15)
- [DAC-E1-3] Migrations MUST be applied in ascending numbered order, each recorded with its version, name and checksum on success. A correction MUST be a new file, never an edit to a file already applied. (traces to: AC-15)
- [DAC-E1-4] When the store carries a migration number this build does not know, the container MUST exit non-zero and the API MUST never bind. (traces to: AC-16)
- [DAC-E1-5] Migration MUST be serialised by an advisory lock, so that two containers starting concurrently cannot apply the same migration twice. (traces to: AC-15)
- [DAC-E1-6] The observation tables MUST carry a natural-key uniqueness constraint including a value hash, so that appending an identical value is a no-op and appending a restated value adds a row. (traces to: AC-15)
- [DAC-E1-7] A missing required configuration value MUST fail process start with a message naming the environment variable but never its value. (traces to: AC-13)
- [DAC-E1-8] The credential MUST be held in memory only, redacted from every log record, and absent from every API response. (traces to: AC-13)
- [DAC-E1-9] The credential MUST be supplied to both containers: the ingestion process uses its value, and the application process reads only whether it is set, so that health can report presence without the application ever reading the value. (traces to: AC-13)
- [DAC-E1-10] The credential MUST be rotatable without a restart: the ingestion process re-reads it when it claims a run and rebuilds its provider client when the value has changed. (traces to: AC-13, SEC-SEC-002)
- [DAC-E1-11] Both processes MUST emit structured log records only, with no direct console output. (traces to: AC-13)
- [DAC-E1-12] The application shell MUST present four destinations in the order Coverage, Instruments, Runs, Settings, with run detail as a child route rather than a fifth destination, and MUST NOT include a user menu, account area or sign-in, since no principal is assumed anywhere. (traces to: AC-14, AC-18)
- [DAC-E1-13] A persistent status region MUST appear on every screen, poll health every 30 seconds, and show its last-updated time. (traces to: AC-18)
- [DAC-E1-14] The status region MUST be sized to take a third line later without restructuring, since the trading-environment indicator lands there when a capability introduces one. (traces to: AC-18)
- [DAC-E1-15] A failure to reach the API MUST render as a named unreachable state identifying the likely cause and where to look, rather than surfacing a transport failure, so that a refused start is legible rather than blank. (traces to: AC-16, AC-18)
- [DAC-E1-16] `GET /api/health` MUST report liveness, database reachability, credential presence as a boolean and schema version. Its most-recent-run field is delivered by E7. (traces to: AC-18, AC-13)
- [DAC-E1-17] The status region MUST render correctly before any run exists, since the shell ships before the EPICs that create runs. (traces to: AC-18, AC-17)

## Open Questions

- **Backup and restore procedure is unspecified.** Raised in `component-design-market-data-store.md` section 14 as the higher-value gap in place of the rejected database-role enforcement of append-only history. Point-in-time history cannot be re-acquired as observed, so its loss is unrecoverable. Not blocking for this EPIC's implementation, but it should be answered before the store holds history the owner relies on.
- **Whether a separate DDL credential is worth introducing.** Recorded in `component-design-schema-migrator.md` section 14. The migrator currently holds the same database credential as the application, which is the only credential the deployment defines.
