# Forward-Only Migrator With Refusal to Start on an Inconsistent Store

## User Story

As an owner-operator, I want a newer build to bring my existing data forward or refuse to start, so that I never end up serving from a store the running code does not understand.

## Description

Delivers `src/factorflow/db/migrator.py` and the container entrypoint `src/factorflow/db/migrate_main.py`. The migrator runs once at application container start and exits before the API binds.

Module: `schema-migrator`. This story is the component's application logic; migration `0001` and the `applied_migrations` definition come from CAP-001-E1-S1.

The refusal path is the point of the story. AC-16 is satisfied by exiting non-zero so the API never binds, rather than by starting degraded. Four distinct non-zero exits distinguish causes the owner acts on differently.

Source: `component-design-schema-migrator.md` sections 2.5, 4, 5, 6.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-15] Given an existing store holding acquired history, When a newer build starts, Then unapplied migrations are applied in order and no existing row is lost or rewritten.
- [AC-16] Given a store that cannot be brought forward, When the container starts, Then the migrator reports the failure and the API never binds.
- [DAC-E1-3] Given several unapplied migrations, When the migrator runs, Then it applies them in ascending numbered order, recording version, name and checksum on success.
- [DAC-E1-4] Given a store carrying a migration number this build does not know, When the migrator runs, Then the container exits non-zero and the API never binds.
- [DAC-E1-5] Given two containers starting concurrently, When both attempt migration, Then an advisory lock serialises them and no migration is applied twice.

### Derived

- [DAC-E1-S2-1] Given a schema already current, When the migrator runs, Then it exits `0` logging `schema current at version N` and applies nothing. (traces to: AC-15)
- [DAC-E1-S2-2] Given an unreachable database or rejected credentials, When the migrator runs, Then it exits `1` with a message naming the host and database but never the password. (traces to: AC-16, AC-13)
- [DAC-E1-S2-3] Given a store at a version this build does not carry, When the migrator runs, Then it exits `2` stating the store's version and the highest this build carries. (traces to: DAC-E1-4)
- [DAC-E1-S2-4] Given a recorded migration whose checksum differs from the file this build carries, When the migrator runs, Then it exits `3`, because a file that has been applied must never be edited. (traces to: DAC-E1-3)
- [DAC-E1-S2-5] Given a migration that fails partway, When the failure occurs, Then the migrator exits `4` and no change from that migration is committed, since each migration runs in its own transaction. (traces to: AC-16)
- [DAC-E1-S2-6] Given any migrator message, When it is emitted, Then it goes through the structured logger at `error` level carrying the migration version as a field, never through `print`. (traces to: DAC-E1-11)
- [DAC-E1-S2-7] Given a connection failure, When its message is constructed, Then it is built from known-safe fields rather than by formatting the driver exception, because a `psycopg` connection error can include the connection string. (traces to: AC-13, DAC-E7-12)
- [DAC-E1-S2-8] Given a long migration on a populated store, When it runs, Then the advisory lock is held for its duration so a second container waits rather than corrupting the store. (traces to: DAC-E1-5)

## Technical Details

### Implementation

- `src/factorflow/db/migrator.py`, discovery, ordering, checksum comparison, advisory lock, application.
- `src/factorflow/db/migrate_main.py`, entrypoint mapping outcomes to the exit codes below.
- `psycopg` 3. The `applied_migrations` insert uses **bound parameters** (SEC-INP-002). Migration files are trusted repository content executed as SQL by design; no filename or version from outside the repository is interpolated into a statement.

### Exit Codes

| Exit | Cause | Message shape |
|---|---|---|
| 0 | Schema current or brought forward | `schema current at version N` / `applied migrations: N, M` |
| 1 | Database unreachable or credentials rejected | `database unreachable: <safe fields>`, host and database only |
| 2 | Store holds a version this build lacks | `store is at version N, this build carries up to M; deploy a build that knows version N` |
| 3 | Recorded checksum mismatch | `migration N was applied with a different definition than this build carries` |
| 4 | A migration failed to apply | `migration N failed: <driver message>; no change was committed` |

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Applying `0001` through `0004` to an empty database, then writing observation rows, then applying again, asserts every row unchanged. This is AC-15's proof.
- Each non-zero exit is exercised: unreachable database, a seeded `applied_migrations` row above this build's maximum, a tampered checksum, and a deliberately failing migration.
- A test asserts no log record from this module contains the database password.
- Concurrency: two migrator invocations against one container, asserting one applies and the other waits then finds the schema current.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E1-S1**, the `applied_migrations` definition and migration `0001` this story applies.
- **CAP-001-E1-S3**, supplies the database connection settings. Can be developed in parallel against the settings contract.
