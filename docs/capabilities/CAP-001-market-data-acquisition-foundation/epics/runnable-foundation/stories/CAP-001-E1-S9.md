# Release Image and Compose Deployment With Smoke Check and Rollback

## User Story

As an owner-operator, I want one reproducible image, a compose file and a smoke check that prove the product starts, serves its interface and listens only on loopback, plus a backup and rollback procedure I have rehearsed, so that I can deploy, verify and undo a release on my own machine.

## Description

Delivers the deployment definition of `component-design-runtime-config.md` section 2.8, closing release manifest v1 blockers B3 (no interface bundle in the image) and B4 (no deployment definition for the application, ingestion and PostgreSQL together):

- **`Dockerfile`** (rewritten), the three stages of section 2.8.2: `interface` (`node:22-slim`, `npm ci && npm run build`); `lock` (`python:3.12-slim`, uv 0.12.10, `uv export --locked --no-emit-project --format requirements.txt`); and the release stage (`pip install --require-hashes -r requirements.txt`, the bundle copied from `interface`, then `pip install --no-deps .`). The command stays `python -m factorflow.db.migrate_main && exec python -m factorflow.app_main`. No `COPY` names `tests/` or `migrations/`.
- **`.dockerignore`** (new), the entries section 2.8.2 lists, including `tests/` and `src/factorflow/api/static/`.
- **`pyproject.toml`** `[tool.setuptools.package-data]` adds `"api/static/**/*"` beside the `"db/migrations/*.sql"` entry CAP-001-E1-S8 adds.
- **`compose.yaml`** (new), exactly the definition of section 2.8.3: project `factorflow`; `postgres:16`, `app` and `ingestion` all `network_mode: host` with no `ports:`; PostgreSQL `listen_addresses=127.0.0.1`, `POSTGRES_HOST_AUTH_METHOD: scram-sha-256` and `POSTGRES_INITDB_ARGS: --auth-host=scram-sha-256 --auth-local=scram-sha-256`; the database URL to `127.0.0.1:5432` with `require_auth=scram-sha-256`; every secret and the image tag as `${...:?...}`; the `pg_isready` (local socket) and `http.client` healthchecks; `ingestion` from the same image with `python -m factorflow.ingestion_main`, in the `ingestion` profile, depending on a healthy `app`; `restart: unless-stopped`; volume `factorflow-pgdata`.
- **`scripts/deploy-smoke.sh [project]`** (new), section 2.8.5: default project `factorflow`; checks 1 to 4 (containers healthy and a `pg_hba.conf` method allow-list; health `database == "reachable"` and `schema_version` equal to the image's highest; `GET /` serves `index.html`; neither 8000 nor 5432 reachable on any non-loopback IPv4, IPv6 or link-local address of the machine or of Docker Desktop's virtual machine). Exits non-zero on the first failure; never reads, prints or sends a secret; starts no acquisition run.
- **README**, replacing the source-checkout run instructions with the owner procedure of runtime-config sections 2.8.3, 2.8.4 and 9: host networking precondition; password generation with `openssl rand -hex 24`; the four variables; `docker compose up -d`; the smoke check; only then the interface at `http://127.0.0.1:8000` and `docker compose --profile ingestion up -d`; re-running the check after any change to the host's network configuration; the upgrade, backup and both rollback procedures of section 2.8.4; the immutable `<version>-<shortsha>` tag rule.

Module: `runtime-config` (owner of the deployment artifacts, owner decision 2026-10-12).

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-13] Given the deployment definition, When it is committed, Then it contains no secret: every secret is interpolated from the owner's shell and a missing one stops `docker compose` naming the variable.
- [AC-14] Given the deployment running, When any non-loopback address of the machine is probed, Then neither the interface nor the database accepts a connection.
- [AC-15] Given a newer image deployed onto an existing store, When the application container starts, Then the migrator brings the store forward before the API serves.
- [AC-16] Given a store ahead of the image, When the application container starts, Then it exits 2 on every start, never serves, and ingestion never starts.
- [AC-18] Given the deployment running, When the owner runs the smoke check or opens `GET /api/health`, Then liveness, database reachability and schema version are reported without inspecting the store.
- [DAC-E1-21] Given the release image, When it is built, Then it carries the interface bundle and exactly the dependency versions `uv.lock` records, and fails to build when the lock is out of date.
- [DAC-E1-22] Given `compose.yaml`, When it is rendered, Then every service runs on the host network with nothing published, PostgreSQL listens on `127.0.0.1` only with `scram-sha-256` on every route, and ingestion starts only in its profile after the application is healthy.
- [DAC-E1-23] Given any deployment, When the owner runs the smoke check, Then it verifies service health, schema version, the served interface, the `pg_hba.conf` methods and the absence of any off-host listener, and exits non-zero on the first failure.
- [DAC-E1-24] Given an upgrade, When the owner follows the documented procedure, Then a dump is taken first, and a rollback after a migration restores that dump before the older image starts.

## Technical Details

### Configuration Surface

| Variable | Set by | Required | Notes |
|---|---|---|---|
| `FACTORFLOW_POSTGRES_PASSWORD` | owner's shell | yes | URL-safe, at least 128 bits (`openssl rand -hex 24`); Restricted; composed into `FACTORFLOW_DATABASE_URL` |
| `FACTORFLOW_MASSIVE_API_KEY` | owner's shell | yes | Value used by ingestion, presence only by the application |
| `FACTORFLOW_MASSIVE_REQUESTS_PER_MINUTE` | owner's shell | yes | Ingestion pacing |
| `FACTORFLOW_IMAGE_TAG` | owner's shell | yes | `<version>-<shortsha>`, never reused |
| `FACTORFLOW_BACKUP_DIR` | owner's shell | for backup only | Outside the repository; dumps never committed |

### Data Changes

None to the schema. Data lives in the named volume `factorflow-pgdata`.

### Testing

- `tests/unit/test_release_excludes_test_paths.py` (extended): DAC-E1-S9-1. Its `_copy_sources` splits lines with `shlex`, which raises on a `\` continuation; it joins continuation lines first (runtime-config section 7).
- `tests/unit/test_distribution_contents.py` (extended from CAP-001-E1-S8): DAC-E1-S9-2.
- `tests/unit/test_compose_definition.py` (new, text-based, no YAML parser since PyYAML is not a dependency): DAC-E1-S9-3.
- `scripts/deploy-smoke.sh` passes `bash -n` and `shellcheck` if available; its checks run only against a real deployment (owner-run, see Description), never a second deployment beside it.
- Image build: `docker build .` succeeds on a clean checkout where Docker is available; when it is not, the plan records the build as not run rather than passed.

### Validation

`uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`, `uv build`, `uv run pytest -m 'not postgres'`, `uv run pytest`, `npm run lint`, `npm run format`, `npx tsc --noEmit`, `npm run test`, `npm run test:e2e`; `docker build .` and `docker compose config` where Docker is available.

### Dependencies

- **CAP-001-E1-S8**, hard: the image relies on the migrations travelling as package data and `MIGRATIONS_DIR` (smoke check 2 imports it), and the compose database URL relies on `DatabaseSettings` accepting `127.0.0.1` under the H7 rule.
- **CAP-001-E1-S6**, hard (done): `GET /api/health`, which the application healthcheck and smoke check 2 call.
- **CAP-001-E3-S6**, hard (done): `test_release_excludes_test_paths.py`, which this story extends. CAP-001-E1-S7 also edits that module (DAC-E1-S7-6), so whichever of the two merges second rebases onto the first.
- **CAP-001-E4-S5**, hard (done): `factorflow.ingestion_main`, the ingestion container's command.
- **CAP-001-E1-S7**, soft: developable in parallel. The release evidence for H9 needs the Host and Origin middleware deployed, but no file here depends on it.
- Docker with host networking (Linux, or Docker Desktop with host networking enabled) for the owner-run items.
