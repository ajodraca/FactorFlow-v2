# Health Endpoint and API Application Factory

## User Story

As an owner-operator, I want a health endpoint that reports whether the product can serve, so that the interface and I can both tell a working system from a broken one.

## Description

Delivers `src/factorflow/api/app.py`, the FastAPI application factory with its lifespan and middleware, and `src/factorflow/api/routes/health.py`.

Module: `ingestion-api`. This story establishes the API surface every later endpoint story adds routes to, and delivers four of the five health fields. The `most_recent_run` field is CAP-001-E7-S3's, and is `null` until that story lands.

The application binds to loopback only. No endpoint declares a credential, session or token requirement, by deliberate design (AC-14, system design 5.11).

Source: `component-design-ingestion-api.md` sections 2.1, 2.2, 11; system design 5.11, 5.12.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-14] Given the API process, When it binds, Then it binds to `127.0.0.1` only and is unreachable from any other interface.
- [AC-18] Given `GET /api/health`, When it is called, Then it reports whether the product is running without the caller inspecting the data store.
- [DAC-E1-16] Given `GET /api/health`, When it responds, Then it reports liveness, database reachability, credential presence as a boolean, and schema version.
- [DAC-E1-9] Given the health response, When credential presence is reported, Then it is a boolean and never the credential value.

### Derived

- [DAC-E1-S6-1] Given a reachable database, When health is called, Then `database` reports reachable and `schema_version` reports the highest applied migration version. (traces to: DAC-E1-16)
- [DAC-E1-S6-2] Given an unreachable database, When health is called, Then it responds `200` with `database` reporting unreachable, rather than failing the request, so the interface can distinguish a dead database from a dead API. (traces to: AC-18)
- [DAC-E1-S6-3] Given the health response, When it is serialised, Then `most_recent_run` is present as `null` until CAP-001-E7-S3 populates it, so the field's absence never has to be handled by the interface. (traces to: DAC-E1-16)
- [DAC-E1-S6-4] Given the application factory, When it is constructed, Then it mounts the built frontend bundle from the API package's static directory. (traces to: AC-14)
- [DAC-E1-S6-5] Given request handling, When any request is served, Then middleware generates a request id and includes it in every log record for that request. (traces to: DAC-E1-11)
- [DAC-E1-S6-6] Given any endpoint in the application, When it is declared, Then it declares no authentication requirement, because the loopback binding is what makes that sound. (traces to: AC-14)

## Technical Details

### API Contract

- Endpoint: `GET /api/health`
- Auth: none, loopback only
- Response `200`:
  ```json
  {
    "status": "ok",
    "database": "reachable",
    "credential_present": true,
    "schema_version": 4,
    "most_recent_run": null
  }
  ```
- Errors: none. An unreachable database is reported in the body with `200`, not as a failure status.

### Implementation

- FastAPI on uvicorn, Pydantic response models in `src/factorflow/api/models.py`.
- `psycopg` 3 for the schema-version and reachability probe.
- Bind host from `runtime-config`, defaulting to `127.0.0.1`.

### Testing

- `pytest` with FastAPI's test client; the database-backed cases marked `postgres` via `testcontainers`.
- Health with a reachable database reports the applied schema version.
- Health with the database stopped still responds `200` reporting unreachable.
- A test asserts the credential value appears nowhere in the response body.
- A test asserts the app declares no security scheme on any route.

### Validation

`uv run pytest`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E1-S1**, **CAP-001-E1-S2**, the schema and `applied_migrations` this endpoint reads its version from.
- **CAP-001-E1-S3**, bind host and credential-presence settings.
