# Application Shell: Navigation Rail and Routing

## User Story

As an owner-operator, I want one consistent frame with four destinations, so that every screen I open sits in a predictable place and nothing suggests an account I do not have.

## Description

Delivers `web/src/app/shell.tsx` and `web/src/app/routes.tsx`, plus the Vite and package scaffolding the tech stack's validation table names: `package.json`, `vite.config.ts`, `web/index.html`, `web/src/main.tsx`.

Module: `owner-web-app`. This is the frame E2, E5, E6 and E7 render their screens inside, which is why it sits in E1 rather than in a screen-delivering EPIC.

Vite is configured with `root: "web"` and `build.outDir` pointing into `src/factorflow/api/static`, so the application container ships one image carrying both the API and the bundle.

The shell is a composition, not a design-system component. It introduces no spacing value outside the scale (STD-UI-29) and selects no density tier, inheriting the current default.

Source: `component-design-owner-web-app.md` sections 2.1, 2.2; `ux-design.md` section 0.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-14] Given the shell, When it renders, Then it contains no sign-in, no user menu and no account area, because no principal is assumed anywhere.
- [DAC-E1-12] Given the navigation rail, When it renders, Then it presents four destinations in the order Coverage, Instruments, Runs, Settings, with run detail as a child route rather than a fifth destination.

### Derived

- [DAC-E1-S4-1] Given the destination labels, When they render, Then they use the product vocabulary STD-UI-1 fixes: Coverage, Instruments, Runs, Settings. Not "Jobs", not "Sync", not "Import". (traces to: DAC-E1-12)
- [DAC-E1-S4-2] Given a run detail route, When it is opened, Then it renders as a child of Runs and the Runs destination remains the active one in the rail. (traces to: DAC-E1-12)
- [DAC-E1-S4-3] Given any spacing or type value in the shell, When it is applied, Then it comes from the defined scale and introduces no new value. (traces to: DAC-E1-12)
- [DAC-E1-S4-4] Given keyboard navigation, When the user tabs through the rail, Then every destination is reachable and the active one is announced, meeting WCAG 2.1 AA. (traces to: DAC-E1-12)
- [DAC-E1-S4-5] Given an unknown route, When it is opened, Then the shell renders a not-found state inside the frame rather than an empty page or a crash. (traces to: DAC-E1-12)
- [DAC-E1-S4-6] Given the built bundle, When `npm run build` runs, Then output lands in the API package's static directory so one image serves both. (traces to: AC-14)

## Technical Details

### Implementation

- React 18 with Vite, TypeScript 5.x, Tailwind CSS, shadcn/ui on Radix primitives.
- `web/src/app/shell.tsx`, fixed left rail, main region, status region slot filled by CAP-001-E1-S5.
- `web/src/app/routes.tsx`, four destinations plus the run detail child route.
- Layout per ux-design section 0: rail width, main padding, region gap and dense table padding all from the spacing scale.

### Testing

- `vitest` with React Testing Library.
- The rail renders exactly four destinations in the specified order.
- No element matching sign-in, account or user-menu semantics is present.
- Opening a run detail route keeps Runs active.
- An unknown route renders the not-found state inside the shell.
- Keyboard traversal reaches every destination.

### Validation

`npm run test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`.

### Dependencies

None for the frame itself. CAP-001-E1-S5 fills the status region slot this story defines.
