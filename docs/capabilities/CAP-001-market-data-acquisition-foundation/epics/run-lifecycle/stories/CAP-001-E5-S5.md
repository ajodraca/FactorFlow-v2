# Acquisition Run API Endpoints

## User Story

As an owner-operator using the interface, I want endpoints to start, list and cancel runs, so that the Runs screen has a contract and starting a run never makes me wait on the provider.

## Description

Delivers `src/factorflow/api/routes/runs.py`.

Module: `ingestion-api`. `POST /api/acquisition-runs` records a request and returns immediately with `202`, so the browser never waits on the provider. The run begins when the ingestion container claims it.

Two preconditions are refused at the boundary rather than encoded as run outcomes, both because the owner can act on them and both cheaper to state here. A zero-instrument run would otherwise finalise as `failed` under the derive-from-what-was-written rule, reporting a system fault for what is an empty list.

Source: `component-design-ingestion-api.md` sections 2.4, 11; system design 5.17, 5.18, 5.20.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-23] Given a run already active, When another is requested, Then the request is accepted with `202` and reports the run it is queued behind, never rejected for the active run.
- [AC-24] Given no active instrument, When a run is requested, Then it is refused `409` with code `no_active_instruments` and no run is recorded.
- [AC-19] Given a running run, When cancellation is requested, Then it responds `202` with `cancelling`.
- [AC-26] Given a queued run, When cancellation is requested, Then it responds `202` with `cancelled`.
- [DAC-E5-14] Given no history depth set, When a run is requested, Then it is refused `409` with code `history_depth_not_set` and no run is recorded.
- [DAC-E5-15] Given the start endpoint, When it accepts, Then it returns the new run as `requested` with `queued_behind` naming the active run or `null`.

### Derived

- [DAC-E5-S5-1] Given both preconditions unmet, When a run is requested, Then one `409` is returned naming which precondition failed, and the response is deterministic rather than order-dependent. (traces to: AC-24, DAC-E5-14)
- [DAC-E5-S5-2] Given a cancellation of an already-terminal run, When it is requested, Then `409 run_already_terminal` is returned carrying the run's actual state. (traces to: DAC-E5-9)
- [DAC-E5-S5-3] Given a cancellation of an unknown run id, When it is requested, Then `404` is returned. (traces to: AC-19)
- [DAC-E5-S5-4] Given `GET /api/acquisition-runs`, When it is called, Then runs are returned reverse-chronologically with a state filter, limit and cursor. (traces to: AC-9)
- [DAC-E5-S5-5] Given `GET /api/acquisition-runs/{id}`, When it is called, Then it returns the run, its counts and its per-instrument per-data-type results, with an outcome filter and paging. (traces to: AC-10)
- [DAC-E5-S5-6] Given any refusal, When it is returned, Then no run row is created, asserted by count. (traces to: AC-24)

## Technical Details

### API Contract

| Method | Path | Success | Errors |
|---|---|---|---|
| `POST` | `/api/acquisition-runs` | `202` `{run_id, state: "requested", queued_behind}` | `409 history_depth_not_set`; `409 no_active_instruments` |
| `GET` | `/api/acquisition-runs` | `200` runs reverse-chronological, `next_cursor` | `422` bad bounds |
| `GET` | `/api/acquisition-runs/{id}` | `200` run, counts, per-instrument results | `404` unknown |
| `POST` | `/api/acquisition-runs/{id}/cancel` | `202` `{state: "cancelling"\|"cancelled"}` | `409 run_already_terminal` with actual state; `404` unknown |

Auth: none, loopback only. Request body for start is empty.

### Testing

- `pytest` with FastAPI's test client and `testcontainers[postgres]`, marked `postgres`.
- Start with no depth returns `409 history_depth_not_set` and creates no run.
- Start with no active instruments returns `409 no_active_instruments` and creates no run.
- Start while a run is active returns `202` with `queued_behind` set.
- Cancel on running returns `cancelling`; on queued returns `cancelled`; on terminal returns `409` with the actual state; on unknown returns `404`.
- Run detail returns per-data-type results.
