# Cancellation: Running and Queued

## User Story

As an owner-operator, I want to stop a run that is taking too long, and cancel one still waiting, so that I keep control of a large acquisition without losing what it already wrote.

## Description

Delivers the cancellation paths in `src/factorflow/runs/journal.py` and the finalisation that computes a run's outcome from written coverage.

Module: `run-journal`. Two cancellation paths that are genuinely different mechanisms:

A **running** run is cancelled cooperatively. The request is recorded against the run rather than acting on the process, and the runner observes it between instruments, so it takes effect within one instrument's work rather than at the end of the run.

A **queued** run has no runner to signal, so cancelling it is a direct state transition to `cancelled`, and the runner never claims it.

Source: `component-design-run-journal.md` section 2.2; system design 5.20.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-19] Given a run under way, When it is cancelled, Then it begins no instrument it had not already started and coverage already written is retained.
- [AC-26] Given a run requested but not started, When it is cancelled, Then it is recorded cancelled, never started, and any active run is unaffected.
- [DAC-E5-4] Given finalisation, When an outcome is computed, Then it derives from what was actually written rather than from what was requested.
- [DAC-E5-5] Given a finished roster, When the run finalises, Then succeeded requires every instrument to have written; otherwise partial, or failed when none wrote.
- [DAC-E5-6] Given a running run, When cancellation is requested, Then it is recorded against the run and observed between instruments.
- [DAC-E5-7] Given a cancelled run, When it terminates, Then it is distinct from failed and committed coverage is retained.
- [DAC-E5-8] Given a requested run, When it is cancelled, Then it moves directly to cancelled as a state transition.
- [DAC-E5-9] Given a terminal run, When cancellation is attempted, Then it conflicts, naming the run's actual state.

### Derived

- [DAC-E5-S3-1] Given a running run, When cancellation is requested, Then the run moves to `cancelling` and only reaches `cancelled` once the runner acknowledges it. (traces to: DAC-E5-6)
- [DAC-E5-S3-2] Given a cancelled run, When coverage is read afterwards, Then instruments it committed retain their coverage and instruments never reached are simply absent. (traces to: AC-19, DAC-E4-11)
- [DAC-E5-S3-3] Given a run cancelled while queued, When an active run is executing, Then the active run is entirely unaffected. (traces to: AC-26)
- [DAC-E5-S3-4] Given a run that completed between the owner's decision and the request arriving, When cancellation is attempted, Then the owner is told it completed rather than shown a cancellation that did not happen. (traces to: DAC-E5-9)
- [DAC-E5-S3-5] Given a run where every instrument recorded `written` or `unchanged`, When it finalises, Then it is `succeeded`. (traces to: DAC-E5-5)
- [DAC-E5-S3-6] Given a run where at least one instrument recorded `not_found` or `failed` and at least one wrote, When it finalises, Then it is `partial` and never `succeeded`. (traces to: AC-9)
- [DAC-E5-S3-7] Given a run where nothing wrote, When it finalises, Then it is `failed`. (traces to: DAC-E5-5)

## Technical Details

### Implementation

- `request_cancellation(run_id)`, `running` moves to `cancelling`; `requested` moves directly to `cancelled`; terminal raises a conflict carrying the actual state.
- `acknowledge_cancellation(run_id)`, called by the runner between instruments, moving `cancelling` to `cancelled`.
- `finalise(run_id)`, computes the outcome by counting `run_instrument_result` rows against the run's roster size, never from intent.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Cancelling a `running` run yields `cancelling`, then `cancelled` on acknowledgement.
- Cancelling a `requested` run yields `cancelled` immediately, and a concurrently running run is untouched.
- Cancelling a terminal run raises a conflict naming its actual state.
- Finalisation: all-written yields succeeded; one not-found yields partial; none-written yields failed.
- A cancelled run's committed coverage is still readable.
