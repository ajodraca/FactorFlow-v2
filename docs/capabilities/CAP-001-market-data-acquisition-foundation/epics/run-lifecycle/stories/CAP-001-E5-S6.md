# Runs Screen and Run Controls

## User Story

As an owner-operator, I want to see my run history with honest outcomes and start or stop a run, so that I can tell at a glance whether acquisition is working.

## Description

Delivers `web/src/screens/runs/`, the Runs list, the Start action and the cancel controls.

Module: `owner-web-app`. Renders inside the shell from CAP-001-E1-S4. The run detail screen is CAP-001-E7-S4.

Outcome rendering is where STD-UI-12's tiers become visible, and the mapping is not cosmetic: `partial` is a warning and **never** good, `cancelled` is neutral and **never** critical, and `abandoned` is serious and distinct from both.

Polling stops when no run is non-terminal, so a quiet system makes no requests.

Source: `ux-design.md` sections 1.4, 5; `component-design-owner-web-app.md` section 2.3.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-9] Given the Runs list, When outcomes render, Then each run shows succeeded, partial, failed, cancelled or abandoned honestly.
- [AC-23] Given a run already active, When the owner starts another, Then the action stays available and the interface says the new run is queued.
- [AC-24] Given no instruments named, When the Start action renders, Then it is `blocked` with the reason *No instruments are named. Add instruments before acquiring.*
- [DAC-E5-16] Given run outcomes, When they render, Then they use the STD-UI-12 tier mapping.
- [DAC-E5-17] Given an abandoned run, When it renders, Then it is explained rather than shown as a bare state, with the path to a new run.

### Derived

- [DAC-E5-S6-1] Given any run in a non-terminal state, When the screen is open, Then it polls every 10 seconds, and polling stops when no run is non-terminal. (traces to: AC-9)
- [DAC-E5-S6-2] Given the tier mapping, When each state renders, Then `requested` is neutral, `running` active, `cancelling` warning, `succeeded` good, `partial` warning, `failed` critical, `cancelled` neutral and `abandoned` serious. (traces to: DAC-E5-16)
- [DAC-E5-S6-3] Given no history depth set, When Start renders, Then it is `blocked` with its own distinct reason, mirroring the no-instruments treatment. (traces to: DAC-E2-9)
- [DAC-E5-S6-4] Given a run id in the list, When it renders, Then it links to run detail as an anchor, so middle-click and open-in-new-tab work. (traces to: AC-10)
- [DAC-E5-S6-5] Given a cancel confirmation for a queued run, When it renders, Then its copy differs from the running-run confirmation, since the effects differ. (traces to: AC-26)
- [DAC-E5-S6-6] Given a cancel that races a completion, When `409` returns, Then the screen tells the owner the run completed rather than showing a cancellation that did not happen. (traces to: DAC-E5-9)
- [DAC-E5-S6-7] Given no run has ever been recorded, When the list renders, Then it says so plainly rather than appearing empty and healthy. (traces to: AC-17)

## Technical Details

### Implementation

- React 18, TypeScript, Tailwind, shadcn/ui.
- `data-table` `history` for the list; `badge` with six `status-*` variants; `button` `default` for Start, `button` `secondary` plus `dialog` `confirm` for cancel; `button` `blocked` for refused preconditions.
- Endpoints: `GET`/`POST /api/acquisition-runs`, `POST /api/acquisition-runs/{id}/cancel`.
- Timestamps ISO-8601 in America/Chicago.

### Testing

- `vitest` with React Testing Library; `@playwright/test` for start-then-cancel.
- Each of the eight states renders its specified tier.
- Polling starts with a non-terminal run and stops when all are terminal, asserted with fake timers.
- Start renders `blocked` with the correct reason for each of the two preconditions.
- A `409` on cancel renders the completed message.
- The empty state distinguishes never-run from filtered-empty.

### Validation

`npm run test`, `npm run test:e2e`, `npm run lint`, `npx tsc --noEmit`.

### Dependencies

- **CAP-001-E1-S4**, the shell.
- **CAP-001-E5-S5**, the endpoints consumed.

### Open Question

The indeterminate progress indicator for a run whose duration cannot be estimated is an unresolved component-spec gap, recorded in `ux-design.md` section 3. The region and its polling are specified; only the indicator is missing. This story renders the region without an indeterminate indicator until that gap is closed.
