# Heartbeat and Abandoned-Run Reclaim Sweep

## User Story

As an owner-operator, I want a run whose process died to reach a terminal state on its own, so that a crash never wedges acquisition with no remedy but editing the database.

## Description

Delivers `src/factorflow/runs/reclaim.py` and the heartbeat refresh in `journal.py`.

Module: `run-journal`. The sweep runs in the **application container**, not the ingestion container, because the failure it recovers from is the ingestion process dying, and a component cannot be relied on to notice its own death. A sweep that only ran when the dead process restarted would not deliver AC-20 for a container that is stopped or crash-looping.

Without this, the only recovery from an interrupted run is editing the database by hand, which AC-18 exists to make unnecessary. The design calls this out as a defect found during system design rather than a gap.

Source: `component-design-run-journal.md` section 2.2; system design 3 steps 48-51, 5.7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-20] Given a run whose process stops unexpectedly, When the sweep runs, Then the run reaches a terminal state without the owner modifying the data store, and a later run can start.
- [DAC-E5-10] Given a runner holding a claim, When it processes instruments, Then it refreshes a heartbeat at the same point it checks for cancellation.
- [DAC-E5-11] Given a claim stale past the configured window, When the sweep runs, Then it releases the claim and records the run `abandoned`, terminal and distinct from failed and cancelled.
- [DAC-E5-12] Given the sweep, When it runs repeatedly, Then it is idempotent and a subsequent run can start once a stale claim is released.
- [DAC-E5-13] Given a runner whose claim was reclaimed, When it continues, Then it writes no further results against that run.

### Derived

- [DAC-E5-S4-1] Given a live runner refreshing its heartbeat, When the sweep runs, Then that run is not reclaimed. (traces to: DAC-E5-11)
- [DAC-E5-S4-2] Given a run in `cancelling` whose runner died, When the sweep runs, Then it is reclaimed as `abandoned`, since that state is also claimable-stale. (traces to: DAC-E5-11)
- [DAC-E5-S4-3] Given coverage written before an interruption, When the run is reclaimed, Then that coverage stands, because the per-instrument commit boundary makes it independently valid. (traces to: AC-12)
- [DAC-E5-S4-4] Given the sweep placed in the application container, When ingestion is stopped entirely, Then reclaim still happens, which is the property that makes AC-20 hold for a crash-looping container. (traces to: AC-20)
- [DAC-E5-S4-5] Given two sweeps running concurrently, When both find the same stale claim, Then exactly one reclaims it and the other is a no-op. (traces to: DAC-E5-12)
- [DAC-E5-S4-6] Given a reclaimed run, When the original runner attempts a write, Then the write is rejected because its claim no longer matches. (traces to: DAC-E5-13)

## Technical Details

### Implementation

- Heartbeat: `UPDATE acquisition_run SET heartbeat_at = now() WHERE run_id = %s AND claimed_by = %s`, returning zero rows if the claim was taken away, which is the runner's signal to stop.
- Sweep: finds runs in `running` or `cancelling` whose `heartbeat_at` is older than the configured staleness window, sets `abandoned` with an end timestamp, and clears the claim. Runs periodically in the application container's lifespan.
- The window comes from `runtime-config` (CAP-001-E1-S3).

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`, using a controlled clock.
- A stale `running` run is reclaimed as `abandoned`; a fresh one is not.
- A stale `cancelling` run is also reclaimed.
- After reclaim, a new run claims successfully, proving AC-20's unblocking.
- A reclaimed runner's heartbeat returns zero rows and its subsequent write is rejected.
- Two concurrent sweeps reclaim exactly once.
- Coverage written before the interruption is still present after reclaim.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E5-S1**, the state machine including `abandoned`.
- **CAP-001-E5-S2**, the claim this sweep releases.
- **CAP-001-E1-S3**, the staleness window setting.
- **CAP-001-E1-S6**, the application lifespan this sweep is scheduled in.
