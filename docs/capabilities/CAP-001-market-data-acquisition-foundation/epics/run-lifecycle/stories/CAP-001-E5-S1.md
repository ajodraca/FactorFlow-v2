# Coverage, Run Schema and State Machine

## User Story

As an owner-operator, I want coverage evidence and every acquisition run recorded under database-enforced invariants, so that coverage cannot overlap and a run marked succeeded means every instrument actually wrote.

## Description

Delivers migrations `0003_coverage.sql` (`coverage_segment`, `acquisition_state`) and `0004_runs.sql` (`acquisition_run`, `run_instrument_result`), plus `src/factorflow/runs/states.py`.

Modules: `market-data-store` and `run-journal`. This story owns the two consecutive schema migrations needed before the observation writer and run-journal operations can be implemented without a migration-order cycle. Migration 0003 stores derived coverage evidence and last-acquisition state; migration 0004 stores run lifecycle and per-instrument results. The capability's honesty requirements are enforced in both layers: coverage ranges cannot overlap, and illegal run transitions or persisted run states are rejected rather than left to convention.

Five terminal exits from `running` are not interchangeable: `succeeded` requires every named instrument to have written, `partial` is the honest outcome when some did not, `cancelled` records the owner's decision and is never `failed`, and `abandoned` records a runner that died and is distinct from both.

Source: `component-design-market-data-store.md` section 2.3; `component-design-run-journal.md` section 2.2.

- [DAC-E5-3] Given two concurrent claims, When both attempt to start a run, Then a partial unique index makes the second fail on a unique violation rather than start a second run.

## Technical Details

### Data Changes

`migrations/0003_coverage.sql` creates the derived-coverage schema from `component-design-market-data-store.md` section 2.3:

- `coverage_segment`, including `coverage_data_type_known`, `coverage_range_ordered`, the GiST `coverage_no_overlap` exclusion constraint and `idx_coverage_instrument`;
- `acquisition_state`, including its `(instrument_id, data_type)` primary key, last-acquired fields, and known data-type and outcome checks;
- `last_run_id` remains a UUID without a foreign key to migration 0004, avoiding a forward migration dependency.

`migrations/0004_runs.sql` creates the run journal from the same design section:

- `acquisition_run`, including known-state, positive-depth, claim-agreement and terminal-end checks;
- the single-active, FIFO-requested and recent-run indexes;
- `run_instrument_result`, including its composite key, foreign keys, known data-type and outcome checks, and failure index.

Neither migration contains `BEGIN` or `COMMIT`; the existing migrator owns the transaction boundary.

### State Machine

```
requested -> running | cancelled
running   -> cancelling | succeeded | partial | failed | abandoned
cancelling -> cancelled | abandoned
```

All five terminal states are absorbing.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Applying migrations through 0003 creates coverage/state tables but no run tables; applying 0004 then creates the run journal.
- Unknown coverage data types, reversed ranges and overlapping coverage segments are rejected; disjoint segments remain valid.
- `acquisition_state` retains the last attempt independently of whether coverage changed.
- Every legal run transition succeeds; representative illegal transitions raise in `states.py` before reaching the database.
- Inserting a second active run violates the partial unique index.
- A terminal run without an end timestamp is rejected.
- A run row snapshots depth at creation and is unaffected by a later setting change.
