# Run Schema and State Machine

## User Story

As an owner-operator, I want every run recorded with an outcome that cannot overstate what happened, so that a run marked succeeded means every instrument actually wrote.

## Description

Delivers migration `0004_runs.sql` (`acquisition_run`, `run_instrument_result`, `acquisition_state`) and `src/factorflow/runs/states.py`.

Module: `run-journal` and `market-data-store`. The capability's honesty requirements are expressed as which transitions are **forbidden**, so the state machine is encoded and checked rather than left to convention.

Five terminal exits from `running` are not interchangeable: `succeeded` requires every named instrument to have written, `partial` is the honest outcome when some did not, `cancelled` records the owner's decision and is never `failed`, and `abandoned` records a runner that died and is distinct from both.

Source: `component-design-run-journal.md` section 2.2; `component-design-market-data-store.md` section 2.3.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-9] Given any run, When it reaches a terminal state, Then it is recorded succeeded, failed or partial, and never succeeded when a named instrument failed.
- [DAC-E5-1] Given the state machine, When a transition is attempted, Then only requested, running, cancelling, succeeded, partial, failed, cancelled and abandoned exist, and an illegal transition raises rather than being written.
- [DAC-E5-3] Given two concurrent claims, When both attempt to start a run, Then a partial unique index makes the second fail on a unique violation rather than start a second run.

### Derived

- [DAC-E5-S1-1] Given `states.py`, When a transition is requested, Then it is checked against a mapping of legal transitions and an illegal one raises before any write. (traces to: DAC-E5-1)
- [DAC-E5-S1-2] Given the database, When a run row is written, Then check constraints `acquisition_run_state_known`, `acquisition_run_claim_agrees` and `acquisition_run_terminal_has_end` act as the backstop behind the application check. (traces to: DAC-E5-1)
- [DAC-E5-S1-3] Given a run row, When it is created, Then it snapshots `history_depth_years` at request time, so a depth changed while queued does not redefine it. (traces to: DAC-E4-8)
- [DAC-E5-S1-4] Given at most one active run, When the index is defined, Then a partial unique index over runs in `running` or `cancelling` enforces it. (traces to: DAC-E5-3)
- [DAC-E5-S1-5] Given FIFO ordering, When requested runs are queried, Then an index on `requested_at` serves the claim's ordering. (traces to: DAC-E5-2)
- [DAC-E5-S1-6] Given a terminal run, When it is written, Then it carries an end timestamp, enforced by constraint. (traces to: AC-9)
- [DAC-E5-S1-7] Given `run_instrument_result`, When rows are written, Then each carries instrument, data type, outcome and reason, supporting per-data-type reporting. (traces to: AC-10)

## Technical Details

### Data Changes

`migrations/0004_runs.sql` creates `acquisition_run`, `run_instrument_result` and `acquisition_state` per `component-design-market-data-store.md` section 2.3, including:

```sql
CREATE UNIQUE INDEX idx_acquisition_run_single_active
    ON acquisition_run ((true)) WHERE state IN ('running', 'cancelling');
CREATE INDEX idx_acquisition_run_requested
    ON acquisition_run (requested_at) WHERE state = 'requested';
```

### State Machine

```
requested -> running | cancelled
running   -> cancelling | succeeded | partial | failed | abandoned
cancelling -> cancelled | abandoned
```

All five terminal states are absorbing.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Every legal transition succeeds; a sample of illegal ones raise in `states.py` before reaching the database.
- Inserting a second `running` run violates the partial unique index.
- A terminal state without an end timestamp is rejected.
- A run row snapshots the depth at creation and is unaffected by a later setting change.
