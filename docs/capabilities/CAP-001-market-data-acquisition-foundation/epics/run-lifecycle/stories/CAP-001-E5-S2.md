# FIFO Claim and Request Queueing

## User Story

As an owner-operator, I want a second run request to queue behind the first rather than be rejected, so that I can ask for a run without checking whether one is already going.

## Description

Delivers the request and claim halves of `src/factorflow/runs/journal.py`.

Module: `run-journal`. The claim is **one statement in one transaction**, with no read-then-write window. The `NOT EXISTS` clause is the one-active-run rule and `ORDER BY requested_at` is AC-23's FIFO requirement.

The partial unique index makes a race that slipped past the guard fail on a unique violation rather than start a second run, so correctness does not rest on the statement alone.

Source: `component-design-run-journal.md` sections 2.2, 2.3.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-23] Given a run already under way, When another is requested, Then it is accepted as requested and starts only after the active run reaches a terminal state, in request order.
- [DAC-E5-2] Given the claim, When it executes, Then it is a single statement claiming the oldest requested run only when none is running or cancelling.
- [DAC-E5-3] Given a race, When two claims execute concurrently, Then one fails on a unique violation rather than starting a second run.

### Derived

- [DAC-E5-S2-1] Given several requested runs, When claims occur, Then they are claimed oldest-first by `requested_at`, so request order is execution order. (traces to: AC-23)
- [DAC-E5-S2-2] Given no claimable run, When the runner polls, Then it receives no row and waits at the configured interval rather than erroring. (traces to: AC-23)
- [DAC-E5-S2-3] Given a claim, When it succeeds, Then it sets `state`, `started_at`, `claimed_by` and `heartbeat_at` in the same statement. (traces to: DAC-E5-10)
- [DAC-E5-S2-4] Given a claim, When it returns, Then it yields the run id and the snapshotted `history_depth_years`, so the runner plans from the run's own record. (traces to: DAC-E4-8)
- [DAC-E5-S2-5] Given `FOR UPDATE SKIP LOCKED`, When two runners contend, Then neither blocks on the other's row. (traces to: DAC-E5-3)
- [DAC-E5-S2-6] Given a queued request, When it is created while a run is active, Then the response reports the active run it is queued behind. (traces to: DAC-E5-15)

## Technical Details

### Claim Statement

```sql
UPDATE acquisition_run
   SET state = 'running', started_at = now(),
       claimed_by = %(runner_id)s, heartbeat_at = now()
 WHERE run_id = (
       SELECT run_id FROM acquisition_run
        WHERE state = 'requested'
          AND NOT EXISTS (SELECT 1 FROM acquisition_run
                           WHERE state IN ('running', 'cancelling'))
        ORDER BY requested_at LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING run_id, history_depth_years;
```

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Three requested runs are claimed in request order.
- A claim attempted while one is `running` returns no row.
- Concurrent claims from two connections: exactly one succeeds; the other returns no row or fails on the unique index, and never starts a second run.
- A claim returns the snapshotted depth, not the current setting.
