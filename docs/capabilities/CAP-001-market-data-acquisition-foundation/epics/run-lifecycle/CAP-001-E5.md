# Run Lifecycle: Queueing, Cancellation and Recovery

**EPIC ID:** CAP-001-E5
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Own the acquisition run record and its full lifecycle, so that every run reaches a terminal state that means what it says. A run is requested, claimed only when no other is active, and exits through one of five terminal states that are not interchangeable: succeeded requires every instrument to have written, partial is the honest outcome when some did not, cancelled records the owner's decision, and abandoned records a runner that died. This EPIC is what keeps a killed container from wedging acquisition with no remedy short of editing the data store by hand. Delivers the Runs screen and the run controls.
**Actors:** Owner-operator, run-journal, acquisition-runner, ingestion-api, owner-web-app
**Estimate:** L
**Out of Scope:** Acquiring or writing data (E4); presenting per-instrument failure reasons (E7); deriving coverage (E6)
**Dependencies:** E1 (schema), E2 (instrument list and stated depth, both preconditions the start endpoint enforces). E4 consumes this EPIC's claim contract and can be developed in parallel against it.
**Links:** system-design.md sections 3 (queued requests, cancellation, reclaim), 4.2, 5.7, 5.17, 5.18, 5.19, 5.20; component-design-run-journal.md sections 2.2, 2.3; component-design-acquisition-runner.md section 2.5; component-design-ingestion-api.md section 11; ux-design.md sections 1.4, 1.5

## Goals

- Record every acquisition run with an outcome that cannot overstate what happened.
- Permit at most one active run, with further requests queued in request order rather than rejected.
- Let the owner cancel a run that is under way, and one that is merely queued, with different and correct semantics for each.
- Guarantee that every claimed run reaches a terminal state without the owner touching the data store.
- Refuse a run that has nothing to acquire, rather than recording one whose outcome would misrepresent an empty list.

## Non-Functional Requirements

- **Concurrency:** The claim is a single statement in one transaction, with no read-then-write window. A partial unique index makes a race that slipped past the guard fail on a unique violation rather than start a second run.
- **Correctness:** Legal state transitions are encoded and checked in code, so an illegal transition raises rather than being written. Database check constraints are the backstop.
- **Recovery:** Claims carry a heartbeat. A periodic sweep in the application container reclaims a claim stale past the configured window as abandoned, because a component cannot be relied on to notice its own death.
- **Responsiveness:** The start endpoint returns immediately, so the browser never waits on the provider. The Runs screen polls every 10 seconds while any run is non-terminal and stops when none is (STD-UI-25).
- **Presentation:** Run outcomes render in the tiers STD-UI-12 fixes: partial is a warning and never good; cancelled is neutral and never critical; abandoned is serious and distinct from both failed and cancelled.

## EPIC Acceptance Criteria

### From Capability

- [AC-9] Every acquisition run MUST be recorded as succeeded, failed or partial, and MUST NOT be recorded as succeeded when any named instrument failed to acquire.
- [AC-19] An owner-operator MUST be able to cancel an acquisition run that is under way. The cancelled run MUST NOT begin acquiring any instrument it had not already started, and coverage already written MUST be retained.
- [AC-20] An acquisition run whose process stops unexpectedly MUST reach a terminal state without the owner-operator modifying the data store, and MUST NOT prevent a subsequent run from starting.
- [AC-23] When the owner-operator starts an acquisition run while another run is under way, the product MUST accept the new request, record it as requested, and start it only after the active run reaches a terminal state. Requested runs MUST start in request order.
- [AC-24] When the owner-operator starts an acquisition run while no instrument is active, the product MUST refuse the request, state that no instruments are named, and record no run.
- [AC-26] When the owner-operator cancels an acquisition run that has been requested but not yet started, the product MUST record it as cancelled, MUST NOT start it, and MUST leave any run already under way unaffected.

### Derived

- [DAC-E5-1] The run state machine MUST define exactly the states requested, running, cancelling, succeeded, partial, failed, cancelled and abandoned, with illegal transitions raising rather than being written. (traces to: AC-9)
- [DAC-E5-2] The claim MUST be a single statement claiming the oldest requested run only when no run is running or cancelling, so that request order is execution order. (traces to: AC-23)
- [DAC-E5-3] A partial unique index MUST make a concurrent second claim fail on a unique violation rather than start a second run. (traces to: AC-23)
- [DAC-E5-4] The run outcome MUST be computed from what was actually written rather than from what was requested. (traces to: AC-9, AC-12)
- [DAC-E5-5] A run MUST be recorded succeeded only when every instrument in its roster wrote; otherwise partial when some wrote, or failed when none wrote or the run itself failed. (traces to: AC-9)
- [DAC-E5-6] Cancellation of a running run MUST be recorded as a request against the run rather than acting on the process, and MUST be observed by the runner between instruments, so it takes effect within one instrument's work. (traces to: AC-19)
- [DAC-E5-7] A cancelled run MUST be terminal and distinct from failed, and coverage already committed MUST be retained. (traces to: AC-19)
- [DAC-E5-8] Cancelling a run still in the requested state MUST move it directly to cancelled as a state transition rather than cooperative cancellation, since there is no runner to signal, and MUST leave an active run unaffected. (traces to: AC-26)
- [DAC-E5-9] Cancelling a run that has already reached a terminal state MUST return a conflict naming the run's actual state, so the owner is told it completed rather than shown a cancellation that did not happen. (traces to: AC-19)
- [DAC-E5-10] A runner MUST refresh a heartbeat on the run it holds, at the same point it checks for cancellation. (traces to: AC-20)
- [DAC-E5-11] A periodic sweep in the application container MUST release any claim whose heartbeat is stale past the configured window and record the run as abandoned, terminal and distinct from both failed and cancelled. (traces to: AC-20)
- [DAC-E5-12] The sweep MUST be idempotent and MUST NOT prevent a subsequent run from starting once it has released a stale claim. (traces to: AC-20)
- [DAC-E5-13] A runner whose claim has been reclaimed MUST stop without writing further results against that run. (traces to: AC-20)
- [DAC-E5-14] The start endpoint MUST refuse with a conflict and create no run when no history depth is set, and separately when no instrument is active, naming which precondition failed. (traces to: AC-24, AC-2)
- [DAC-E5-15] The start endpoint MUST accept a request while a run is active, returning the new run as requested together with the active run it is queued behind, and MUST NOT reject, merge or start it concurrently. (traces to: AC-23)
- [DAC-E5-16] Run outcomes MUST render in the tiers STD-UI-12 fixes, with partial never good, cancelled never critical, and abandoned distinct and serious. (traces to: AC-9)
- [DAC-E5-17] The abandoned state MUST be explained to the owner rather than presented as a bare state, together with the path to a new run. (traces to: AC-20)
