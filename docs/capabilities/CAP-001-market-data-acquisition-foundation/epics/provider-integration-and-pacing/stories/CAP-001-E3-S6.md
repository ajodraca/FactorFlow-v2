# Provider Base URL: Validate at Start and Honour It, Release Build Only

## User Story

As the owner-operator, I want `FACTORFLOW_MASSIVE_BASE_URL` validated as an `https` URL when ingestion starts and then used for every provider request, so that the provider credential can only ever be sent over TLS to the host I configured, and never follows a redirect or a proxy somewhere else.

## Description

Today `MassiveSettings.base_url` is loaded but never validated, and `MassiveClient` builds `RESTClient` without `base=`, so the setting has no effect and the SDK always uses its built-in host. The approved designs close both gaps for the release build. This story implements every part of that change that applies in every build and needs nothing from CONST-SEC 1.2. The loopback `http` allowance (clause 2a) is CAP-001-E3-S7.

Modules: `runtime-config` (`src/factorflow/config/settings.py`) and `massive-client` (`src/factorflow/ingestion/massive/client.py`), with a start-refusal test against `factorflow.ingestion_main` (owned by `acquisition-runner`). One writable repository, `FactorFlow-v2`.

Scope:

1. **Base URL validator** on `MassiveSettings` (`runtime-config` section 2.2c, *The rule*, clauses 1 to 9 and the value table). `https` only. No setting, flag, constant or environment variable in `src/` accepts `http` (section 2.2c item 1, DEC-0033). The snippet in section 2.2c is the reference implementation.
2. **`base=settings.base_url`** on the SDK client (`massive-client` section 2.2b). `RESTClient.__init__` hands the same `base` to its `vx` sub-client, so one argument covers every read.
3. **No redirect and no proxy, proven socket-free** (`massive-client` sections 2.2b and 7, DEC-0038), with the corrections the owner directed from specification review v7 FINDING-19 and the extra assertion decided for FINDING-21 (DEC-0041).
4. **TLS and default-base tests**: `tests/unit/test_massive_tls.py` does not exist yet (expedited review EXP-20261009-1 ER-001, ER-004).
5. **Release-artifact exclusion test** (`runtime-config` section 7, `tests/unit/test_release_excludes_test_paths.py`; DEC-0033, DEC-0034). It asserts what the release artifact contains, which this story changes.

Placement and split: DEC-0039.

Out of scope: clause 2a, the test-only entry point, the `main()` parameters and the `scripts/run-e2e-server.sh` change (CAP-001-E3-S7). Also out of scope, because they are open owner questions: the standing of other host-local plaintext channels under SEC-ENC-001 (`runtime-config` section 14 item 6), the ratios response shape (`massive-client` section 14 item 7, specification review v6 FINDING-2), how the production ingestion container is launched (`runtime-config` section 14 item 5), and naming this setting in the release evidence (`runtime-config` section 3, ER-002), which is release readiness. The setting validates scheme and shape, not host. An allow-list is not wanted (`runtime-config` section 3).

**Known interim effect (specification review v7 FINDING-10 (a), not resolved here).** Once this story lands, the E2E acquisition stack in `scripts/run-e2e-server.sh` (line 145, `FACTORFLOW_MASSIVE_BASE_URL=http://127.0.0.1:8126`) starts an ingestion process that exits at start. The script waits only on the acquisition API's health, so the acquisition E2E journeys then fail with no visible cause until CAP-001-E3-S7 lands. The approved design specifies the script change only for when clause 2a takes effect, so this story does not change the script. See Open Questions.

## Technical Details

### API Contract

No HTTP endpoint changes. The configuration contract changes as follows:

- `FACTORFLOW_MASSIVE_BASE_URL`: optional, default `https://api.massive.com`, validated per `runtime-config` 2.2c and normalised by removing one trailing `/`.
- Failure: `ConfigurationError` at start, message `FACTORFLOW_MASSIVE_BASE_URL: <clause that failed>`, formatted with `include_input=False` by `_EnvNamedSettings`. The ingestion process exits non-zero.
- `MassiveClient.__init__` passes `base=settings.base_url` alongside the existing `retries=0`, `connect_timeout`, `read_timeout`, `pagination=False` and `trace=False`. No `redirect` argument, no replacement `Retry`, no proxy and no `ProxyManager` (2.2b).

### Data Changes

None.

### Implementation

- `src/factorflow/config/settings.py`: `@field_validator("base_url")` on `MassiveSettings`, as the 2.2c snippet shows. Use `urlsplit`. The validator checks the scheme first and returns the value without its single trailing `/`. Add no `http` branch and no flag.
- `src/factorflow/ingestion/massive/client.py`: add `base=settings.base_url` to the `RESTClient(...)` call. Update the 2.2b comment. Leave the `retries=0` line as it is.

### Testing

`pytest`, all marked `not postgres`, no socket:

| `tests/unit/test_ingestion_main.py` (extend) | DAC-E3-S6-7 |
| `tests/unit/test_massive_tls.py` (new) | DAC-E3-S6-8 (default base), S6-11 |

The redirect and proxy tests generate their key per test. No fixed key literal is committed (`runtime-config` 2.2c item 3).

### Validation

`uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`.

### Rollback

Revert the commit. The validator and `base=` are independent of stored data. With them reverted, the setting is ignored again and the SDK default host is used.

### Dependencies

- **CAP-001-E1-S3**: `MassiveSettings`, `_EnvNamedSettings` and `ConfigurationError`, which the validator extends.
- **CAP-001-E3-S1**: `MassiveClient`'s `RESTClient` construction, which gains `base=`.
- **CAP-001-E3-S4**: the `RateLimitGovernor` whose production retry count DAC-E3-S6-13 and S6-14 assert.
- **CAP-001-E4-S5**: `factorflow.ingestion_main`, which DAC-E3-S6-7 drives. This is a deliberate dependency on a story in a **later** epic: the start-refusal test needs the ingestion entry point, which E4 owns. E4-S5 is already implemented, so it does not delay this story.

Consumed by CAP-001-E3-S7, which wraps this validator for the test-only entry point.

## Open Questions

- **Interim E2E breakage (specification review v7 FINDING-10 (a)).** Between this story landing and CAP-001-E3-S7 landing, the acquisition E2E stack's ingestion process exits at start, and the failure is silent. The approved design does not state this interim. Options include landing E3-S6 and E3-S7 together, or the review's suggestion of making the script fail loudly while held. Choosing between them is the owner's call and needs a design change. *Owner: capability owner. Not blocking for this story.*
- **Rejection reason for `http://::1:8126` (specification review v7 FINDING-12 (c)).** The 2.2c table gives "host missing", but the approved validator checks the scheme first and reports "scheme must be https". DAC-E3-S6-5 asserts only that the value is rejected and the variable is named, which holds under either reading. The table needs correcting at the next `runtime-config` revision.
