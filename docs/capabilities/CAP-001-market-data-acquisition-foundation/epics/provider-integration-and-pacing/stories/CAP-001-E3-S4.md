# Rate Limit Governor: Pacing, Throttle Waits and Bounded Backoff

## User Story

As an owner-operator, I want the product paced to my provider plan and resilient to transient failures, so that a long run neither trips limits nor gives up on a brief outage.

## Description

Delivers `src/factorflow/ingestion/rate_limit.py`.

Module: `rate-limit-governor`. The component's whole point is that **throttling is not an attempt**: a `429` means the request was never served, so waiting it out must not consume the retry budget. Conflating the two would either abandon instruments over ordinary throttling or retry a genuine outage until the run never ends.

Massive sends no `Retry-After`, verified against the live provider on 2026-09-05. So the live path waits to the next minute boundary, matching the fixed per-minute window the provider actually enforces. Exponential backoff would either wait past the refill, idling the run, or retry before it and consume a second 429.

Source: `component-design-rate-limit-governor.md` sections 2.5, 3; system design 5.13, 5.14.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-4] Given a run of up to 3000 instruments, When it executes, Then pacing keeps it within the configured budget without manual intervention.
- [DAC-E3-6] Given a `429`, When it is handled, Then the attempt counter is unchanged, because the request was never served.
- [DAC-E3-7] Given no `Retry-After` from the provider, When throttled, Then the wait runs to the next minute boundary with jitter rather than applying exponential backoff.
- [DAC-E3-8] Given a timeout or server error, When it occurs, Then it is retried with exponential backoff up to a configured attempt limit defaulting to 3.
- [DAC-E3-9] Given a provider returning `429` indefinitely, When the throttle wait budget is exhausted, Then the instrument fails rather than the run stalling forever.

### Derived

- [DAC-E3-S4-1] Given a provider that does state a delay, When throttled, Then the stated delay is honoured. This path is dead code against Massive and is retained because the governor is provider-agnostic. (traces to: DAC-E3-7)
- [DAC-E3-S4-2] Given several retries queued behind the same minute boundary, When they wait, Then full jitter is applied so they do not resynchronise onto the same instant. (traces to: DAC-E3-7)
- [DAC-E3-S4-3] Given a `FATAL` outcome such as 404 or 401, When it is seen, Then no wait and no retry occur and it re-raises to the caller immediately. (traces to: DAC-E3-2)
- [DAC-E3-S4-4] Given the attempt limit is exhausted for one instrument and data type, When exhaustion occurs, Then that instrument is recorded failed and the run continues. (traces to: AC-11)
- [DAC-E3-S4-5] Given the configured request budget, When the plan has no limit, Then pacing introduces no artificial delay, since the target plan is unlimited as verified 2026-09-05. (traces to: AC-4)
- [DAC-E3-S4-6] Given the throttle wait budget, When it is configured, Then it bounds the throttled path so `OPS-LOOP-001`'s unbounded-loop failure cannot occur. (traces to: DAC-E3-9)

## Technical Details

### Outcome Table

| Outcome | Attempt counter | Wait | Then |
|---|---|---|---|
| `THROTTLED`, provider stated a delay | unchanged | the stated delay | retry |
| `THROTTLED`, no stated delay (the Massive case) | unchanged | to the next minute boundary, with jitter | retry |
| `RETRYABLE` (timeout or 5xx) | plus one | initial delay times two to the power of attempts, with jitter | retry while attempts remain |
| `OK` | unchanged | none | return |
| `FATAL` (404, 401, not retryable) | unchanged | none | re-raise |

Two budgets bound the loop: the attempt limit (default 3, owner decision 2026-09-04) and a separate throttle wait budget.

### Testing

- `pytest`, marked `not postgres`, with a controlled clock so no test sleeps in real time.
- A `429` does not increment the attempt counter, asserted directly.
- Repeated `429` exhausts the throttle wait budget and fails the instrument rather than looping forever.
- A timeout increments attempts and retries with growing delays.
- Three failures exhaust the limit; the fourth attempt is not made.
- Jitter is exercised by asserting successive computed delays are not identical.
- A `FATAL` outcome neither waits nor retries.

### Validation

`uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run mypy src`.
