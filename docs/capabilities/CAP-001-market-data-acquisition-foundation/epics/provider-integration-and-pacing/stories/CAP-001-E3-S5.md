# Provider Failure Reasons and Credential Safety

## User Story

As an owner-operator diagnosing a failure, I want each recorded reason to name the symbol, the data type and the provider's own request id, so that I can trace it with the provider and never see my key in the record.

## Description

Wires the typed errors from CAP-001-E3-S3 into the reason strings stored against per-instrument results, and adds the safety test that no reason can carry the credential.

Module: `massive-client`. Small but deliberately separate: it is the seam where a provider error becomes owner-visible text, and it carries the security assertion for that path.

Massive returns a `request_id` on every response including errors. It is the identifier the provider can trace, which is what makes a reported failure actionable rather than merely descriptive.

Source: `component-design-massive-client.md` sections 2.4, 4.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-13] Given any stored or rendered failure reason, When it is written, Then it contains no part of the provider credential.
- [DAC-E3-13] Given a failure reason, When it is recorded, Then it names the symbol, the data type and the provider's `request_id`.

### Derived

- [DAC-E3-S5-1] Given a provider response without a `request_id`, When a reason is composed, Then the reason records its absence rather than fabricating or omitting the field silently. (traces to: DAC-E3-13)
- [DAC-E3-S5-2] Given a `CredentialRejected` error, When its reason is composed, Then it states that the credential was rejected without echoing any part of the value. (traces to: AC-13)
- [DAC-E3-S5-3] Given a reason string, When it is stored, Then it is bounded in length so a pathological provider message cannot bloat the run record. (traces to: DAC-E3-13)
- [DAC-E3-S5-4] Given any of the four typed errors, When a reason is composed, Then the resulting text distinguishes which type it came from, so `not_found` is separable from `failed` downstream. (traces to: AC-11)

## Technical Details

### Implementation

- A reason composer in the `massive-client` module producing the text stored in `run_instrument_result.reason` by CAP-001-E4-S6.
- Shape: error kind, symbol, data type, provider request id when present.
- Length bounded; truncation marked rather than silent.

### Testing

- `pytest`, marked `not postgres`.
- A property-style test constructs reasons from each error type with a credential-like value present in the environment and asserts it appears in no output.
- Absent `request_id` renders explicitly as unavailable.
- An over-long provider message is truncated with the truncation visible.
- Each error type yields a distinguishable reason.

### Validation

`uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E3-S3**, the typed errors.

Consumed by CAP-001-E4-S6, which records these reasons on per-instrument results.
