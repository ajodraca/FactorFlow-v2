# Massive Client: The Four Historical Reads

## User Story

As the acquisition runner, I want one operation per data type accepting a symbol and a date range, so that I can drive acquisition without knowing provider paths or wire formats.

## Description

Delivers `src/factorflow/ingestion/massive/client.py` and `paging.py`.

Module: `massive-client`. A thin project-owned boundary around Massive's official `massive` Python client, adding pacing, retry, error typing and test substitution. Per the tech stack the provider is deliberately **not** abstracted behind a vendor-neutral port, so this client may use Massive's own shapes internally.

The interface must leave room for the M3 streaming half of the same provider contract without redefinition (C4).

Source: `component-design-massive-client.md` sections 2.2, 2.2b, 2.3, 2.5.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-3] Given a named instrument the provider covers, When the four reads are called, Then reference data, daily prices, fundamentals and corporate actions are returned over the requested range.
- [DAC-E3-1] Given the client, When it is used, Then it exposes one operation per data type, each accepting a symbol and a date range.
- [DAC-E3-10] Given reference data, When it is read, Then it captures CIK, composite FIGI and share class FIGI so identity does not rest on the ticker.
- [DAC-E3-11] Given a delisted instrument, When it is read, Then it remains acquirable and carries its active flag and delisting date.
- [DAC-E3-14] Given the client interface, When it is designed, Then it does not foreclose the M3 streaming half.

### Derived

- [DAC-E3-S1-1] Given the SDK's default construction, When the client is built, Then the defaults the component design identifies as requiring override are overridden explicitly rather than inherited. (traces to: DAC-E3-1)
- [DAC-E3-S1-2] Given daily aggregates, When they are requested, Then the multiplier is `1`, the timespan is `day`, and `from` and `to` are inclusive `YYYY-MM-DD`. (traces to: AC-3)
- [DAC-E3-S1-3] Given a paged response, When `next_url` is present, Then paging follows it until exhausted and the caller sees one complete result. (traces to: AC-3)
- [DAC-E3-S1-4] Given the ticker reference endpoint, When it is called, Then the single-ticker form is used, since the instrument list is the owner's and reference data is fetched per named symbol. (traces to: DAC-E3-1)
- [DAC-E3-S1-5] Given the market-status endpoint, When acquisition runs, Then it is never called, because it is forward-looking only and trading days are derived from acquired data instead. (traces to: AC-8)
- [DAC-E3-S1-6] Given the credential, When the client is constructed, Then it is passed to the SDK and never written to a log record. (traces to: AC-13)

## Technical Details

### Provider Endpoints

| Data type | Path | Notes |
|---|---|---|
| Reference | `GET /v3/reference/tickers/{ticker}` | Single object, not paged. Fields: `active`, `cik`, `composite_figi`, `share_class_figi`, `list_date`, `delisted_utc`, `primary_exchange`, `name`, `type`, `currency_name` |
| Daily prices | `GET /v2/aggs/ticker/{t}/range/1/day/{from}/{to}` | Paged by `next_url`; `limit` default 5000, max 50000 |
| Fundamentals | per component design section 2.5 | Paged |
| Corporate actions | per component design section 2.5 | Paged |

Deliberately unused: `GET /v1/marketstatus/upcoming` (forward-looking only) and `GET /v3/reference/tickers` list form (recorded for a later capability building a universe from the provider).

### Testing

- `pytest`, marked `not postgres`; the SDK is substituted at the boundary this client owns.
- Each of the four reads returns parsed results for a covered symbol.
- Paging follows `next_url` across at least two pages.
- A delisted fixture returns `active: false` with `delisted_utc` set.
- A test asserts the market-status path is never requested.
- A test asserts no log record contains the credential.

### Validation

`uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E1-S3**, the credential from runtime configuration.
- **CAP-001-E3-S2**, the models the reads parse into. Developable together.
