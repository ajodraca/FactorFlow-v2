# Provider Error Taxonomy

## User Story

As the acquisition runner, I want provider failures typed precisely, so that I can skip an instrument the provider does not recognise without mistaking an outage for one.

## Description

Delivers `src/factorflow/ingestion/massive/errors.py`.

Module: `massive-client`. The component design names this the most fragile code in the component, carrying the most tests, because the SDK raises one exception for every non-200 with **the status code discarded**, and AC-11 depends on telling a 404 from a 401.

The taxonomy reconstructs the distinction by parsing the error envelope. Two properties make that necessary and fragile: the failure field is not stably named, a 404 carrying `message` while 401 and 429 carry `error`; and `status` is `"NOT_FOUND"` on a missing ticker and `"ERROR"` on everything else.

If the SDK later preserves the status code on the exception, this module should be reduced to reading it.

Source: `component-design-massive-client.md` sections 2.4, 2.6a.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-11] Given a symbol the provider does not recognise, When it is fetched, Then the failure is typed so the run can report that instrument and continue.
- [DAC-E3-2] Given a provider failure, When it is classified, Then it is one of `InstrumentNotFound`, `CredentialRejected`, `ProviderUnavailable` or `ProviderContractViolation`.
- [DAC-E3-3] Given the SDK discards the status code, When an error is classified, Then the envelope is parsed accepting either `message` or `error` as the failure field and requiring neither.
- [DAC-E3-4] Given an error payload that will not parse as JSON, When it is classified, Then it is `ProviderUnavailable` and never `InstrumentNotFound`.
- [DAC-E3-5] Given a `200` that fails model validation, When it is classified, Then it is `ProviderContractViolation`, distinct from unavailability.
- [DAC-E3-13] Given any typed error, When it is raised, Then it carries the provider's `request_id` and never the credential.

### Derived

- [DAC-E3-S3-1] Given an envelope whose `status` is `"NOT_FOUND"`, When it is classified, Then it becomes `InstrumentNotFound`. (traces to: DAC-E3-2)
- [DAC-E3-S3-2] Given an envelope whose `error` names an API-key problem, When it is classified, Then it becomes `CredentialRejected`, and the credential value appears in neither the exception nor any log record. (traces to: DAC-E3-13)
- [DAC-E3-S3-3] Given an envelope that parses but matches no known case, When it is classified, Then it becomes `ProviderUnavailable`, the safe default. (traces to: DAC-E3-4)
- [DAC-E3-S3-4] Given a `ProviderContractViolation`, When the runner handles it, Then retrying is not attempted, because it means the provider changed rather than that it is down. (traces to: DAC-E3-5)
- [DAC-E3-S3-5] Given every typed error, When it is constructed, Then `provider_request_id` is populated from the response when present and `None` when absent, never fabricated. (traces to: DAC-E3-13)
- [DAC-E3-S3-6] Given a `429`, When it is seen, Then it is not raised as a failure at all but handed to the governor as flow control. (traces to: DAC-E3-6)

## Technical Details

### Taxonomy

```python
class MassiveError(Exception):
    def __init__(self, message: str, *, provider_request_id: str | None = None): ...

class InstrumentNotFound(MassiveError): ...      # provider does not recognise the symbol
class CredentialRejected(MassiveError): ...      # API-key problem
class ProviderUnavailable(MassiveError): ...     # transport, 5xx, or unclassifiable
class ProviderContractViolation(MassiveError): ...  # 200 failing validation, or unparseable envelope shape
```

Classification order: parse the `BadResponse` payload as JSON; `status == "NOT_FOUND"` or the documented not-found text becomes `InstrumentNotFound`; an `error` naming an API-key problem becomes `CredentialRejected`; anything else becomes `ProviderUnavailable`. A payload that will not parse as JSON is `ProviderUnavailable`.

### Testing

This module carries the most tests in the component. At minimum:

- A 404 envelope with `message` classifies as `InstrumentNotFound`.
- A 401 envelope with `error` classifies as `CredentialRejected`.
- A 429 envelope is handed to the governor, not raised.
- Unparseable bytes classify as `ProviderUnavailable`, asserted explicitly **not** `InstrumentNotFound`, since that false negative is what AC-12 exists to prevent.
- A valid-JSON envelope of an unknown shape classifies as `ProviderUnavailable`.
- A `200` failing model validation classifies as `ProviderContractViolation`.
- `provider_request_id` is populated when present and `None` when absent.
- No exception's `str()` contains the credential.
