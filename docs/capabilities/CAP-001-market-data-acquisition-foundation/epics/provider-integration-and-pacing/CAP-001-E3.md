# Provider Integration and Pacing

**EPIC ID:** CAP-001-E3
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Establish the one market-data contract through which all four data types are read from Massive: instrument reference, daily prices, company fundamentals and corporate actions. The client is a thin project-owned boundary around the provider's official Python SDK, adding pacing, retry, error typing and test substitution without reimplementing transport or protocol handling. Its error taxonomy is what lets a later run tell an unrecognised instrument from a provider outage, which AC-11 and AC-12 both depend on.
**Actors:** acquisition-runner (consumer), massive-client, rate-limit-governor, Massive REST API (external)
**Estimate:** L
**Out of Scope:** The live streaming feed and its long-lived connection, deferred to M3 behind this same contract; driving the run loop or writing observations (E4); calling `GET /v1/marketstatus/upcoming`, which is forward-looking only and deliberately unused; `GET /v3/reference/tickers` list form, recorded for a later capability that builds a universe from the provider
**Dependencies:** E1 (runtime configuration supplies the credential). The Massive dependency is typed `requires-runtime` in capability section 5.1 and carries `no-acceptance-criterion`, since Massive is an external provider rather than a capability. It binds at integration, not at design time, so this EPIC is startable now against the documented contract.
**Links:** system-design.md sections 4.1, 4.2 (provider reads), 5.6, 5.13, 5.14; component-design-massive-client.md sections 2.2, 2.2b, 2.3, 2.4, 2.5, 2.6; component-design-rate-limit-governor.md sections 2.5, 3

## Goals

- Read all four data types for a named instrument over a requested date range.
- Type provider failures precisely enough that the runner can isolate an unrecognised instrument without mistaking an outage for one.
- Pace requests to a configured budget, so the owner's plan rather than the code determines throughput.
- Treat rate limiting as flow control and errors as failures, since conflating them would either abandon instruments over ordinary throttling or retry a genuine outage until the run never ends.
- Leave room in the contract for the M3 streaming half without redefinition.

## Non-Functional Requirements

- **Throughput:** Request rate is a configured budget, not a hard-coded constant. The design is tier-agnostic; the owner's plan determines the budget. Verified 2026-09-05: the target plan (Stocks Starter with Financials and Ratios) has no rate limit, so AC-4's 3000 instruments are not throughput-bound.
- **Resilience:** Timeouts and server errors are retried with bounded exponential backoff, default 3 attempts per instrument and data type (owner decision, 2026-09-04). Full jitter applies so retries do not resynchronise.
- **Resilience:** A throttle wait budget bounds the throttled path, so a provider returning `429` indefinitely, which is what an exhausted monthly quota looks like, fails the instrument rather than stalling the run forever (OPS-LOOP-001).
- **Security:** The credential is passed to the SDK and never logged. No recorded failure reason may contain it (AC-13).
- **Observability:** The provider's `request_id`, present on every Massive response including errors, is recorded alongside the symbol and data type on every stored failure reason, since it is the identifier the provider can trace.

## EPIC Acceptance Criteria

### From Capability

- [AC-3] A successful acquisition run MUST provide, for each named instrument the provider covers, instrument reference data, daily prices, company fundamentals and corporate actions over the stated history depth.
- [AC-5] Every acquired value MUST be recorded with the date on which it was known. The provider's own filing date MUST NOT serve as that date.
- [AC-11] When the provider does not recognise a named instrument, the run MUST report that instrument and MUST continue acquiring the remaining instruments.
- [AC-13] The provider credential MUST NOT appear in log output or in any view the product renders.

### Derived

- [DAC-E3-1] The client MUST expose one operation per data type, each accepting a symbol and a date range, so that the runner drives acquisition without knowing provider paths. (traces to: AC-3)
- [DAC-E3-2] Provider failures MUST be typed as `InstrumentNotFound`, `CredentialRejected`, `ProviderUnavailable` or `ProviderContractViolation`, since AC-11 depends on telling a 404 from a 401. (traces to: AC-11)
- [DAC-E3-3] Because the SDK discards the status code and raises only the response body, the client MUST reconstruct the distinction by parsing the error envelope, accepting either `message` or `error` as the failure field and requiring neither. (traces to: AC-11)
- [DAC-E3-4] An error payload that will not parse as JSON MUST be classified `ProviderUnavailable` and never `InstrumentNotFound`, because guessing not-found from an unparseable error would let an outage look like an empty instrument. (traces to: AC-11, AC-12)
- [DAC-E3-5] A `200` response that does not validate against the model MUST be `ProviderContractViolation`, distinct from unavailability, because it means the provider changed rather than that it is down and retrying will not help. (traces to: AC-11)
- [DAC-E3-6] A `429` MUST NOT consume the attempt budget, because the request was never served. (traces to: AC-4, AC-11)
- [DAC-E3-7] Since Massive sends no `Retry-After`, verified against the live provider on 2026-09-05, the throttled path MUST wait to the next minute boundary with jitter, matching the fixed per-minute window the provider enforces, rather than applying exponential backoff. (traces to: AC-4)
- [DAC-E3-8] Timeouts and server errors MUST be retried with exponential backoff up to a configured attempt limit, defaulting to 3, after which the instrument is recorded failed and the run continues. (traces to: AC-11)
- [DAC-E3-9] A throttle wait budget MUST bound the throttled path so that indefinite `429` responses fail the instrument rather than stalling the run. (traces to: AC-4, AC-11)
- [DAC-E3-10] Reference data MUST capture stable instrument identity, including CIK, composite FIGI and share class FIGI, so identity does not rest on the ticker. (traces to: AC-3)
- [DAC-E3-11] A delisted instrument MUST remain acquirable, carrying its active flag and delisting date, so survivorship bias does not enter the recorded history. (traces to: AC-3, AC-5)
- [DAC-E3-12] Provider wire field names MUST NOT escape this component; models MUST name fields in the product's vocabulary. (traces to: AC-3)
- [DAC-E3-13] Every stored failure reason MUST carry the provider's `request_id` alongside the symbol and data type, and MUST NOT contain the credential. (traces to: AC-10, AC-13)
- [DAC-E3-14] The client's interface MUST NOT foreclose the M3 streaming half of the same provider contract. (traces to: AC-3)

## Open Questions

- **Massive's instrument coverage remains untested.** Whether the provider holds all four data types for every named instrument is unverified, and a shortfall changes AC-3. Recorded in capability section 7 and assumption 1. Rate limiting is closed: verified 2026-09-05, the target plan is unlimited. Not blocking for implementation, since the error taxonomy already handles a data type the provider does not hold, but it should be settled before AC-3 is treated as fixed.
- **The provider's error envelope was observed directly rather than documented.** Recorded in `component-design-massive-client.md` section 2.4 as the most fragile code in the component. If the SDK later preserves the status code on the exception, that mapping should be reduced to reading it.
