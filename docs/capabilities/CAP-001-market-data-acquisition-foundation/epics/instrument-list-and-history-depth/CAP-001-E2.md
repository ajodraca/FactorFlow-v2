# Instrument List and History Depth

**EPIC ID:** CAP-001-E2
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Give the owner-operator the two inputs every acquisition run depends on: the explicit list of instruments to acquire data for, and the stated depth history must reach. Instruments can be added singly or in bulk and retired without discarding what was already observed for them, because point-in-time history cannot be re-acquired as observed. History depth is stated by the owner and never assumed by the product. Delivers the Instruments and Settings screens.
**Actors:** Owner-operator, instrument-list-service, ingestion-api, owner-web-app
**Estimate:** M
**Out of Scope:** Composing a universe by rule, screen or ranking (a later capability owns that outcome); acquiring any data for the named instruments (E3, E4); enforcing the provider plan's history cap, which is issued as stated and returns what the provider holds (capability section 6)
**Dependencies:** E1 (schema, runtime configuration, and the application shell its Instruments and Settings screens render inside). No cross-capability blockers: `tech-stack.md` and `STD-UI` are typed `conforms-to` in capability section 5.1 and are designed against rather than waited on, so this EPIC is startable as soon as E1's schema exists.
**Links:** system-design.md sections 4.1, 4.2 (`/api/instruments`, `/api/settings/history-depth`), 5.8, 5.19; component-design-instrument-list-service.md sections 2.2, 2.3, 2.4, 2.5; component-design-ingestion-api.md section 11; component-design-owner-web-app.md section 2.1; ux-design.md sections 1.2, 1.3

## Goals

- Let the owner maintain the acquisition list without editing configuration files or the data store directly.
- Make bulk entry practical, since AC-4's 3000 instruments are not reachable one at a time.
- Make retirement mean retirement: acquisition stops, observations stand, and the distinction is visible.
- Require the history depth to be stated before the first run, and never acquire to a depth the owner has not stated.
- Fix a run's scope at claim time, so that what a run did is explainable from what it set out to do.

## Non-Functional Requirements

- **Volume:** The instrument list must remain usable at AC-4's 3000 instruments. The list and coverage tables require search and filter at that volume (STD-UI-30).
- **Usability:** Bulk entry accepts newline, comma, tab or semicolon separated symbols and reports what was recognised before anything is added. Rejected entries never discard accepted ones (ux-design 1.2).
- **Vocabulary:** Screen and action labels use the product vocabulary STD-UI-1 fixes. Retirement is confirmed as retirement, using `dialog` `confirm` rather than `destructive`, because it is not a destructive action (STD-UI-2).
- **Accessibility:** WCAG 2.1 AA per STD-UI-24. A control that cannot be used renders as `button` `blocked` with its reason stated, rather than disabled, because a disabled control hides its reason from keyboard and screen-reader users.
- **Error clarity:** Every error states the operation, the resource and the reason, per STD-UI-19.

## EPIC Acceptance Criteria

### From Capability

- [AC-1] The owner-operator MUST be able to add instruments to and remove them from the acquisition list, and see the current list, without editing configuration files or the data store directly.
- [AC-2] The product MUST require the owner-operator to state the history depth before the first acquisition run, and MUST NOT acquire to a depth the owner has not stated.
- [AC-21] Removing an instrument from the acquisition list MUST stop further acquisition for that instrument and MUST retain every observation already recorded for it. The owner-operator MUST be able to see that retained coverage and distinguish it from instruments still being acquired.
- [AC-25] An instrument retired while an acquisition run is under way MUST still be reached by that run, and MUST NOT be acquired by any later run.

### Derived

- [DAC-E2-1] Symbols MUST be normalised on entry to a single canonical form, so that the same instrument named two ways is one row. (traces to: AC-1)
- [DAC-E2-2] Adding a symbol already present and active MUST be reported as a duplicate rather than creating a second row; adding one already present and retired MUST reactivate it. (traces to: AC-1)
- [DAC-E2-3] Bulk entry MUST accept newline, comma, tab or semicolon separated symbols, and MUST report recognised and rejected entries separately before anything is added, with rejected entries never discarding accepted ones. (traces to: AC-1, AC-4)
- [DAC-E2-4] `POST /api/instruments` MUST return `201` when at least one symbol was added or reactivated, `409` when all were duplicates, and `422` when all were malformed. (traces to: AC-1)
- [DAC-E2-5] Retiring an instrument MUST be a lifecycle transition, never a delete. `DELETE /api/instruments/{symbol}` MUST return `404` for an unknown symbol and `409` for one already retired. (traces to: AC-21)
- [DAC-E2-6] Coverage reads MUST distinguish retired instruments rather than omitting them, so that retained history remains visible. (traces to: AC-21)
- [DAC-E2-7] History depth MUST be stated as a number of years, and `GET /api/settings/history-depth` MUST return `null` when never set, distinct from zero. (traces to: AC-2)
- [DAC-E2-8] `PUT /api/settings/history-depth` MUST reject a value that is not a positive integer with `422`. (traces to: AC-2)
- [DAC-E2-9] When no history depth is set, the Start action MUST render as `blocked` with its reason stated, rather than disabled or absent. (traces to: AC-2)
- [DAC-E2-10] The instrument list MUST support search and filter at 3000 instruments, and MUST report active and retired counts. (traces to: AC-1, AC-4)
- [DAC-E2-11] The retire confirmation MUST state that a run already under way still finishes with the instrument included. (traces to: AC-25)
- [DAC-E2-12] A depth beyond what the provider plan holds MUST be issued as stated, and a uniform shortfall across every instrument MUST NOT be presented as a provider data gap. (traces to: AC-2)
