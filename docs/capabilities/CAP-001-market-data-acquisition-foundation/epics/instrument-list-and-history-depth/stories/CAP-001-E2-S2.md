# History Depth Setting

## User Story

As an owner-operator, I want to state how far back history must reach, so that the product acquires to a depth I chose rather than one it assumed.

## Description

Delivers `src/factorflow/instruments/settings.py`, the read and write of the history depth setting held in `owner_setting`.

Module: `instrument-list-service`. The HTTP surface is CAP-001-E2-S3.

Depth is a number of years rather than an absolute start date. The two differ in meaning: years re-evaluates on every run, so five years in 2027 reaches further back in absolute terms than the same setting did in 2026. Years also fits how the provider bounds history, by plan tier rather than by calendar.

Source: `component-design-instrument-list-service.md` section 2.5; `ux-design.md` section 7, settled question.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-2] Given no stated history depth, When an acquisition run is requested, Then the product does not acquire to a depth the owner has not stated.
- [DAC-E2-7] Given the depth has never been set, When it is read, Then the result is `null`, distinct from zero.
- [DAC-E2-12] Given a depth beyond what the provider plan holds, When it is stated, Then it is issued as stated and a uniform shortfall is not presented as a provider data gap.

### Derived

- [DAC-E2-S2-1] Given a depth value, When it is written, Then it must be a positive integer number of years and any other value is rejected. (traces to: DAC-E2-8)
- [DAC-E2-S2-2] Given the setting store, When depth is written, Then it is held in `owner_setting` as a `jsonb` value under a fixed key, so a later setting needs no schema change. (traces to: AC-2)
- [DAC-E2-S2-3] Given a depth already set, When a new value is written, Then it replaces the previous one and `updated_at` advances. (traces to: AC-2)
- [DAC-E2-S2-4] Given a depth read, When it returns, Then it carries the `updated_at` timestamp alongside the value, so the interface can show when it was last changed. (traces to: DAC-E2-7)
- [DAC-E2-S2-5] Given the plan's five-year cap, When a larger depth is stated, Then this module records it unchanged and enforces no cap, because the provider returns what it holds. (traces to: DAC-E2-12)

## Technical Details

### Implementation

- `settings.py`, `get_history_depth()` returning `None` when unset, and `set_history_depth(years: int)`.
- `owner_setting` row keyed `history_depth_years`, value `{"years": <int>}`.
- `psycopg` 3, bound parameters, no ORM.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Unset depth returns `None`, and a test asserts `None` is distinguishable from `0`.
- Zero, negative and non-integer values are rejected.
- Overwriting advances `updated_at`.
- A depth of 50 years is stored unchanged, asserting no cap is enforced here.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E1-S1**, the `owner_setting` table.
