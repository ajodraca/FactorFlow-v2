# Coverage and Gap Visibility

**EPIC ID:** CAP-001-E6
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Let the owner-operator tell, without inspecting the data itself, which instruments have complete coverage over the range they need and which do not. Coverage is derived from what was actually written rather than from what a run intended to write, so a run that died partway cannot present as complete. Gaps are computed at read time against a trading-day set derived from the named instruments' own observed dates, since the provider supplies no historical calendar. Where that derivation carries no signal, the product says so rather than reporting a vacuous zero. Delivers the Coverage screen.
**Actors:** Owner-operator, coverage-service, ingestion-api, owner-web-app
**Estimate:** L
**Out of Scope:** Acquiring or writing the data being reported (E4); run history and per-instrument failure detail (E5, E7); charting, since CAP-001 renders no chart (system design 4.3)
**Dependencies:** E1 (schema), E4 (coverage segments and observations to read). The read contract is fixed by the component design, so this EPIC can be developed against it in parallel with E4.
**Links:** system-design.md sections 3 (steps 40-43), 4.1, 4.2 (`/api/coverage`), 5.5, 5.8, 5.9; component-design-coverage-service.md sections 2.2, 2.3, 2.4, 2.5; component-design-ingestion-api.md section 11; ux-design.md section 1.1

## Goals

- Show, per instrument, which data types are present, the date range covered, and when it was last acquired.
- Identify missing trading days inside a range already acquired for an instrument.
- Report coverage only as evidence of rows written, never as intent.
- Distinguish never-acquired from acquired-and-empty, so an empty view never reads as healthy.
- Say plainly when gap detection cannot mean anything, rather than reporting zero gaps.
- Keep retired instruments visible with their retained coverage, distinguishable from active ones.

## Non-Functional Requirements

- **Correctness:** The trading-day set is built from all named instruments' bars, never from the instrument being checked, since checking an instrument against its own dates would report zero gaps for every instrument always.
- **Honesty:** Gap detection is unavailable when fewer than two named instruments hold data in the range, and the availability predicate is applied inside the query so an unavailable check returns no rows rather than a zero count.
- **Scope:** Gap detection is a prices-only notion. Fundamentals are quarterly and corporate actions sporadic, so neither carries a per-day expectation.
- **Performance:** Deriving coverage is the most expensive read in the product, so the Coverage screen does not auto-poll and shows a last-updated time (STD-UI-25).
- **Volume:** The coverage table supports search and filter at AC-4's 3000 instruments (STD-UI-30).
- **Presentation:** Absent renders an em dash, zero means a measured zero, and blank means inapplicable (STD-UI-4). Dates are ISO-8601, with session dates left unconverted (STD-UI-5).

## EPIC Acceptance Criteria

### From Capability

- [AC-7] The owner-operator MUST be able to see, for each named instrument, which data types are present, the date range covered, and when that instrument was last acquired.
- [AC-8] The product MUST identify missing trading days within a date range it has acquired for an instrument.
- [AC-12] A run that fails partway MUST NOT leave data that presents as complete coverage for a range it did not fully acquire.
- [AC-17] Before any acquisition has run, the ingestion view MUST state that no data has been acquired rather than presenting an empty successful state.
- [AC-21] The owner-operator MUST be able to see coverage retained for a retired instrument and distinguish it from instruments still being acquired.
- [AC-22] An instrument whose coverage falls short of the stated history depth MUST be identifiable as such.

### Derived

- [DAC-E6-1] Coverage MUST be derived at read time from coverage segments and observation rows, and MUST NOT be stored as an asserted summary. (traces to: AC-12, AC-7)
- [DAC-E6-2] The trading-day set MUST be formed as the union of dates on which any named instrument has a daily bar in the requested range. (traces to: AC-8)
- [DAC-E6-3] A missing date MUST be reported as a gap only when it falls inside that instrument's own covered range, since a date before the instrument was first acquired is outside coverage rather than a gap. (traces to: AC-8)
- [DAC-E6-4] Gap detection MUST be reported as unavailable, with a reason, when fewer than two named instruments hold data in the range, rather than returning an empty gap list. (traces to: AC-8)
- [DAC-E6-5] Gap detection MUST apply to daily prices only. (traces to: AC-8)
- [DAC-E6-6] The product MUST NOT claim to detect a market-wide provider outage, since every instrument is missing that day and the derived set cannot represent it. (traces to: AC-8)
- [DAC-E6-7] Never-acquired MUST be computed as the absence of any observation row in the store, not as an empty result for the current filter, and the two MUST render distinct copy. (traces to: AC-17)
- [DAC-E6-8] Retired instruments MUST appear in coverage reads with their retained coverage, marked distinctly from active instruments rather than omitted. (traces to: AC-21)
- [DAC-E6-9] An instrument covered to a shallower depth than the current stated depth MUST be presented as short by a stated amount. (traces to: AC-22)
- [DAC-E6-10] Coverage reads MUST support symbol filter, lifecycle filter, date bounds and cursor paging at 3000 instruments. (traces to: AC-7, AC-4)
- [DAC-E6-11] Each instrument row MUST report per-data-type presence as present, absent or unknown. (traces to: AC-7, AC-3)
- [DAC-E6-12] A uniform shortfall across every instrument caused by the provider plan's history cap MUST NOT be presented as a provider data gap. (traces to: AC-12, AC-17)
- [DAC-E6-13] The Coverage screen MUST NOT auto-poll and MUST show a last-updated time. (traces to: AC-7)
- [DAC-E6-14] Specific missing dates MUST be available behind expansion rather than in the collapsed row. (traces to: AC-8)

## Open Questions

- **Density tier is unselected (OQ-UI-4).** Every table consumes the inherited row-height default, which ux-design section 0 records as a port-time placeholder. STD-UI-29 permits selecting a tier from the defined set but not introducing a value, and this design deliberately inherits rather than choosing. Affects the Coverage table's presentation at 3000 rows.
- **`data-table` offers pagination rather than virtualisation**, which STD-UI-30 requires at AC-4's volume, so the component does not discharge that rule alone. Recorded in capability section 5.4.
