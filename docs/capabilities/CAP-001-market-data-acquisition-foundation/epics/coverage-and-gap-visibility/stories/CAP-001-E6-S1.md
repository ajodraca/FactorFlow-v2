# Coverage Derivation From Written Rows

## User Story

As an owner-operator, I want coverage reported only from rows that actually exist, so that a run which died partway can never show me complete coverage it did not acquire.

## Description

Delivers `src/factorflow/coverage/service.py` and the coverage half of `src/factorflow/coverage/sql/`.

Module: `coverage-service`. Coverage is derived at read time and never stored as an asserted summary. This is what makes AC-12 hold: no component may record intended coverage ahead of the write that justifies it.

Source: `component-design-coverage-service.md` sections 2.2, 2.4, 2.5.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-7] Given each named instrument, When coverage is read, Then it reports which data types are present, the date range covered, and when it was last acquired.
- [AC-12] Given a run that failed partway, When coverage is read, Then no range presents as complete that was not fully acquired.
- [AC-17] Given nothing acquired yet, When coverage is read, Then never-acquired is reported rather than an empty successful state.
- [AC-21] Given a retired instrument, When coverage is read, Then its retained coverage appears, marked distinctly from active instruments.
- [DAC-E6-1] Given coverage, When it is produced, Then it is derived at read time from coverage segments and observation rows.
- [DAC-E6-7] Given never-acquired, When it is computed, Then it means no observation row exists at all, not an empty result for the current filter.

### Derived

- [DAC-E6-S1-1] Given an instrument, When its per-data-type presence is reported, Then each of the four types is present, absent or unknown. (traces to: DAC-E6-11)
- [DAC-E6-S1-2] Given `never_acquired`, When it is computed, Then it uses its own query over observation existence, separate from the filtered coverage query, because conflating them produces AC-17's exact failure. (traces to: DAC-E6-7)
- [DAC-E6-S1-3] Given an instrument covered to a shallower depth than the current stated depth, When coverage is read, Then it reports how far short it falls. (traces to: DAC-E6-9)
- [DAC-E6-S1-4] Given a retired instrument, When coverage is read, Then it is included with a lifecycle marker rather than omitted. (traces to: DAC-E6-8)
- [DAC-E6-S1-5] Given last-acquired, When it is reported, Then it comes from `acquisition_state` stamped inside the write transaction, not from a run's intent. (traces to: DAC-E6-1)
- [DAC-E6-S1-6] Given a uniform shortfall across every instrument caused by the plan's history cap, When coverage renders, Then it is not presented as a provider data gap. (traces to: DAC-E6-12)
- [DAC-E6-S1-7] Given coverage reads, When they are issued, Then they support a symbol filter, lifecycle filter, date bounds and cursor paging at 3000 instruments. (traces to: DAC-E6-10)

## Technical Details

### Implementation

- SQL statements as `.sql` files under `src/factorflow/coverage/sql/`, loaded at import, executed with `psycopg` 3 and bound parameters. No ORM.
- Reads `coverage_segment`, the observation tables and `acquisition_state`.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- An instrument with prices but no fundamentals reports present and absent respectively.
- A store with zero observations reports `never_acquired` true; a filter matching nothing on a populated store reports it false.
- A retired instrument appears with its coverage and a lifecycle marker.
- An instrument covered to three years against a stated five reports the shortfall.
- A rolled-back partial write leaves no coverage, asserted by writing then failing and reading back.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E4-S1**, **CAP-001-E4-S3**, the observation tables and the coverage segments the writer commits.
- **CAP-001-E5-S1**, `acquisition_state`.
