# Gap Detection Against the Derived Trading-Day Set

## User Story

As an owner-operator, I want missing trading days flagged inside ranges I have acquired, so that I can tell complete coverage from coverage with holes in it.

## Description

Delivers `src/factorflow/coverage/gaps.py` and `src/factorflow/coverage/sql/gaps.sql`.

Module: `coverage-service`. The provider supplies no historical trading calendar: its market-holidays endpoint is forward-looking only, verified 2026-09-03, and no plan tier changes that. So a date counts as a trading day when **any** named instrument has a daily bar for it, and a gap is a date in that set falling inside an instrument's covered range for which that instrument has no bar.

Three properties of the statement are load-bearing, and two consequences must be honoured rather than hidden.

Source: `component-design-coverage-service.md` section 2.3; system design 5.5.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-8] Given a range acquired for an instrument, When gaps are computed, Then missing trading days within it are identified.
- [DAC-E6-2] Given the trading-day set, When it is formed, Then it is the union of dates on which any named instrument has a daily bar in the range.
- [DAC-E6-3] Given a missing date, When it is classified, Then it is a gap only if it falls inside that instrument's own covered range.
- [DAC-E6-4] Given fewer than two instruments holding data in the range, When gaps are computed, Then detection is reported unavailable with a reason, not as an empty gap list.
- [DAC-E6-5] Given gap detection, When it runs, Then it applies to daily prices only.
- [DAC-E6-6] Given a market-wide provider outage, When gaps are computed, Then the product does not claim to detect it.

### Derived

- [DAC-E6-S2-1] Given an instrument checked against its own dates alone, When the set is built, Then this is explicitly avoided, because it would report zero gaps for every instrument always. (traces to: DAC-E6-2)
- [DAC-E6-S2-2] Given a date before an instrument was first acquired, When it is evaluated, Then it is outside coverage rather than a gap. (traces to: DAC-E6-3)
- [DAC-E6-S2-3] Given the availability predicate, When it is applied, Then it is evaluated inside the statement so an unavailable check returns no rows rather than a zero count. (traces to: DAC-E6-4)
- [DAC-E6-S2-4] Given fundamentals or corporate actions, When gaps are considered, Then none are computed, since quarterly and sporadic data carry no per-day expectation. (traces to: DAC-E6-5)
- [DAC-E6-S2-5] Given a day on which every instrument is missing a bar, When gaps are computed, Then no gap is reported for anyone, which is the market-wide outage limitation stated plainly rather than hidden. (traces to: DAC-E6-6)
- [DAC-E6-S2-6] Given gap results, When they are returned, Then a count is available for the collapsed row and specific dates for expansion. (traces to: DAC-E6-14)

## Technical Details

### Statement

Per `component-design-coverage-service.md` section 2.3: a CTE forming `in_range` bars, an `availability` predicate requiring at least two distinct instruments, a `trading_day` set of distinct session dates, and `covered` segments restricted to `data_type = 'prices'`, joined to find dates inside an instrument's covered range with no bar for it.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Two instruments, one missing a day the other has, inside both covered ranges: one gap reported.
- A date before an instrument's coverage start: not a gap.
- One instrument only: detection reported unavailable, asserted **not** as zero gaps.
- Zero instruments with data: unavailable.
- A day missing for every instrument: no gap reported for anyone.
- Fundamentals coverage with holes: no gaps computed.
