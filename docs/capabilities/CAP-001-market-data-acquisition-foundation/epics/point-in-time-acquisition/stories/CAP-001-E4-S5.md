# Acquisition Run Loop

## User Story

As an owner-operator, I want a claimed run to work through my instruments one at a time, so that one instrument's failure never stops the rest and I can stop the run between instruments.

## Description

Delivers `src/factorflow/ingestion/runner.py` and the container entrypoint `src/factorflow/ingestion_main.py`.

Module: `acquisition-runner`. The largest story in the capability. It claims a run, reads its roster once, and drives instruments one at a time, each in its own transaction through the writer.

The run's roster is read **once, at claim time**, so the run's scope is fixed when it starts. Re-reading before each instrument was rejected: a run that changes shape underneath itself cannot be explained from its own record, since run detail would list instruments the roster no longer contains with no way to say why.

Source: `component-design-acquisition-runner.md` sections 2.2, 2.5.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-3] Given a claimed run, When it executes, Then it acquires all four data types for each active instrument over the run's stated depth.
- [AC-4] Given up to 3000 instruments, When a run executes, Then it completes without manual intervention.
- [AC-11] Given an instrument the provider does not recognise, When it is reached, Then it is recorded and the run continues.
- [DAC-E4-12] Given a claimed run, When it starts, Then it reads the active roster once, at claim time.
- [DAC-E4-13] Given a run with no stated history depth, When it is claimed, Then it acquires nothing and is finalised failed.
- [DAC-E4-14] Given each instrument, When it is processed, Then it commits in its own transaction so the run is resumable.

### Derived

- [DAC-E4-S5-1] Given the instrument loop, When each iteration begins, Then it checks for a cancellation request and refreshes the claim heartbeat at the same point. (traces to: AC-19, DAC-E5-10)
- [DAC-E4-S5-2] Given a cancellation observed between instruments, When it is seen, Then the loop exits without starting the next instrument and the run finalises cancelled. (traces to: AC-19)
- [DAC-E4-S5-3] Given a runner whose claim has been reclaimed by the sweep, When it notices, Then it stops without writing further results against that run. (traces to: DAC-E5-13)
- [DAC-E4-S5-4] Given an instrument raising any provider error, When it is caught, Then it is recorded against that instrument and the loop continues to the next. (traces to: AC-11)
- [DAC-E4-S5-5] Given the run finishes its roster, When it finalises, Then the outcome is computed from what was written rather than from what was requested. (traces to: AC-9, DAC-E5-4)
- [DAC-E4-S5-6] Given no run is available to claim, When the runner polls, Then it waits and polls again at the configured interval rather than exiting. (traces to: AC-23)
- [DAC-E4-S5-7] Given the credential has changed since the last run, When a run is claimed, Then the provider client is rebuilt before the first fetch. (traces to: DAC-E1-10)
- [DAC-E4-S5-8] Given a run of 3000 instruments, When it executes, Then no manual step is required and progress is observable through the journal between instruments. (traces to: AC-4)

## Technical Details

### Loop Shape

1. Poll the journal for a claimable run (CAP-001-E5-S2 owns the claim statement).
2. On claim: read the active roster once; read `history_depth_years` from the run row; rebuild the provider client if the credential changed.
3. For each instrument: check cancellation and refresh heartbeat, plan ranges (CAP-001-E4-S4), fetch the four data types (CAP-001-E3-S1), write in one transaction (CAP-001-E4-S3), classify the outcome (CAP-001-E4-S6).
4. Finalise the run from written coverage.

Runs in the **ingestion container**, which shares only the database with the application. There is no in-process call between the two.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`; the provider client substituted at its boundary.
- A run over several instruments where one raises `InstrumentNotFound` completes and records the rest.
- A cancellation requested mid-loop stops before the next instrument and retains committed coverage.
- A reclaimed run stops writing.
- A run with no depth set acquires nothing and finalises failed.
- Killing the process mid-run leaves committed instruments intact; a later run completes the remainder without re-fetching them. This is the story's failure-scenario test.
- A scale test at a reduced instrument count asserting no per-instrument state accumulates in memory.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.
