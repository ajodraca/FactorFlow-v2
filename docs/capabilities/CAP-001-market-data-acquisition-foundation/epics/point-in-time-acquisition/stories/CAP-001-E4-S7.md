# Volume and Resumability at 3000 Instruments

## User Story

As an owner-operator, I want a run covering my whole instrument list to finish without me watching it, and to survive an interruption, so that a large acquisition is something I can start and walk away from.

## Description

Hardens the run loop for AC-4's stated volume and proves resumability. Separate from CAP-001-E4-S5 because it is verification and hardening work against an already-working loop, with its own failure scenarios.

Module: `acquisition-runner`. No duration target is fixed: AC-4 constrains completeness but not time, which the capability records as an open question. This story therefore asserts completion and resumability, not elapsed time.

Rate limiting is not the constraint it once looked like. Verified 2026-09-05, the target plan has no rate limit, so 3000 instruments are not throughput-bound.

Source: `component-design-acquisition-runner.md` section 5; capability section 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-4] Given up to 3000 named instruments, When a run executes, Then it completes without manual intervention.
- [AC-20] Given a run whose process stops unexpectedly, When a later run starts, Then the interrupted run does not prevent it.
- [DAC-E4-14] Given each instrument, When it commits in its own transaction, Then an interruption loses at most one instrument's work.

### Derived

- [DAC-E4-S7-1] Given a run of 3000 instruments, When it executes, Then memory use stays bounded, with no accumulation of per-instrument results in process memory. (traces to: AC-4)
- [DAC-E4-S7-2] Given the ingestion process is killed mid-run, When a later run starts, Then instruments already committed are not re-fetched and the remainder completes. (traces to: AC-20, AC-6)
- [DAC-E4-S7-3] Given database connections, When a long run executes, Then connections are not leaked across instruments. (traces to: AC-4)
- [DAC-E4-S7-4] Given a run interrupted after some instruments, When coverage is read, Then it reports exactly the committed instruments, with no partial range for the one in flight. (traces to: AC-12)
- [DAC-E4-S7-5] Given no duration target exists, When this story is verified, Then completion and resumability are asserted and elapsed time is recorded for information rather than asserted as a threshold. (traces to: AC-4)

## Technical Details

### Approach

- A volume test at a reduced but representative instrument count with a substituted provider, asserting completion, bounded memory and no connection growth. The full 3000 is exercised against the live provider only as a manual pre-release check, since it depends on a real subscription.
- A kill-and-resume test: start a run, terminate the process after N instruments, start another run, assert the first N are not re-fetched and the remainder completes.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres` and `slow`.
- Memory sampled across the run; growth bounded.
- Connection count sampled; no growth per instrument.
- Kill-and-resume asserts no re-fetch of committed instruments, using the writer's zero-rows-appended signal as the evidence.
- Elapsed time logged, not asserted.

### Open Question

No acceptable duration for a first 3000-instrument run is defined. Recorded in capability section 7 and in this EPIC. Until it is answered, this story cannot assert a time bound, and a run taking many hours satisfies AC-4 as written.

### Validation

`uv run pytest -m 'postgres and slow'`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E4-S5**, the loop this story hardens.
- **CAP-001-E5-S4**, the reclaim sweep that makes an interrupted run terminal.
