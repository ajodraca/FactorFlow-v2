# Observation Schema: Append-Only Point-in-Time Tables

## User Story

As an owner-operator, I want every acquired value stored with the date it was known and never overwritten, so that a later restatement adds a record rather than destroying the one I had.

## Description

Delivers migration `0002_observations.sql`: `instrument_reference`, `daily_bar`, `fundamental_observation` and `corporate_action`.

Module: `market-data-store`. This is the schema half of the capability's most consequential constraint. C5 cannot be repaired retrospectively: fundamentals are restated and delisted instruments disappear, so anything overwritten now is lost permanently.

Each table carries a natural-key uniqueness constraint **including a hash of the value**, which is what makes re-running safe. An identical value conflicts and writes nothing; a restated value hashes differently and appends a new row.

The owner considered and **rejected** enforcing append-only through database role grants: the deny would have to be table-scoped across six rules, role passwords cannot live in a numbered migration without committing a secret, and the grant does not reach a data-fix migration or the owner acting as superuser. The reasoning is recorded in the component design section 2.5.

Source: `component-design-market-data-store.md` sections 2.3, 2.5.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-5] Given an acquired value, When it is stored, Then it carries the date FactorFlow observed it, and a restated value for a date already held adds a row rather than replacing one.
- [AC-6] Given a period already acquired, When it is acquired again, Then no row is duplicated, overwritten or removed.
- [DAC-E1-6] Given the observation tables, When they are defined, Then each carries a natural-key uniqueness constraint including a value hash.
- [DAC-E4-2] Given an append, When it executes, Then it uses insert-on-conflict-do-nothing against that natural key, so an identical value writes nothing and a restated value writes a new row.
- [DAC-E4-1] Given a fundamental record, When it is stored, Then the provider's filing date may be a descriptive attribute but never the as-of date.

### Derived

- [DAC-E4-S1-1] Given any observation row, When it is written, Then `observed_on` is FactorFlow's own observation date, defaulting to the current date, and is never taken from a provider field. (traces to: DAC-E4-1)
- [DAC-E4-S1-2] Given an identical value re-fetched, When it is inserted with `ON CONFLICT DO NOTHING`, Then zero rows are affected and the existing row is untouched. (traces to: AC-6)
- [DAC-E4-S1-3] Given a restated value for a date already held, When it is inserted, Then the differing value hash makes it a new row and both records coexist. (traces to: AC-5)
- [DAC-E4-S1-4] Given the value hash column, When it is defined, Then it is a 32-byte digest with a length check constraint, matching SHA-256 output. (traces to: DAC-E1-6)
- [DAC-E4-S1-5] Given `daily_bar`, When it is defined, Then price and volume columns use exact numeric types rather than floating point, so no binary rounding enters recorded history. (traces to: AC-5)
- [DAC-E4-S1-6] Given every observation table, When migration `0002` is reviewed, Then it contains no `UPDATE` or `DELETE` statement against observation history, and no later migration may introduce one. (traces to: AC-5)
- [DAC-E4-S1-7] Given a query path over observations, When it is written anywhere in the codebase, Then it performs no `UPDATE` or `DELETE` against these tables. (traces to: AC-5)

## Technical Details

### Data Changes

`migrations/0002_observations.sql` creates the four observation tables per `component-design-market-data-store.md` section 2.3. Each carries:

- `instrument_id` referencing `instrument`
- the natural key for its data type, such as `session_date` for `daily_bar`
- `observed_on date NOT NULL DEFAULT current_date`
- `value_hash bytea NOT NULL` with `CHECK (octet_length(value_hash) = 32)`
- a unique constraint over the natural key plus `observed_on` plus `value_hash`

`fundamental_observation` additionally holds the provider's `filing_date` as a descriptive attribute, documented in a column comment as never serving as the as-of date.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- Inserting the same value twice affects one row then zero.
- Inserting a differing value for the same date and instrument yields two coexisting rows.
- A 31-byte or 33-byte hash is rejected by the check constraint.
- A static test greps the migrations directory and the source tree for `UPDATE` or `DELETE` against the four observation tables and fails if any is found. This is the cheapest available guard for a constraint the owner deliberately chose not to enforce with grants.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.
