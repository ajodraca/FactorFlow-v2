# Observation Writer: One Transaction Per Instrument

## User Story

As an owner-operator, I want each instrument's data committed all at once or not at all, so that a run that dies partway can never leave coverage claiming a range it did not fully acquire.

## Description

Delivers `src/factorflow/ingestion/writer.py` and `src/factorflow/ingestion/coverage.py`.

Module: `observation-writer`. The component's whole contract is the boundary of one transaction: all four data types for one instrument are appended, the coverage segment is merged, acquisition state is stamped and per-instrument results are recorded, and then one commit makes all of it visible at once.

Nothing partial is ever observable. A failure at any step rolls back the whole instrument, which is what lets `coverage-service` read coverage as **evidence** rather than as intent.

Source: `component-design-observation-writer.md` sections 2.2, 2.4.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-12] Given a run that fails partway, When it stops, Then no data presents as complete coverage for a range it did not fully acquire.
- [AC-5] Given an acquired value, When it is appended, Then it carries FactorFlow's observation date.
- [AC-6] Given a re-run over an acquired period, When it writes, Then nothing is duplicated, overwritten or removed.
- [DAC-E4-4] Given one instrument's write, When any step fails, Then the whole instrument rolls back.
- [DAC-E4-5] Given a coverage segment, When it is extended, Then the extension happens inside the transaction that wrote the rows justifying it.

### Derived

- [DAC-E4-S3-1] Given the write call, When it succeeds, Then it reports rows appended per data type and whether anything changed, so the runner can classify the outcome as written or unchanged. (traces to: DAC-E4-10)
- [DAC-E4-S3-2] Given existing coverage segments for an instrument and data type, When a newly written range abuts or overlaps them, Then they are merged into the minimal set of non-overlapping segments. (traces to: DAC-E4-5)
- [DAC-E4-S3-3] Given the `coverage_no_overlap` exclusion constraint, When a merge is attempted that would overlap, Then the constraint rejects it, so the invariant is enforced by the database and not only by the merge arithmetic. (traces to: DAC-E4-5)
- [DAC-E4-S3-4] Given a write that raises partway, When the transaction rolls back, Then neither observations nor a coverage segment exist for the attempted range, leaving the instrument as though never attempted. (traces to: AC-12)
- [DAC-E4-S3-5] Given acquisition state, When a write commits, Then `last_acquired_at`, `last_run_id` and `last_outcome` are stamped in the same transaction. (traces to: AC-7)
- [DAC-E4-S3-6] Given per-instrument results, When a write commits, Then one row per data type is recorded in the same transaction. (traces to: AC-10)
- [DAC-E4-S3-7] Given inserts, When they execute, Then they use `INSERT ... ON CONFLICT DO NOTHING` and never `UPDATE` or `DELETE` against observation history. (traces to: AC-5)

## Technical Details

### Write Sequence

One transaction per instrument:

1. `BEGIN`
2. For each observation: canonical hash, then `INSERT ... ON CONFLICT DO NOTHING`
3. Read existing `coverage_segment` rows for this instrument and data type
4. Merge the written range into them; delete and reinsert the merged set, or extend in place
5. `UPSERT acquisition_state` (`last_acquired_at`, `last_run_id`, `last_outcome`)
6. `INSERT run_instrument_result` per data type
7. `COMMIT`, or `ROLLBACK` and raise on any failure

Signature: `write_instrument(instrument_id, run_id, observations, range_written)`.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- A successful write commits observations, one merged coverage segment, acquisition state and per-data-type results together.
- A failure injected at step 5 leaves no observation and no coverage segment for the attempted range.
- Re-writing an identical payload reports zero rows appended and leaves coverage unchanged.
- Adjacent and overlapping ranges merge into one segment; a deliberate overlapping insert is rejected by the exclusion constraint.
- A restated value appends a second row and coverage is unchanged.
