# Per-Instrument Outcome Classification

## User Story

As an owner-operator, I want each instrument's result recorded per data type, so that I can tell an instrument the provider does not cover from one that genuinely failed.

## Description

Delivers `src/factorflow/ingestion/outcomes.py`.

Module: `acquisition-runner`. Classification is separate from the loop because it is the input to the run's honest outcome, and getting it wrong makes AC-9 unsatisfiable.

`not_found` is recorded per data type as well as per instrument, because Massive may recognise an instrument for prices and hold no fundamentals for it. The UX design's run detail expands an instrument to four data types precisely to show this.

Rate limiting never appears in this classification. A `429` means the request was never served, so the governor waits it out and it is not an attempt.

Source: `component-design-acquisition-runner.md` section 2.4.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Given a failed or partial run, When results are recorded, Then which instrument and which data type was affected is recorded with a reason.
- [AC-11] Given an unrecognised instrument, When it is classified, Then it is `not_found` and distinguishable from other failures.
- [DAC-E4-10] Given each instrument, When it is classified, Then the outcome is written, unchanged, not-found or failed, recorded per data type as well as per instrument.
- [DAC-E4-11] Given an instrument not reached because the run was cancelled, When the run ends, Then no row is written for it.
- [DAC-E4-15] Given a recorded failure reason, When it is stored, Then it contains no provider credential.

### Derived

- [DAC-E4-S6-1] Given data returned and rows appended, When it is classified, Then the outcome is `written` and counts toward `succeeded`. (traces to: DAC-E4-10)
- [DAC-E4-S6-2] Given data returned whose values are all already held, When it is classified, Then the outcome is `unchanged` and counts toward `succeeded`, because nothing was wrong. (traces to: AC-6)
- [DAC-E4-S6-3] Given an instrument unknown to the provider, When it is classified, Then the outcome is `not_found`, the run continues, and the run's outcome becomes `partial`. (traces to: AC-11)
- [DAC-E4-S6-4] Given attempts exhausted by transport or server errors, When it is classified, Then the outcome is `failed`, the run continues, and the run's outcome becomes `partial`. (traces to: AC-11)
- [DAC-E4-S6-5] Given a `429`, When outcomes are classified, Then it never appears as an outcome, since it is flow control rather than a result. (traces to: DAC-E3-6)
- [DAC-E4-S6-6] Given an instrument recognised for prices but not for fundamentals, When it is classified, Then prices record `written` and fundamentals record `not_found` for the same instrument. (traces to: DAC-E4-10)
- [DAC-E4-S6-7] Given a recorded reason, When it is stored, Then it carries the provider request id and no credential. (traces to: DAC-E3-13)

## Technical Details

### Classification Table

| Provider result | Recorded outcome | Run effect |
|---|---|---|
| Data returned, rows appended | `written` | counts toward `succeeded` |
| Data returned, every value already held | `unchanged` | counts toward `succeeded` |
| Instrument unknown to the provider | `not_found` | run continues, outcome becomes `partial` |
| Transport or server error, attempts exhausted | `failed` | run continues, outcome becomes `partial` |
| Not reached because the run was cancelled | no row written | no coverage, no failure |

Rows are written to `run_instrument_result` inside the writer's transaction.

### Testing

- `pytest`, marked `not postgres` for the pure classification, `postgres` for the persisted rows.
- Each row of the table is exercised.
- A per-data-type mix on one instrument records different outcomes for prices and fundamentals.
- A cancelled-before-reached instrument produces no row at all, asserted by count.
- A `429` in the input stream produces no outcome row.
