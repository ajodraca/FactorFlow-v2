# Point-in-Time Acquisition and Re-run Safety

**EPIC ID:** CAP-001-E4
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Drive an acquisition run instrument by instrument and append what it returns as point-in-time history that can be trusted. This EPIC carries the three commitments the system design names as unrecoverable if wrong: observations are appended with the date FactorFlow observed them and never the provider's filing date; every write is idempotent on the value itself, so a re-run adds nothing when the provider returns what is already held but does add a row when it returns something different; and coverage is extended only inside the committed write transaction, so a run that dies partway cannot leave history that looks complete.
**Actors:** Owner-operator (starting a run), acquisition-runner, observation-writer, massive-client, market-data-store
**Estimate:** XL
**Out of Scope:** Run state transitions, queueing, cancellation and reclaim (E5); deriving or presenting coverage and gaps (E6); presenting per-instrument failure detail (E7); the provider client itself (E3)
**Dependencies:** E1 (schema), E2 (instrument list and stated depth), E3 (provider client and pacing). No cross-capability blockers; Massive is `requires-runtime` and binds at integration.
**Links:** system-design.md sections 3 (steps 7-17, 22-28), 5.3, 5.4, 5.9, 5.19; component-design-acquisition-runner.md sections 2.2, 2.3, 2.4; component-design-observation-writer.md sections 2.2, 2.3; component-design-market-data-store.md sections 2.3, 2.4, 2.5

## Goals

- Acquire all four data types for every active instrument over the run's stated depth.
- Record every value point-in-time, so that a later restatement adds a record rather than replacing one.
- Make re-running safe, so the owner can recover from a failure by simply running again.
- Fetch only what is missing, so deepening the stated depth backfills the earlier range without re-acquiring what is covered.
- Isolate each instrument, so one failure neither stops the run nor leaves a partial write behind.
- Complete a run of 3000 instruments without manual intervention.

## Non-Functional Requirements

- **Volume:** A run of 3000 instruments completes without manual intervention (AC-4). Each instrument is processed in its own transaction, so a run is resumable and a long run is not lost to an interruption.
- **Data integrity:** Append-only. No `UPDATE` or `DELETE` against observation history on any path (C5, system design 5.3). This is the constraint that cannot be repaired retrospectively.
- **Atomicity:** All four data types for one instrument, its coverage segment merge, its acquisition-state stamp and its per-instrument results commit together or roll back together. Nothing partial is ever observable.
- **Idempotence:** Value hashing is deterministic: canonical JSON with sorted keys, no whitespace and decimals as strings, hashed with SHA-256.
- **Duration:** No duration target is fixed for a 3000-instrument run. AC-4 constrains completeness but not time (capability section 7, open question).

## EPIC Acceptance Criteria

### From Capability

- [AC-3] A successful acquisition run MUST provide, for each named instrument the provider covers, instrument reference data, daily prices, company fundamentals and corporate actions over the stated history depth.
- [AC-4] The product MUST complete an acquisition run covering up to 3000 named instruments without manual intervention.
- [AC-5] Every acquired value MUST be recorded with the date on which it was known, and a run returning a restated value for a date already held MUST add a record rather than replace the existing one.
- [AC-6] Re-running acquisition over a period already acquired MUST NOT duplicate, overwrite or remove previously recorded data.
- [AC-12] A run that fails partway MUST NOT leave data that presents as complete coverage for a range it did not fully acquire.
- [AC-22] When the owner-operator increases the stated history depth, the next acquisition run MUST acquire the missing earlier range for every active named instrument that falls short of the new depth, without re-acquiring the range already covered.

### Derived

- [DAC-E4-1] Observations MUST be appended with the date FactorFlow observed them. The provider's filing date MAY be stored as a descriptive attribute but MUST NEVER serve as the as-of date, because it conflates restatements of the same period. (traces to: AC-5)
- [DAC-E4-2] Appending MUST use insert-on-conflict-do-nothing against a natural key that includes a hash of the value, so an identical value writes nothing and a restated value writes a new row. (traces to: AC-5, AC-6)
- [DAC-E4-3] Value hashing MUST be deterministic across processes: canonical JSON with sorted keys, no whitespace and decimals rendered as strings, hashed with SHA-256. (traces to: AC-6)
- [DAC-E4-4] All four data types for one instrument, the coverage segment merge, the acquisition-state stamp and the per-instrument results MUST commit in a single transaction, and any failure MUST roll back the whole instrument. (traces to: AC-12)
- [DAC-E4-5] A coverage segment MUST be extended only inside the transaction that wrote the rows justifying it. No component may record intended coverage ahead of the write. (traces to: AC-12)
- [DAC-E4-6] The runner MUST compute, per instrument and data type, only the sub-ranges of the requested depth not already covered. (traces to: AC-22, AC-6)
- [DAC-E4-7] An instrument covered from a later date than the depth start MUST yield the earlier gap for fetching, which is the deepening backfill. (traces to: AC-22)
- [DAC-E4-8] The depth start MUST be computed from the depth snapshotted onto the run row at request time, not from the current setting, so a depth changed mid-queue does not redefine a run already requested. (traces to: AC-22, AC-2)
- [DAC-E4-9] The trailing range since the last covered day MUST be re-fetched on every run, because the last covered day may have been a partial session, and idempotence makes re-fetching a day already held write nothing. (traces to: AC-6)
- [DAC-E4-10] Each instrument's per-data-type outcome MUST be classified as written, unchanged, not-found or failed, with not-found recorded per data type as well as per instrument, since the provider may recognise an instrument for prices and hold no fundamentals for it. (traces to: AC-3, AC-11)
- [DAC-E4-11] An instrument not reached because the run was cancelled MUST write no row, leaving neither coverage nor a failure record. (traces to: AC-19, AC-12)
- [DAC-E4-12] The run's instrument roster MUST be read once, at claim time, so that the run's scope is fixed when it starts. (traces to: AC-25)
- [DAC-E4-13] A run whose stated history depth is unset MUST acquire nothing and MUST be finalised as failed. (traces to: AC-2)
- [DAC-E4-14] Each instrument MUST be processed in its own transaction so that a run is resumable and an interruption loses at most one instrument's work. (traces to: AC-4, AC-12)
- [DAC-E4-15] No recorded failure reason MUST contain the provider credential. (traces to: AC-13)

## Open Questions

- **No duration target is fixed for a first acquisition run of 3000 instruments.** AC-4 constrains completeness but not time, so a run taking many hours satisfies it. Recorded in capability section 7. Worth settling before the owner's first full run, since the answer bears on whether progress reporting and resumability are sufficient.
- **Massive's instrument coverage remains untested** (shared with E3). A shortfall changes AC-3. The per-data-type not-found classification already handles it without failing the run.
