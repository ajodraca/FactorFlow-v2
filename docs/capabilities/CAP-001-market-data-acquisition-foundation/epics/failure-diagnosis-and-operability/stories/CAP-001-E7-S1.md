# Per-Instrument Result Queries

## User Story

As an owner-operator diagnosing a failure, I want to see which instrument and which data type failed and why, so that I can fix the cause rather than guess at it.

## Description

Delivers `src/factorflow/runs/queries.py`, the run history and run detail reads.

Module: `run-journal`. Results are recorded per data type as well as per instrument, because the provider may recognise an instrument for prices and hold no fundamentals for it.

Source: `component-design-run-journal.md` section 2.2; `component-design-ingestion-api.md` section 11.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Given a failed or partial run, When its detail is read, Then which instrument and which data type was affected and the reason are available.
- [AC-11] Given an unrecognised instrument, When results are read, Then `not_found` is distinguishable from other failures.
- [DAC-E7-1] Given results, When they are recorded, Then they are per data type as well as per instrument.
- [DAC-E7-3] Given a failure reason, When it is read, Then it names the symbol, the data type and the provider request id.
- [DAC-E7-10] Given run detail, When it is queried, Then it supports an outcome filter and cursor paging.

### Derived

- [DAC-E7-S1-1] Given a run of 3000 instruments, When detail is read, Then results page rather than returning in one response. (traces to: DAC-E7-10)
- [DAC-E7-S1-2] Given run detail, When it is read, Then per-outcome counts are available without paging through every row. (traces to: AC-10)
- [DAC-E7-S1-3] Given an instrument with mixed per-data-type outcomes, When it is read, Then all four data types are returned together for that instrument. (traces to: DAC-E7-1)
- [DAC-E7-S1-4] Given run history, When it is read, Then runs return reverse-chronologically with a state filter and cursor paging. (traces to: AC-9)
- [DAC-E7-S1-5] Given a stored reason, When it is returned, Then it contains no credential, asserted by test. (traces to: DAC-E7-4)

## Technical Details

### Implementation

- `psycopg` 3, bound parameters, statements alongside the other run-journal SQL.
- Run history: reverse-chronological by `requested_at`, filterable by state, cursor-paged.
- Run detail: the run row, per-outcome counts computed in SQL, and per-instrument per-data-type rows filterable by outcome and cursor-paged.

### Testing

- `pytest` with `testcontainers[postgres]`, marked `postgres`.
- A run with mixed outcomes returns correct per-outcome counts without paging.
- An instrument with `written` prices and `not_found` fundamentals returns both rows.
- Paging over many results is stable across requests.
- A reason containing a credential-like value is asserted absent from query output.

### Validation

`uv run pytest -m postgres`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E5-S1**, `acquisition_run` and `run_instrument_result`.
- **CAP-001-E4-S6**, the outcomes these queries read.
