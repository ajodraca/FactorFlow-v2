# Shared Error Envelope and Request Correlation

## User Story

As an owner-operator, I want every error to tell me the operation, the resource and the reason, so that the interface can always show me something actionable and I can find the failure in the log.

## Description

Delivers `src/factorflow/api/errors.py` and the request-id middleware in `app.py`.

Module: `ingestion-api`. Every non-2xx response carries the same body, so the interface has one shape to render and STD-UI-19's three parts always have somewhere to come from.

Messages are owner-facing and detailed **because** the interface is loopback-only with a single operator. SEC-ERR-001 requires internal detail not reach external clients; there is no external client here, and the boundary the rule protects is the one the deployment closes. Stack traces and driver messages are still never returned.

Source: `component-design-ingestion-api.md` sections 2.3, 4.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Given any failure the owner sees, When it renders, Then the operation, the resource and the reason are available from the response.
- [DAC-E7-5] Given any non-2xx response, When it is returned, Then it carries one envelope: a stable snake_case code, owner-facing prose, the resource and a request id.
- [DAC-E7-6] Given any request, When it is served, Then a generated request id is included in every log record for that request.
- [DAC-E7-7] Given a `500`, When it is returned, Then only an internal-error code and request id are returned, with detail going to the log.

### Derived

- [DAC-E7-S2-1] Given an error code, When the interface branches on it, Then the code is stable snake_case and does not change with message wording. (traces to: DAC-E7-5)
- [DAC-E7-S2-2] Given an unhandled exception, When it reaches the handler, Then no stack trace or driver message appears in the response body. (traces to: DAC-E7-7)
- [DAC-E7-S2-3] Given a request id, When it appears in a response, Then the same id appears in that request's log records, which is what makes a reported failure findable. (traces to: DAC-E7-6)
- [DAC-E7-S2-4] Given any error response, When it is composed, Then no credential value can appear in it. (traces to: DAC-E7-4)
- [DAC-E7-S2-5] Given a validation failure from Pydantic, When it is returned, Then it is mapped into the shared envelope rather than FastAPI's default shape, so the interface has one shape only. (traces to: DAC-E7-5)

## Technical Details

### Envelope

```json
{
  "error": {
    "code": "history_depth_not_set",
    "message": "History depth is not set. Set it in Settings before acquiring.",
    "resource": "acquisition-run",
    "request_id": "0f2f1c2e-9a44-4f0f-9f1e-2b7b0d0f1a55"
  }
}
```

A `500` returns `{"code": "internal_error", "request_id": ...}` only.

### Implementation

- Exception handlers registered on the application factory, including one overriding FastAPI's default validation error shape.
- Middleware generating a request id per request, bound into the structured logging context.

### Testing

- `pytest` with FastAPI's test client, marked `not postgres`.
- Every handled error type returns the envelope with all four fields.
- A deliberately raised unhandled exception returns `internal_error` with no stack trace in the body.
- A Pydantic validation failure returns the shared envelope, not FastAPI's default.
- The response's request id is asserted present in the captured log records.
- A handler raising with a credential in scope produces a response asserted free of it.

### Validation

`uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run mypy src`.

### Dependencies

- **CAP-001-E1-S6**, the application factory these handlers register on.
