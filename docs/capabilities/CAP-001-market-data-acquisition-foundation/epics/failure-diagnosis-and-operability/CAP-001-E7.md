# Failure Diagnosis and Operational Visibility

**EPIC ID:** CAP-001-E7
**Jira Key:** N/A
**Capability:** CAP-001
**Summary:** Let the owner-operator find out what went wrong, without inspecting the data store. A failed or partial run opens to show which instrument and which data type was affected and the reason reported for each, distinguishing an instrument the provider does not recognise from one that failed for another cause. The most recent run's outcome is fed to the status region E1 delivers, completing the operational picture the owner reads from every screen. Delivers the run detail screen and the error contract the whole interface renders.
**Actors:** Owner-operator, run-journal, ingestion-api, owner-web-app
**Estimate:** M
**Out of Scope:** The application shell, navigation, status region and unreachable state, which E1 delivers; run state transitions and cancellation controls (E5); coverage and gaps (E6); exposing the configured provider request budget, which no endpoint carries and which exceeds this capability
**Dependencies:** E1 (schema, and the application shell and status region this EPIC feeds), E5 (run records and per-instrument results to present).
**Links:** system-design.md sections 3 (steps 36-39), 4.2 (`/api/acquisition-runs/{id}`, `/api/health`), 5.15; component-design-run-journal.md section 2.2; component-design-ingestion-api.md sections 2.3, 11; component-design-owner-web-app.md sections 2.2, 2.3; component-design-schema-migrator.md section 4; ux-design.md sections 0, 1.5, 2

## Goals

- Show, for a failed or partial run, which instrument and which data type was affected and why.
- Distinguish a provider not recognising an instrument from a genuine failure, since the owner's remedy differs.
- Supply the most recent run's outcome to the status region E1 delivers, so the owner reads it from every screen without inspecting the data store.
- Give every error one shape, so the interface always has an operation, a resource and a reason to render.
- Give a migration failure a safe, legible log record, so the unreachable state E1 renders has a diagnosable cause behind it.

## Non-Functional Requirements

- **Observability:** Run detail polls while its run is active. The status region that renders this EPIC's run-outcome content is delivered and paced by E1 (STD-UI-25).
- **Diagnosability:** Each request carries a generated request id, included in every log record for that request, which is what makes a reported failure findable in the container log.
- **Security:** Health reports credential presence as a boolean and never the value. The application process reads only whether the credential is set (AC-13, system design 5.12).
- **Security:** A `500` returns an internal-error code and a request id only, with detail going to the log. Owner-facing messages elsewhere are detailed because the interface is loopback-only with a single operator, which is the boundary SEC-ERR-001 protects.
- **Presentation:** Every error states the operation, the resource and the reason (STD-UI-19), and names its recovery where one exists. Every status carries a text label plus icon or shape, so each screen is readable in greyscale (STD-UI-8).
- **Volume:** Run detail collapses a 3000-instrument run to one row per instrument, expanding to four data types.

## EPIC Acceptance Criteria

### From Capability

- [AC-10] For a failed or partial run, the owner-operator MUST be able to see which instrument and which data type was affected and the reason reported for the failure.
- [AC-11] The run MUST report an instrument the provider does not recognise, distinguishably from other failures.
- [AC-18] The owner-operator MUST be able to determine whether the product is running and whether its most recent acquisition run failed, without inspecting the data store directly.

### Derived

- [DAC-E7-1] Per-instrument results MUST be recorded per data type, so an instrument recognised for prices but holding no fundamentals is reported precisely. (traces to: AC-10)
- [DAC-E7-2] A not-found outcome MUST render distinguishably from a failed outcome, since the owner's remedy differs. (traces to: AC-11, AC-10)
- [DAC-E7-3] Every stored failure reason MUST name the symbol, the data type and the provider's request id. (traces to: AC-10)
- [DAC-E7-4] No stored or rendered failure reason MUST contain the provider credential. (traces to: AC-13, AC-10)
- [DAC-E7-5] Every non-2xx API response MUST carry one envelope shape: a stable snake_case code the interface may branch on, owner-facing prose, the resource, and a request id. (traces to: AC-10)
- [DAC-E7-6] The request id MUST be generated per request and included in every log record for that request. (traces to: AC-10, AC-18)
- [DAC-E7-7] A `500` MUST return an internal-error code and request id only, with stack traces and driver messages going to the log. (traces to: AC-10, AC-13)
- [DAC-E7-8] `GET /api/health` MUST report the most recent run's outcome, completing the payload whose liveness, database, credential-presence and schema-version fields E1 delivers. (traces to: AC-18)
- [DAC-E7-9] Run detail MUST collapse to one row per instrument and expand to four data types, so a 3000-instrument run remains navigable. (traces to: AC-10, AC-4)
- [DAC-E7-10] Run detail MUST support filtering by outcome and cursor paging. (traces to: AC-10)
- [DAC-E7-11] Every status MUST carry a text label plus icon or shape, so the interface is readable in greyscale. (traces to: AC-10, AC-18)
- [DAC-E7-12] Migration failure detail MUST be written to the container log the owner reads and MUST NOT be constructed by formatting a driver exception directly, since a connection error can include the connection string. (traces to: AC-13, AC-16)
