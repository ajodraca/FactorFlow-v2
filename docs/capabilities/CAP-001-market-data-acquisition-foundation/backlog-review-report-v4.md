### BR-2 Alignment with Upstream

**FINDING-1 (HIGH).** `CAP-001-E7-S4` and `CAP-001-E7-S1` cite three epic-derived
criterion IDs that do not exist. E7 defines `DAC-E7-1` through `DAC-E7-12`. The
stories cite:

| Story | Cites | Text it states | Actual epic criterion with that text |
|-------|-------|----------------|--------------------------------------|
| E7-S4 | `DAC-E7-12` | collapses to one row per instrument, expands to four data types | `DAC-E7-9` |
| E7-S1, E7-S4 | `DAC-E7-13` | outcome filter and cursor paging | `DAC-E7-10` |
| E7-S4 | `DAC-E7-14` | every status carries a text label plus icon or shape | `DAC-E7-11` |

`DAC-E7-13` and `DAC-E7-14` exist nowhere in the backlog. `DAC-E7-12` exists but
says something else entirely — migration failure detail must not be built by
formatting a driver exception — so the citation resolves to the wrong criterion
rather than to nothing. The references are shifted by exactly three against the
epic, consistently, which is the signature of the epic's derived list being
renumbered after these stories were written.

The behaviour itself is correctly specified in the stories; nothing is lost from
the delivered scope. This is HIGH because the traceability chain is broken in a
way that silently resolves wrong: `DAC-E7-12` is a live ID, so a planner or test
designer following it lands on migration-failure logging while implementing a run
detail screen. Test design consumes these IDs directly and preserves them
verbatim, so the corruption propagates into the coverage matrix.

**No scope drift.** Every story's stated scope is grounded in its epic and the
component designs. Spot-checked the stories most able to drift: `CAP-001-E4-S5`
(the 8-point run loop) confines itself to `acquisition-runner` and defers claim
semantics to `CAP-001-E5-S2`; `CAP-001-E1-S1` explicitly declines to add a unique
index on `symbol`, deferring it to `CAP-001-E2-S1` which owns reactivation. That
kind of deliberate boundary-marking recurs throughout.

**No cross-layer inconsistency.** API paths, status codes, table and column names,
run states and error type names in the stories match the system design and
component designs everywhere checked. `DAC-E2-4`'s `201`/`409`/`422` and
`DAC-E2-5`'s `404`/`409` appear unchanged in `CAP-001-E2-S3`. The four provider
error types in `CAP-001-E3-S3` match `component-design-massive-client.md` 2.4.

**Derived numbering is correct.** All 219 story-derived criteria use
`DAC-E<n>-S<m>-<k>` as `story-generation` mandates, and every one carries a
`(traces to: ...)` annotation; zero omissions across 36 files.

### BR-6 Consistency and Sequencing

**FINDING-4 (MEDIUM).** `CAP-001-E3-S5` and `CAP-001-E4-S6` declare each other as
dependencies, which is a cycle:

- `CAP-001-E4-S6` `### Dependencies`: "**CAP-001-E3-S3**, **CAP-001-E3-S5**, the
  typed errors and reason text."
- `CAP-001-E3-S5` `### Dependencies`: "**CAP-001-E3-S3**, the typed errors.
  **CAP-001-E4-S6**, consumes these reasons when recording per-instrument results."

The relationship is genuinely one-directional — E3-S5 produces failure-reason
text and E4-S6 consumes it — so E4-S6's declaration is the correct one and
E3-S5's is a consumer note written into the dependency list where it reads as a
dependency. Other stories express the same relationship without creating a cycle
by keeping it out of the bullet list: `CAP-001-E4-S4` says "None for the function
itself. Consumed by CAP-001-E4-S5", and `CAP-001-E1-S4` says "None for the frame
itself. CAP-001-E1-S5 fills the status region slot this story defines."

Not HIGH because the intended order is unambiguous from the prose and no planner
would deadlock on it, but a tool consuming the dependency lists topologically will
not terminate, and this is the only cycle in the graph.
