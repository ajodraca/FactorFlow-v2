### IR-001 — No test pins that the running row's progress follows a new attention answer

- **Severity**: HIGH
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: DAC-E6-14 (the progress half), AC-25 context
- **Tasks**: T004 (the "progress row" half of DAC-E6-14), T003 (b)
- **Files**:
  - `web/src/screens/data-health/recent-downloads.tsx:142–199`: the `columns` memo; its deps `[idPrefix, runningId, done, total]` are what make the cell re-render with a new answer.
  - `web/src/screens/data-health/recent-downloads.test.tsx:300–315` (T003 (b)) and `:435–500` (T004 (a), (b), (d)).
- **Claim challenged**: That the T003 and T004 tests pin the progress half of DAC-E6-14, so a regression in how the cell follows attention would fail them.
- **Observed evidence**: T003 (b) delivers three running answers with `done` 813, 814 and 815, but asserts only the call count and the sub-line. Every T004 progress case asserts a single render. Three reviewer mutants of the memo dependencies at l.199 survive the full `web/src/screens/data-health` suite:
  - `rv:1` drops `done`. The bar stays at the first answer's count for the whole download.
  - `rv:2` drops `total`. A download claimed with `done` 0 keeps its indeterminate bar after the total arrives (DEC-0213 (f)).
  - `rv:3` drops `runningId`. When the latest download changes while `done` and `total` stay equal, the progress stays on the old row.

  A reviewer probe in a throwaway clone of HEAD shows the code is right: the bar reads *900 of 1,236 stocks* after an answer with `done` 900, and turns determinate when the total arrives. The same probe fails with `rv:1` and with `rv:2` applied.
- **Expected evidence/behavior**: DAC-E6-14 and data-health-ui 2.6: "a running download heads the list with `progress` `determinate` and *{done} of {total} stocks* from attention's `latest_download.progress`". ux-design 1.4 *Refresh*: "Recent downloads re-reads on each 10 s attention tick while a download runs and the running row's progress updates". Resolved Conflict 4 ties the progress to the row whose `runId` equals `latest_download.run_id`.
- **Impact**: The suite would pass a change that freezes the progress bar at its first value for a whole download. That bar is the region's only live indicator of a running download. A memo or `useCallback` dependency slip is exactly the edit this would let through, for example when CAP-003-E6-S5 mounts the card.
- **Required remediation**: Add tests that deliver successive non-terminal answers and assert the running row's bar after each:
  - a changed `done` with the same total (`aria-valuenow` and the visible *{done} of {total} stocks*);
  - a total that becomes known while `done` stays the same (the bar becomes determinate);
  - a changed `latest_download.run_id` (the progress moves to the matching row).

  `rv:1`–`rv:3` (in `CAP-003-E6-S4-implementation-review-v1-mutation.json`) must then be killed. No production change is required.

### IR-002 — What you follow's Try again does not return to loading, against T014

- **Severity**: HIGH
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: N/A (DAC-E6-17's error rendering is satisfied); constitution STD-UI-24
- **Tasks**: T014 (*Reads*), T008
- **Files**:
  - `web/src/screens/data-health/what-you-follow.tsx:56–77`: `read()` bumps the counter and awaits `Promise.all` but never sets `{ kind: "loading" }`.
  - `web/src/screens/data-health/what-you-follow.test.tsx:257–274` and `:488–506`: both click **Try again** twice in a row, which works only because the error body stays on screen.
- **Claim challenged**: That T014 is complete. The evidence records this as cycle 5's deviation (1): "the error body stays until the reads answer, as in Recent downloads, and no criterion or test case observes the difference".
- **Observed evidence**: After **Try again**, the card keeps its error sentence and button until both reads settle. If the retry fails the same way, React keeps the same `<output>` text, so nothing changes on screen and nothing is announced.

  The recorded reason does not hold. In Recent downloads, `read()` is also the 10 s polling re-read, so a loading body there would blank the table on every tick, and T013 deliberately sets none. In What you follow, `read()` runs only on mount and on **Try again**, so that reason does not transfer.

  The established pattern also goes the other way. The same epic's `needs-fixing.tsx` `LastComplete.load` sets `{ kind: "pending" }` before re-reading (l.46–49), and the research screens set `loading` on Try again (`screens/research/stocks/index.tsx:195`, `screens/research/universes/index.tsx:69`).
- **Expected evidence/behavior**:
  - Task plan T014 *Reads*: "`read()` sets `loading` and awaits `Promise.all([listInstruments({ limit: 1 }), getHistoryDepth()])` … It runs once on mount and on **Try again**". T008 (a) then defines the loading body: `h2` kept, `aria-busy`, no `dl`.
  - Constitution STD-UI-24: "An operation whose effect is not immediately visible MUST confirm its completion explicitly."
- **Impact**: The owner's only recovery action on the card gives no sign that it ran. A retry that fails again looks exactly like a button that did nothing. Overlapping retries are also possible, and that is the only reason the stale-call guard is observable at all.
- **Required remediation**: Make What you follow's `read()` set the loading body before it reads, as T014 states. Add a test that **Try again** shows the T008 (a) loading body until the reads settle. Rework the two double-click tests so they still prove what they claim, or record why the guard is no longer observable. Recent downloads' **Try again** is not covered by this finding: T013 is silent there, and its `read()` serves polling.
