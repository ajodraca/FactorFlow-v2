# Needs Fixing: Problem Rows with Their Fix, the Header Action, Show More and Nothing Needs Fixing

## User Story
As an owner-operator, I want every followed stock with a problem listed with what failed, why, what it means and the fix that applies, so that I never guess whether downloading again would help.

## Description
Creates `web/src/screens/data-health/problem-row.tsx` (the symbol at weight 600 linking to `/data/coverage?symbol={SYMBOL}`; per failure `StatusBadge` *Failed* (critical) or *Not found* (warning) with *Downloading {daily prices / company financials / corporate actions / reference data} failed: {reason}, {attempts} attempts* or *The provider doesn't recognise this symbol.*; the consequence; the fix: *Failed* reads the download-again sentence with no per-row control, *Not found* gives **Stop following** (`button` `ghost`, opening E6-S2's dialog) and **Follow a different symbol** (`button` `outline`, a link to `/data/followed` with router state `{ focusAdd: true }`) with *Probably a typo or a delisted ticker. Downloading again won't help.*) and `needs-fixing.tsx` (header *Needs fixing · {n}* from `affected_count`, the sub-line *From your most recent downloads · checked {time}*, **Download now** only when any loaded row is `retryable`, one `li` per row ordered by symbol, **Show more** when `next_cursor` is set appending `fetchProblems(cursor, 50)` with focus kept and the new count announced, a `422` reading *Couldn't read more problems: {reason}.* with **Try again** restarting from the first page; at `affected_count` 0, *Nothing needs fixing.* with *Last complete download {start time}* from `listAcquisitionRuns({ state: "succeeded", limit: 1 })` or *No complete download yet*). Writes `problem-row.test.tsx` and `needs-fixing.test.tsx`.

**Version 2 (2026-11-08): the fix by cause is CAP-003-E8-S9's** (DAC-E6-8 v3; backlog review v5 FINDING-1). DAC-E6-8 v3 makes *Download again* the fix of a *Failed* failure except one whose cause is a plan refusal or a rate limit, whose what-failed line and fix are DAC-E8-17's. This story lands before the failure type carries `cause` (CAP-003-E8-S8), so it renders the *Download again* line, with its attempt count, for every *Failed* failure, choosing the fix in one place by outcome; CAP-003-E8-S9 replaces that choice with `ui-components`' `failureRecovery` and adds the two causes' lines. To keep the two stories' tests from contradicting each other, this story's *Failed* fixtures use reasons beginning `[unavailable] ` (or `null`), the causes whose fix stays *Download again*, and never `[not_entitled] ` or `[rate_limited] `; when CAP-003-E8-S8 has already landed, those fixtures also carry `cause` `"unavailable"` or `null`. The header's **Download now** reads the served `retryable` and needs no change for plan refusals, which the server stops counting as retryable (CAP-003-E8-S6). **Attempt counts:** the delivered writer never records `attempts`, so the served value is the column default, 1 (specification review v5 FINDING-29; backlog review v5 FINDING-4); the line shows the served value and no test asserts a count other than the one its fixture serves.

Source: component-design-data-health-ui.md 2.1, 2.5, 3, 7; epic CAP-003-E6 DAC-E6-8 (v3) to DAC-E6-10, DAC-E6-13.
