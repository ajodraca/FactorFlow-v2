# Register Setup in the Shell: the /setup Route, Its Title and the SetupDraftProvider Mount

## User Story
As an owner-operator, I want setup reachable at `/setup` inside the shell with my drafts held above the route, so that an empty install opens on setup and leaving setup never discards what I typed.

## Description
The owner-shell story that closes E4 (DEC-0223 answer A): registers `/setup` with `setup-ui`'s `SetupScreen` in `web/src/app/routes.tsx`, adds *Setup* to `titles.ts`, and mounts `SetupDraftProvider` (`web/src/screens/setup/draft.tsx`) in `shell.tsx` inside `ShellProvider` and outside the main region's route map, so neither a route change nor the unreachable state unmounts it (owner-shell 2.1, 2.2; setup-ui 3). Setup is not a rail destination, so `DESTINATIONS` is unchanged. Extends `routes.test.tsx`, `titles.test.tsx` and `shell.test.tsx` (the provider survives the unreachable state), and extends `tests/e2e/startup-health.spec.ts` with the empty-install landing on setup's `h1` (owner-shell 2.10).

**Cross-epic delivery, for traceability (backlog review v3 FINDING-2).** This story delivers E3's AC-3 clause (*This EPIC mounts `setup-ui`'s `SetupDraftProvider` above the `/setup` route*) and DAC-E3-14 from E4, because the provider is E4's and the owner chose the registration-with-mount placement over an E3-before-E4 inversion (DEC-0223, owner_decision). The epic text still states the earlier allocation; at the next EPIC edit the mount clause moves to E4.
