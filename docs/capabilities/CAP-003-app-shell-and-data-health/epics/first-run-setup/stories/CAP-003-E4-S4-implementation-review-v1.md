### IR-001 — The progress line renders *Started* and *checked* fused into one string

- **Severity**: HIGH
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: DAC-E4-9 (with AC-7, AC-25)
- **Tasks**: T017; T002 (TC-COMP-101), T005 (TC-COMP-119)
- **Files**: `web/src/screens/setup/step-download.tsx:229-238`; `web/src/screens/setup/step-download.test.tsx:242-243`, `:425`, `:772-773`
- **Claim challenged**: T017 and the cycle-2 evidence claim the `202` outcome renders *Started {start time}* and *checked {time}* as DAC-E4-9 states, and TC-COMP-101 claims to prove it.
- **Observed evidence**: The paragraph's children are two `<span>`s with no text node between them (compiled: `jsxs("p", { className: "text-xs text-muted-foreground", children: [jsx("span", …started…), attention.kind === "ok" ? jsx("span", …checked…) : null] })`), and `STEP4.started` and `STEP4.checked` (`copy.ts:153-154`) carry no surrounding space. The `<p>` is not a flex container, so nothing separates them visually either. Rendering the delivered component with the test fixtures gives the text content `"Started 2026-10-15 09:30 CDTchecked 09:31:12 CDT"`: the owner reads *CDTchecked*, and a screen reader reads the same token. Every test queries the two spans separately with `getByText("Started …")` and `getByText("checked …")`, which match each span on its own, so the suite passes on the fused line.
- **Expected evidence/behavior**: DAC-E4-9 (epic CAP-003-E4) and setup-ui §10 step 4 state *Started {start time}* and *checked {time}* as two texts; UX design §1.2 writes the line *Started {start time} · checked {time}*. The plan's Resolved Conflict 2 settles it as "two spans in one muted line, with no separator character", meaning no `·`, not no boundary at all. The delivered `components/patterns/as-of-line.tsx:183-192` renders the same *checked {time}* tail "with no separator" by emitting `{" "}` before its span.
- **Impact**: Every view of step 4's progress after a `202`, and every reopened setup with a download, shows the garbled line. It is the line AC-25 and STD-UI-25 rely on for polled freshness.
- **Required remediation**: The two texts render with a boundary in the DOM text, for example a space between the spans as `as-of-line.tsx` does, so the line's text content reads `Started {start time} checked {time}` (with any separator Resolved Conflict 2 allows), and the boundary also holds when *checked* is absent. Add a test that asserts the whole line's text content after a `202` (TC-COMP-101) so the fused form fails.

### IR-004 — The pending *Queued* view is not latched to DEC-0356's "until"

- **Severity**: MEDIUM
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: DAC-E4-S4-6 (via DEC-0356); DAC-E4-12's "never a frozen bar"
- **Tasks**: T017, T009 (a)
- **Files**: `web/src/screens/setup/step-download.tsx:137`
- **Claim challenged**: DEC-0356 (and the plan's Open Gap 1) adopt the pending view "until attention's latest_download names this visit's download".
- **Observed evidence**: `shown = ours !== null && latest?.run_id !== ours.runId ? PENDING : latest` re-applies on every render, and `ours` is never cleared. Once attention has named this visit's download, any later download that becomes `latest_download` (attention reports the greatest `requested_at`, data-health-reader §2.6), for instance one requested from Data health in another tab or queued behind this one, makes `latest.run_id` differ again. The region then shows *Queued*, an indeterminate bar and *You can leave; this keeps running.* with no *Started* or *checked* line, whatever state that later download or this one is in, and stays so after both have ended. The plan's T017 expression is the same, so the code follows the plan's letter; the cycle-2 code review named the case as a LOW observation and it was not addressed. No test pins the "until" semantics.
- **Expected evidence/behavior**: DEC-0356's derivation: "showing that older download's state as this one's would misstate it". The converse holds after the switch: a *Queued* label for a download that is running or ended misstates it, and an indeterminate bar that never advances is the frozen bar DAC-E4-12 forbids.
- **Impact**: Narrow: it needs a second download requested during the same setup visit by something other than this step's own **Start download**, which updates `ours` and stays correct. The region then misreports progress until the owner leaves.
- **Required remediation**: Apply the pending view only until attention first names this visit's download (or another rule the owner settles under DEC-0356), with a test in which a later download becomes `latest_download` after this one was named.
