## Findings

### IR-001 — The instant an answer is stamped with is not pinned against a read that takes time

- **Severity**: MEDIUM
- **Scope**: late
- **Status**: OPEN
- **Acceptance criteria**: AC-25, DAC-E3-S2-3 (both SATISFIED; this is test strength)
- **Tasks**: T005 (a), T006 (a), T010, T011
- **Files**: `web/src/app/use-polled-read.ts:117` (`const checkedAt = new Date();` in the settle handler); `web/src/app/health.tsx:132` (`const now = new Date();`); `web/src/app/use-polled-read.test.ts:295-319`; `web/src/app/health.test.tsx:97-125`
- **Claim challenged**: T005 (a) says the test shows "`checkedAt` is the answer's instant and not the mount's". T006 (a) says it shows `lastAnsweredAt` is the instant of the first success.
- **Observed evidence**: Two of my mutants survive all 86 focused tests and `tsc`. `manual:v2:1` takes `usePolledRead`'s `checkedAt` from the instant the read started. `manual:v2:2` does the same for health's `now`, which feeds both `lastAnsweredAt` and `lastUpdated`. Every test settles each read at the instant it starts: deferred reads are resolved without advancing the fake clock, and resolved mocks settle within the same tick. So "start" and "answer" can never differ. The tests do distinguish the answer's instant from the mount's, which is what T005 (a) names, but not from the request's.
- **Expected evidence/behavior**: T010: "On success it … sets `{ kind: "ok", data, checkedAt: new Date() }`", inside the settle handler. The module comment: "Every answer carries `checkedAt`, the instant it arrived (AC-25)". DAC-E3-S2-3: "When a health read succeeds, Then `lastAnsweredAt` is that instant". TC-COMP-071: "`lastAnsweredAt` is the instant of the success". `HealthState.lastUpdated`: "When the last poll completed".
- **Impact**: The code is correct today. A refactor that takes the timestamp before awaiting, to time the request for example, would make *Last answered* and every chip's last-updated time early by the request's latency. That latency is unbounded, because `fetchHealth` has no timeout. The suite would stay green. DEC-0340's e2e bracket for CAP-003-E3-S8 accepts any instant from `floor(request sent)`, so it would not catch this either.
- **Required remediation**: Non-blocking, for a later rework or the next story to touch these files. Add one case per hook: start a deferred read, advance the clock (by 5 s, say), resolve it, and assert that `checkedAt`, and health's `lastAnsweredAt` and `lastUpdated`, equal the settle instant.

### IR-002 — An answer that settles while the page is hidden is not asserted to be applied

- **Severity**: MEDIUM
- **Scope**: late
- **Status**: OPEN
- **Acceptance criteria**: DAC-E3-S2-1, DAC-E3-5 (both SATISFIED; this is test strength)
- **Tasks**: T003, T007, T010
- **Files**: `web/src/app/use-polled-read.ts:49-51` (`onSettled` is called whatever the visibility), `:56` (the hidden check governs scheduling only); `web/src/app/use-polled-read.test.ts:130-148`; `web/src/app/health.test.tsx` (no case of this kind)
- **Claim challenged**: T010's rule that a settled read reports through `onSettled` first, with the hidden check governing only the next timer. The plan treats this as covered by the "settles while hidden" case.
- **Observed evidence**: `manual:v2:14` makes `startPolling` call `onSettled` only while the page is visible, and it survives. `:130-148` resolves a read after `setVisibility("hidden")` and asserts only `read` call counts, never `result.current.state`. `manual:v2:13` makes health report an answer that arrives while hidden as a failure, and it also survives: no health case settles a read while the page is hidden.
- **Expected evidence/behavior**: T010: "On settle it calls `onSettled` first, so `nextDelayMs` sees the new answer. Then, in a `finally`, it clears `inFlight` and, unless `stopped` or `document.visibilityState === "hidden"`, sets `timer`". DAC-E3-5: `HealthProvider` keeps its delivered states, so a successful answer is `answering`.
- **Impact**: The code is correct today. Under either mutant, an answer that arrives just after the owner switches tabs would be thrown away. On return the screen shows the older value, or `loading`, until the read on show answers. If that read fails, `error.last` and *Last answered* name an older answer than the product actually gave. For health, a product that recovered while the tab was hidden would still read as unreachable on return.
- **Required remediation**: Non-blocking. Extend `:130-148` to assert the state carries the answer that settled while hidden (`kind: "ok"`, its data and its instant). Add the health equivalent: a fetch that resolves while hidden gives `answering` and a `lastAnsweredAt`.
