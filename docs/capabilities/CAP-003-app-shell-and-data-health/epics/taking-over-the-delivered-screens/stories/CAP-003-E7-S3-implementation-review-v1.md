### IR-001 — Followed stocks never shows its last-updated time: the Stale row of its eight-state table is neither rendered nor recorded

- **Severity**: HIGH
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: AC-24 (capability AC-24; STD-UI-23)
- **Tasks**: T018 (1), T019 (3). The plan enumerates `StateRegion`'s kinds and omits Stale
- **Files**: `web/src/screens/instruments/instrument-table.tsx:104–108`, `229–263`; `web/src/screens/instruments/index.tsx:82–86`, `106–112`
- **Claim challenged**: "Both data regions render their eight states through `StateRegion` (AC-24)" (plan Summary). AC-24: "The screen MUST keep its eight-state table through `StateRegion`."
- **Observed evidence**: Both reads store `fetchedAt` in their `populated` state (`instrument-table.tsx:107`, `index.tsx:84`), but neither renders it. No other code shows when the list was read. The populated table holds no time-like text (probe 2). No reason for the Stale state appears in the `NOT_REACHED` and `RENDERERS` records (`index.tsx:13–26`, `instrument-table.tsx:31–48`), in the plan, or in a decision record. CAP-001's review of this screen raised the same omission (CAP-001-E2-S4 review v1 IR-012 (b)). It stayed open as the owner's call under CAP-001, before AC-24 existed.
- **Expected evidence/behavior**:
  - UX design 1.6 States: "v5 §1.2's table, relabelled: … last-updated time …".
  - CAP-001 UX design v5 §1.2 States: "Stale | Last-updated time".
  - ux-brief §12.4, *Taken-over screens (five)*: Stale "Unchanged".
  - Owner-web-app 2.5: "Each screen keeps v5's eight-state table, relabelled (UX design 1.5 to 1.9), and renders it through `ui-components`' `StateRegion` over the delivered `ScreenState` union". Under that union, Stale is the `populated` kind's `fetchedAt`.
  - Capability AC-24: "render each of STD-UI-23's eight states as designed, or record why one does not apply".
  - STD-UI-23 lists *stale* among the eight.
  - Coverage and Downloads already render *Last updated {time}* from the same field (`coverage/index.tsx:191`, `runs/index.tsx:147`).
- **Impact**: The owner cannot tell how old the followed list on screen is. A stock followed in setup in another tab, or by a later action elsewhere, is absent with no cue that the list is old. A designed state of a story AC is silently dropped. The derived DAC-E7-S3-6 and TC-COMP-203 phrase the table through the `ScreenState` union and so do not catch it, but they cannot narrow the capability AC that requires it.
- **Required remediation**:
  - Render the table read's last-updated time in its populated state from `fetchedAt`. Use UX design 0.7's timestamp form, as the sibling taken-over screens do, in words free of the DAC-E7-S3-4 terms.
  - Pin it with a test: present after the first read, and moved on by a re-read.
  - If the coder concludes instead that Stale does not apply to this read-on-demand screen, that contradicts UX design 1.6's explicit *last-updated time*. It is a question for the owner, not a provisional decision.

### IR-002 — A double activation of **Stop following** sends two DELETEs and attributes the second refusal to the next stock

- **Severity**: MEDIUM
- **Scope**: initial
- **Status**: OPEN
- **Acceptance criteria**: AC-17, AC-25 (STD-UI-19 three-part refusals)
- **Tasks**: T014, T018 (4)
- **Files**: `web/src/screens/instruments/retire-dialog.tsx:27–37`; `web/src/screens/instruments/instrument-table.tsx:176–185`, `219`, `308–318`; `web/src/components/ui/dialog.tsx:30–31`, `92–97`
- **Claim challenged**: The dialog keeps CAP-001's IR-004 behaviour, under which a failed stop is shown in the dialog for that stock.
- **Observed evidence**: The reviewer probe (scratch clone) clicked the dialog's **Stop following** twice while the first `retireInstrument` was pending, and `retireInstrument` ran twice. The first resolved, so the dialog closed and the list re-read. The second rejected (*AAPL is already stopped*), which sets `retireError` while no dialog is open. Opening **Stop following MSFT** then shows `role="alert"` *Stopping following MSFT failed: AAPL is already stopped*. The cause is twofold:
  - `RetireDialog` does not pass `ConfirmDialog`'s `pending`, which exists to hold the confirm action and the close while the consumer waits (`dialog.tsx:17–20`, `30–31`).
  - The row action sets `retireTarget` without clearing `retireError` (`instrument-table.tsx:219`).

  The delivered code had the same unguarded confirm and the same row action, so this is not a regression.
- **Expected evidence/behavior**: A refusal names the operation, the stock and the reason that belong together (STD-UI-19; UX design 0.7 *Every error has three parts*). A stop is sent once per confirmation.
- **Impact**: The owner can be told that stopping one stock failed for a reason that concerns another. The second, redundant DELETE is harmless server-side (409), but its message is misattributed.
- **Required remediation**: Hold the confirmation while the stop is in flight. Passing `pending` is the dialog's own mechanism. Also make sure a dialog opened for a stock never shows a refusal from an earlier one. Pin both with a test.
