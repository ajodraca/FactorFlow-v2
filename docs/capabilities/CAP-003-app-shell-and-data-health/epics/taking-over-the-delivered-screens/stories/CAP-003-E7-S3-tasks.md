# Tasks: CAP-003-E7-S3 — Followed Stocks Under the Shell: Follow, Follow Many, Stop Following with dialog confirm, Not Found and the Focused Add Field

**Story**: `repos/factorflow-v2/FactorFlow-v2/docs/capabilities/CAP-003-app-shell-and-data-health/epics/taking-over-the-delivered-screens/stories/CAP-003-E7-S3.md`

**Date**: 2026-11-07

## Summary

Takes over CAP-001's Instruments screen, `web/src/screens/instruments/*`, as **Followed stocks** at `/data/followed` (route registered by CAP-003-E3-S4), in the product's words and built from `ui-components`, without changing a request, query parameter, confirmation step, refusal or cadence (AC-17; system design constraint 2; owner-web-app 2.1, 2.3, 2.4, 2.6). Labels follow UX design 1.6 exactly: h1 *Followed stocks*, **Follow a stock**, **Follow many**, **Stop following**, *Stopped following*, *followed*, *No stocks followed yet.*, *No stock matches this filter.*, the add field named *Symbol of the stock to follow*, the count *{n} followed, {m} stopped following* (DAC-E7-4). The native retire `<dialog>` becomes `dialog` `confirm` (CAP-003-E1-S3's `ConfirmDialog`) with the blueprint §9 wording and **Stop following**, **Cancel** first and focused (DAC-E7-9). The stopped-following marker and the *Not found* recognition marker render through `StatusBadge` with label and `aria-hidden` shape (DAC-E7-S3-5). The table becomes `data-table` `virtualised` over the delivered keyset pages (DAC-E7-11), each symbol linking to `/data/coverage?symbol={SYMBOL}` (DAC-E7-1). Opened with router state `{ focusAdd: true }` (sent by CAP-003-E6-S3's **Follow a different symbol**) the add field takes focus once, and the state is cleared so a reload does not re-focus (DAC-E7-6). Both data regions render their eight states through `StateRegion` (AC-24). `parse-bulk-symbols.ts` is untouched (AC-5) and `web/src/screens/instruments/` joins the AC-26 literal scan (DAC-E7-S3-3). The writes are the new `entry-hint.test.tsx`, the edited screen files and their tests, one entry in `web/src/components/token-literals.test.ts`, and one assertion in a Coverage test that pins this story's `LifecycleBadge` output.

## Notes

### Resolved Conflicts

1. **The running-download sentence: "conditional" vs the delivered, accepted rendering.** DAC-E7-9 asks for "v5's conditional sentences relabelled"; CAP-001 v5 §1.2 shows the sentence "when a run is under way". The delivered `retire-dialog.tsx` renders it every time (CAP-001 IR-002, a deviation the CAP-001 review authorised because no run-status source existed). Capability AC-17 requires every confirmation CAP-001 accepted to keep the same outcome, and story DAC-E7-S3-2 only requires the sentence when a download is running, which unconditional rendering satisfies. No artifact determines a reliable "a download is running" source for this screen (Open Gap 2), so whether to make it conditional is recorded as DEC-0390 rather than settled here; the wording itself is fixed by DAC-E7-9 and UX design 1.6 verbatim.
2. **Stopped-following marker: `badge` `secondary` vs "through `StatusBadge`".** UX design 1.6 Component Mapping and Token Usage and owner-web-app 10 map the marker to `badge` `secondary`; story DAC-E7-S3-5 and TC-COMP-202 require it to go "through `StatusBadge` with its label and `aria-hidden` shape". Precedence (story AC over design prose) makes `StatusBadge` govern, and `StatusBadge` (CAP-003-E1-S5) renders only the six `status-<tier>` variants, so the `secondary` variant falls away. Which tier it takes is not determined by any artifact (ux-brief §12.2 has no lifecycle row): DEC-0389.
3. **"Router state is not persisted, so a reload does not re-focus" (owner-web-app 2.4).** The rationale is not true of a browser: React Router keeps `location.state` in `window.history.state`, which survives a reload of the same entry. DAC-E7-6's requirement ("a reload MUST NOT re-focus", epic AC) governs over the design's rationale clause (constraint 9.2), so T019 consumes the hint and replaces the history entry with `state: null`; T002 case 2 proves a reload of that entry does not re-focus. Owner-web-app 2.4's sentence should say the screen clears the state at its next revision.
4. **Focus on route change vs the focused add field.** Owner-shell 2.x ("focus moves to the routed screen's `h1`", implemented by CAP-003-E3-S6) and epic DAC-E7-6 (the add field takes focus when opened with `focusAdd`) both fix where focus lands on arriving at `/data/followed` with the hint. The epic AC governs over the shell design's prose. This story's code focuses the field when it mounts after the list answers; the integrated ordering is CAP-003-E3-S6's to honour (its focus move must not run after, or must skip, a screen that has already placed focus inside the main region). Flagged for owner-shell's next revision and for E3-S6's planner; it does not block this story, whose tests render the screen without the shell.
5. **Error copy and the request id.** The delivered screen shows *Loading instruments failed: {message} (request {id})* with **Retry**; UX design 0.7 says "`request_id` is never shown" and UX design 1.6 States say the error "offers **Try again**". The UX design governs (design prose over delivered code). The sentence *Couldn't read followed stocks: {reason}.* follows the pattern UX design 1.5, 1.7 and 1.8 fix for the other taken-over screens (constraint 9.5 precedent); `StateRegion` renders it in a `status` element with **Try again** (DEC-0314).
6. **Strings the UX design does not list.** UX design 1.6 lists the label deltas; the add field's error and notice, the bulk region's result line and failure, and the dialog's error are not listed.
