# Tasks: CAP-003-E1-S2 — Vendor the Form Family: form, input, textarea, checkbox, radio-group and select

**Story**: `repos/factorflow-v2/FactorFlow-v2/docs/capabilities/CAP-003-app-shell-and-data-health/epics/design-system-components-and-shared-patterns/stories/CAP-003-E1-S2.md`
**Component**: `FactorFlow-v2` (web interface, `web/src/`; design module `ui-components`)
**Branch**: `usr/alvaro-de-jodra/CAP-003-tasks`
**Date**: 2026-11-07

## Summary

Vendors the six form controls the setup steps, Settings and the followed-stocks screen are rebuilt from (component design 2.1; UX design §3): `form` (`stacked`, `inline`, on `react-hook-form` with the `zod` resolver), `input` (`text`, `numeric` with a suffix), `textarea` (`list`), `checkbox` (`default`), `radio-group` (`cards`, Radix) and `select` (`inline`, Radix), into `web/src/components/ui/` from shadcn/ui's Tailwind v3 sources, with `@/` imports rewritten to relative paths, every literal-backed class replaced by a token-backed one, and one contract test file per component. It adds exactly seven packages, `react-hook-form`, `zod`, `@hookform/resolvers`, `@radix-ui/react-label`, `@radix-ui/react-radio-group`, `@radix-ui/react-checkbox` and `@radix-ui/react-select`, each with its licence verified. The keyboard contracts every consuming screen relies on are pinned by test: the radio cards are one tab stop with arrow keys moving the selection, the select opens and closes from the keyboard with `combobox` and `listbox` roles, the checkbox toggles on Space, a numeric field's suffix is part of its accessible name, and a field error is linked through `aria-describedby` and announced (AC-25). The six files pass the AC-26 literal scan CAP-003-E1-S1 writes (AC-26, DAC-E1-12).

## Notes

### Resolved Conflicts

1. **"As shadcn/ui ships them" vs the placement inventory for `label`.** shadcn/ui's `form` imports `Label` from a separate `components/ui/label` file. Component design 2.1 places exactly the vendored files it lists (no `label.tsx`), the story's Implementation lists exactly six component files, and the story's package list adds `@radix-ui/react-label` for `form`. The design placement and the story govern over the generic "as shipped": `FormLabel` renders `@radix-ui/react-label`'s `Root` directly inside `form.tsx`, and no `label.tsx` is created. Controls outside a form are labelled by a native `label` or `aria-label`. (Corrects resolution register gap G5's `label` half; see register Corrections.)
2. **`textarea` `list` anatomy vs who renders the counter.** The textarea design-system spec (§3) lists an entry counter and a rejected-entry list as required parts of the `list` variant. The approved CAP-003 artifacts place the parse, the counter copy (*{a} symbols recognised, {d} duplicates, {r} not recognised*), its badges and the rejected entries in the consuming screens: story CAP-003-E4-S3 (`step-stocks.tsx` "with a polite parse counter", parsed by the delivered `parseBulkSymbols`), setup-ui design §10 and UX design 1.2 / 1.6; component design 2.1 gives `textarea.tsx` the variant only. The story-level and CAP-003 component-design statements govern over the generic spec anatomy: the vendored `list` variant carries the field rules (four rows minimum, no resize, Enter inserts a newline, Escape does nothing, read-only rather than disabled while submitting is the caller's) and each consumer composes its counter in a polite live region tied by `aria-describedby`, as the delivered `bulk-add.tsx` already does. Nothing in either source is wrong; the split is recorded so E4-S3 and E7-S3 do not expect a counter prop.
3. **`radio-group` orientation.** The radio-group spec §4 says "`orientation` follows the variant", and `cards` lays the options out in a row; Radix ignores ArrowUp/ArrowDown under `orientation="horizontal"`. Story DAC-E1-S2-1 ("arrow keys move the selection"), TC-COMP-009 step 1 ("press ArrowDown") and the spec's own keyboard table (ArrowDown/ArrowRight and ArrowUp/ArrowLeft both move) govern: the cards root leaves `orientation` unset, so Radix handles both axes.
4. **`checkbox` box border.** shadcn/ui ships `border-primary`; the checkbox spec §5-6 sets the box border to `--input` (3:1). The design-system spec, which component design 2.1 makes the variant source, governs over the shipped class: `border-input`, with the `--primary` fill only when checked.

### Open Gaps

1. **How the `input` suffix joins the accessible name. PROVISIONAL — awaiting owner confirmation (2026-11-06). Recorded as DEC-0299.** DAC-E1-S2-2 and the input spec §5 require the suffix to be part of the input's accessible name, and UX design 1.2 / 1.3 and setup-ui §10 call it a "non-editable suffix *years* (part of the accessible name)"; no artifact names the prop or the mechanism. shadcn/ui's `FormLabel` names its control by `htmlFor` only, which cannot include text outside the label. Adopted (T007, T008, T009, T015, T016): `Input` takes `suffix?: string`, renders it as visible text in a `span` after the field, and names the input by `aria-labelledby="<label id> <suffix id>"`; `FormLabel` gets `id = \`${id}-form-item-label\`` and `FormControl` passes `aria-labelledby` naming it, so inside a form the name is *History depth years* with no caller wiring. Derivation: `aria-labelledby` is the only accessible-name source that concatenates two elements in order (accname 1.2); putting the label id on `FormControl` also gives a `radiogroup` inside a form its name, which a `label` `for` cannot (a `div` is not labelable; radio-group spec §5 requires the group to be labelled); the delivered `history-depth-form.tsx` reached the same name with a hand-written `aria-label="History depth, in years"`, which the vendored component replaces generically. Outside `FormControl`, a suffixed input must be given `aria-labelledby` (doc comment). Consumers: CAP-003-E4-S2 (setup step 2), CAP-003-E7-S1 (Settings depth form). Follow-up: component design `ui-components` section 2.1 (or 10) should state the suffix prop and the `FormControl` labelling at its next revision.
2. **The variant and part API of the form family. PROVISIONAL — awaiting owner confirmation (2026-11-06). Recorded as DEC-0300.** Component design 2.1 fixes the variant names (`form` `stacked`/`inline`, `input` `text`/`numeric`, `textarea` `list`, `checkbox` `default`, `radio-group` `cards`, `select` `inline`), but shadcn/ui ships none of these as variants and no artifact says how a caller selects one or which parts carry it. ### Other Notes

- **Field errors are `role="alert"`.** DAC-E1-S2-2 and TC-COMP-010 require the error to be "announced"; the input spec §5 says the error is announced when it appears, which a reference through `aria-describedby` alone does not do once focus has left the field (validation runs on blur). The delivered `web/src/screens/settings/history-depth-form.tsx` (the field this component replaces) renders its error `p` with `role="alert"`; `FormMessage` follows that precedent (constraint 9 step 5) and sets the role only while it shows an error. The form spec's assertive summary region has no CAP-003 consumer and is not vendored.
- **Control height floor.** The input, select and form specs require controls at least 44 CSS px tall; shadcn's `h-10` is a Tailwind default literal (2.5rem) and below that floor. `h-7` resolves through the delivered `height` key to `--space-7` (3rem), the smallest theme value meeting the floor. Select options use `h-row` (`--row-height`, 32 px, the spec's option minimum).
- **Spacing keys 5-8 differ from Tailwind's defaults.** The delivered config maps spacing 1-8 to `--space-1..8`; 1-4 equal Tailwind's defaults, but `--space-5` is 1.5rem, `--space-6` 2rem, `--space-7` 3rem and `--space-8` 4rem. Translate each shipped class by value, not by name (shadcn's `pl-8`, 2rem, becomes `pl-6`); fractional steps (`py-1.5`, `h-3.5`, `h-2.5`) round to the nearest key. Classes outside 1-8 (`h-10`, `max-h-96`, `min-w-[8rem]`) are literals and are replaced.
- **Removed shipped classes.** `ring-offset-*` (a literal offset), `ring-2` (replaced by `ring`, which resolves to `--focus-ring-width`), `rounded-md` / `rounded-sm` (replaced by `rounded`, `--radius`; the checkbox uses `rounded-none` because `--radius` on a 16 px box would draw a circle indistinguishable from a radio), `shadow-md` (a literal shadow; the popover is bounded by `border-border`), `md:text-sm` (a breakpoint literal and a size the UX design 10 does not use for fields), the `file:` input classes (no file input is vendored), and every `animate-in`/`fade-*`/`zoom-*`/`slide-in-*` class, which need the `tailwindcss-animate` plugin, a package outside the confirmed set (DAC-E1-12).

A consumer that needs an extra description (CAP-003-E4-S3's counter) puts it inside `FormDescription`, whose id `FormControl` already references, rather than overriding `aria-describedby`.
