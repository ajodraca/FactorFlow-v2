# Vendor the Overlay and Feedback Family: dialog confirm, command, toast, progress and stepper

## User Story
As an owner-operator, I want confirmations, the palette surface, toasts, progress bars and the setup stepper built once with their focus and announcement contracts, so that every screen that confirms, searches, notifies or shows progress does it the same accessible way.

## Description
Vendors `dialog` (`confirm`, Radix AlertDialog), `command` (cmdk inside Radix Dialog: `Command`, `CommandDialog`, `CommandInput`, `CommandList`, `CommandEmpty`, `CommandGroup`, `CommandItem`, `CommandSeparator`, `CommandLoading`), `toast` (`Toaster` and `toast()` with `success`, `warning`, `error`, on `sonner`), `progress` (`determinate`, `indeterminate`, Radix) and the bespoke `stepper` (`vertical`, a native `ol`) into `web/src/components/ui/`, with contract tests (ui-components 2.1, 7; DAC-E1-14). Adds `@radix-ui/react-dialog`, `@radix-ui/react-alert-dialog`, `@radix-ui/react-progress`, `cmdk` and `sonner`, each with its licence (DEC-0205, DEC-0215). `dialog` `destructive` is not vendored: nothing in this capability deletes (DAC-E1-15; STD-UI-2). The `command` dialog keeps shadcn/ui's own 560 px width, the one literal the literal scan allows (UX design 1.1).

Source: component-design-ui-components.md 2.1, 3, 7; UX design §3.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC
- [AC-25] Every operation MUST be completable by keyboard. This story delivers the dialog, combobox, listbox, progressbar and stepper contracts.
- [AC-26] Every surface MUST be built from the product's design-system components and consume its theme tokens.
- [DAC-E1-14] `dialog` `confirm` MUST put **Cancel** first and focus it; `stepper` MUST set `aria-current="step"`; `progress` MUST expose `progressbar` labelled by its visible text; `command` MUST loop and restore focus on close. (traces to: AC-25)
- [DAC-E1-15] `dialog` `destructive` MUST NOT be used for stopping following or cancelling a download, because nothing is deleted. (traces to: AC-25)

### Derived
- [DAC-E1-S3-1] Given `dialog` `confirm` open, When rendered, Then it has `role="dialog"` with `aria-modal`, focus is trapped, **Cancel** is the first control and focused, `Esc` closes it and focus returns to the triggering control. (traces to: DAC-E1-14)
- [DAC-E1-S3-2] Given `toast()` with `error` or `warning`, When raised, Then it persists until dismissed, never takes focus and is announced politely; `success` toasts dismiss on sonner's default. (traces to: AC-25)
- [DAC-E1-S3-3] Given `progress` `indeterminate`, When rendered, Then `progressbar` carries no `aria-valuenow`; `determinate` carries `aria-valuenow`, `aria-valuemin` 0 and `aria-valuemax` from its props and is labelled by its visible text. (traces to: DAC-E1-14)
- [DAC-E1-S3-4] Given `command`, When opened, Then its dialog is labelled *Search FactorFlow*, `loop` is set, the input has focus, and `CommandEmpty` renders the caller's wording. (traces to: DAC-E1-14)
- [DAC-E1-S3-5] Given the five components, When `token-literals.test.ts` runs, Then it passes with the `command` 560 px width as its one allowed literal, and `package.json` gains only the five packages above with their licences. (traces to: DAC-E1-12)

## Technical Details

### API Contract
- None: this story serves no endpoint and consumes none beyond the shell context.

### Data Changes
- None: no schema, migration, index or browser storage.

### Implementation
- Files: `web/src/components/ui/dialog.tsx`, `command.tsx`, `toast.tsx`, `progress.tsx`, `stepper.tsx` and one `*.test.tsx` each; `package.json`, `package-lock.json`.
- The `stepper` is bespoke (ui-components 2.1): a native `ol` whose items carry done, current or to-do state in text and `aria-current="step"` on the current one.

### Validation
`npm run test`, `npm run lint`, `npm run format`, `npx tsc --noEmit`, `npm run build` (tech stack v7 validation commands).

### Dependencies
- **CAP-003-E1-S1**, `cn()`, `button` (dialog actions) and the literal-scan test.
