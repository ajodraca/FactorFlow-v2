# Tasks: CAP-003-E1-S3 — Vendor the Overlay and Feedback Family: dialog confirm, command, toast, progress and stepper

**Story**: `repos/factorflow-v2/FactorFlow-v2/docs/capabilities/CAP-003-app-shell-and-data-health/epics/design-system-components-and-shared-patterns/stories/CAP-003-E1-S3.md`

**Branch**: `usr/alvaro-de-jodra/CAP-003-tasks`
**Date**: 2026-11-07

## Summary

Vendors the overlay and feedback family of the `ui-components` layer into `web/src/components/ui/` (component design 2.1, 3, 7, 10; DAC-E1-14): `dialog.tsx` (`confirm`, on Radix AlertDialog), `command.tsx` (cmdk inside Radix Dialog: `Command`, `CommandDialog`, `CommandInput`, `CommandList`, `CommandEmpty`, `CommandGroup`, `CommandItem`, `CommandSeparator`, `CommandLoading`), `toast.tsx` (`Toaster` and `toast` with `success`, `warning`, `error`, on `sonner`), `progress.tsx` (`determinate`, `indeterminate`, on Radix Progress) and the bespoke `stepper.tsx` (`vertical`, a native `ol`), each with a contract test. Each component carries its focus and announcement contract so every later screen that confirms, searches, notifies or shows progress does it the same accessible way (AC-25): the confirmation puts **Cancel** first and focuses it, traps focus and returns it to the opener; the palette is labelled *Search FactorFlow*, loops and restores focus; `error` and `warning` toasts persist, never take focus and are announced politely; the progress bar is a `progressbar` labelled by its visible text with no `aria-valuenow` while indeterminate; the current step carries `aria-current="step"`. `package.json` gains exactly `@radix-ui/react-dialog`, `@radix-ui/react-alert-dialog`, `@radix-ui/react-progress`, `cmdk` and `sonner`, each with its licence (DEC-0205, DEC-0215), and every class is token-backed, the `command` dialog's 560 px width being the one literal the AC-26 scan allows (DAC-E1-S3-5). `dialog` `destructive` is not vendored (DAC-E1-15).

## Notes

### Resolved Conflicts

1. **Toast politeness.** The toast design-system spec section 5 gives `error` and `warning` an `alert` role in an assertive region; story DAC-E1-S3-2 and TC-COMP-013 require them "announced politely", and UX design 0.6 and component design 10 say every polled change announces politely. Story ACs govern design-system prose: no toast is assertive (T014 exposes no `important` option and no `info` variant); persistence and never taking focus are common to both.
2. **`role="dialog"` on Radix AlertDialog.** Epic DAC-E1-14, component design 2.1 and the story name Radix AlertDialog, which renders `role="alertdialog"`; DAC-E1-S3-1, TC-COMP-012 and the dialog spec section 5 require `role="dialog"` for `confirm` (`alertdialog` is for `destructive` and `real-money`). Both hold: AlertDialog supplies the Cancel-first focus and the trap, and the content overrides the role (T012). Radix sets no `aria-modal` (it hides siblings instead), so T012 adds `aria-modal="true"` explicitly.
3. **Overlay click on `confirm`.** TC-COMP-012's edge case says "Click outside: focus stays trapped (Radix AlertDialog)"; the dialog spec section 4 (normative design-system prose the component design adopts: "Every variant used is one its spec defines", design 3) says a click on the overlay closes `standard` and `confirm`. Design prose governs the test specification: the overlay closes `confirm` (focus returning to the opener), except while `pending`, when nothing closes it (dialog spec section 4 "Never close the dialog before the result is known"; CAP-002's `screens/research/dialog-frame.tsx` and DEC-0259 are the local precedent for both). Radix AlertDialog blocks outside-pointer dismissal, so the overlay closes through its own `onClick` (T012). TC-COMP-012's edge case is sharpened accordingly in T002.
4. **Indeterminate animation.** The progress spec section 4 animates `indeterminate` by sliding the indicator. A sliding animation needs keyframes in `tailwind.config.js`, which epic DAC-E1-11 limits to the listed keys and which is outside this story's file list; the indeterminate bar therefore draws the static `--pattern-indeterminate` hatch the spec already prescribes for reduced motion, with `motion-safe:animate-pulse` (a Tailwind core animation) as its motion. The epic AC governs the spec's animation detail.
5. **Shipped literals and spec pixel values vs AC-26.** shadcn/ui's sources carry literal-backed classes (`max-w-lg`, `max-h-[300px]`, `h-11`, `py-1.5`, `rounded-md`, `shadow-lg`, `bg-black/80`) and the stepper spec gives a 3 px current ring and a 28 px vertical dot. Capability AC-26, epic DAC-E1-12 and component design 3 govern: classes become token-backed (Phase 3 preamble), the 28 px dot comes from the caller's `LAYOUT.markerSize` (component design 3 places the 28 px in `web/src/app/layout.ts`, and design 2.2 forbids this layer importing it), and the three values no token fixes are DEC-0305.
6. **`command`'s dialog.** shadcn/ui's `CommandDialog` imports `Dialog` and `DialogContent` from its own `ui/dialog`, which in this inventory is the AlertDialog `confirm` (component design 2.1; register G5). The story's package list includes `@radix-ui/react-dialog` for exactly this composition, so `command.tsx` uses the standard Radix Dialog primitives in place and `dialog.tsx` gains no `standard` export (`standard` is not in the UX design §3 inventory).
7. **`CommandLoading`.** The story lists `CommandLoading`, which shadcn/ui does not ship, and omits `CommandShortcut`, which it does. The story governs: `CommandLoading` wraps cmdk's `Command.Loading` (command spec section 4, *Searching…* while server results load); `CommandShortcut` is not vendored (command-palette, built by CAP-003-E3-S5, uses no shortcut hint and supplies the *Searching…* wording itself).
8. **Origin of the 560 px.** UX design 1.1 and command-palette 10 call 560 px "the cmdk default shadcn/ui ships"; shadcn/ui's Tailwind v3 `DialogContent`, which its `CommandDialog` uses, ships `max-w-lg` instead. The value itself is fixed by DAC-E1-S3-5, UX design 1.1 and component design 3 regardless of origin, so `command.tsx` writes `max-w-[560px]`, the one literal DEC-0296 allows in that file. ### Other Notes

- **Focus restore without a Trigger.** Radix Dialog's modal content, which AlertDialog and `CommandDialog` use, prevents the default close focus and focuses only its own `Trigger`; the palette opens from a keyboard shortcut and the top-bar button, and the confirmations are controlled by their callers, so neither has a Radix `Trigger`. T012 and T013 therefore record the opener in `onOpenAutoFocus` (without preventing it, so Radix still focuses Cancel or the input) and refocus it in `onCloseAutoFocus`. If the opener has left the document (a row removed after *Stop following*), focus falls to the body and the consumer owns where it goes. If the installed Radix version renders `role="alertdialog"` after the spread props (it renders it before them as of 1.1), T002 fails and the coder reports it rather than editing the test.

- **Packages.** `cmdk` 1.x depends on `@radix-ui/react-dialog` itself; the direct dependency is still added because `command.tsx` imports it (story package list). `lucide-react` (`Search`, `Check`) and `@radix-ui/react-slot` (through `Button` `asChild`) come from S1.
