# Tasks: CAP-003-E1-S4 — Vendor data-table: compact, history, virtualised and expandable Variants on TanStack Table

**Story**: `repos/factorflow-v2/FactorFlow-v2/docs/capabilities/CAP-003-app-shell-and-data-health/epics/design-system-components-and-shared-patterns/stories/CAP-003-E1-S4.md`

**Branch**: `usr/alvaro-de-jodra/CAP-003-tasks`
**Date**: 2026-11-06

## Summary

Vendors the design-system `data-table` into `web/src/components/ui/data-table.tsx` on `@tanstack/react-table` (TanStack Table v8, the upstream the data-table spec names), with the four variants component design 2.1 lists: `compact`, `history` (the first cell of every body row is the row header), `virtualised` (windowed rendering over appended keyset pages, so the 3000-stock Coverage and Followed stocks lists keep a bounded DOM, STD-UI-30) and `expandable` (per-row expansion behind a named, `aria-expanded` expander built from CAP-003-E1-S1's `button`). Headers are programmatic column headers whose sort control is a named button and whose sorted column alone carries `aria-sort`; sorting is controlled by the caller because it runs server-side (data-table spec section 4). Every row consumes `--row-height` through the delivered `h-row` key and the window arithmetic measures that rendered height instead of holding a pixel constant, so the component carries no literal outside the theme (AC-26, DAC-E1-12). No virtualisation library is added (DEC-0215): the windowing is hand-written, and because CAP-001's `coverage-table.tsx` turned out to hold no windowing to re-implement, it follows the one delivered hand-built windowing in the product, CAP-002's `web/src/screens/research/results-window.ts` (Open Gap 1). `package.json` gains only `@tanstack/react-table`, MIT, verified against its `LICENSE`. The delivered `coverage-table.tsx` is not touched; CAP-003-E7-S2 and CAP-003-E7-S3 later move Coverage and Followed stocks onto the `virtualised` variant, and CAP-003-E7-S4, CAP-003-E7-S5 and CAP-003-E6-S4 adopt `history`, `expandable` and `compact`.

## Notes

### Resolved Conflicts

1. **Row height of the `compact` variant.** The data-table design spec section 2 describes `compact` as "reduced row height", and ux-design's Data health token usage (line 948) names "`--row-height-compact` through the `compact` variant". Story DAC-E1-S4-3 requires the component's row height to resolve to `--row-height`; ux-design 0.7 (lines 301-304) and component design 3 ("density inherited: `--row-height` resolves to `--row-height-comfortable`") say every table consumes `--row-height`; epic DAC-E1-11 adds no Tailwind key beyond its list, and the delivered config maps only `height.row`. Story acceptance criteria govern design prose: every variant, `compact` included, uses `h-row` (T009, asserted by T002).
2. **Client-side sorting in shadcn/ui's data-table recipe vs the spec.** shadcn/ui's TanStack recipe sorts the loaded rows with `getSortedRowModel`; the data-table design spec section 4 and section 8 require sorting server-side across the full set ("never sort only the current page"). The design-system spec is the normative contract (design-system README; component design 2.1); the recipe is illustrative. The component uses `manualSorting: true` with caller-controlled `sorting` / `onSortingChange` and never reorders rows itself (T009).
3. **"History" first-cell semantics for Recent downloads.** Component design data-health-ui and ux-design describe Recent downloads as "`compact` with `history` semantics" while design 2.1 lists `compact` and `history` as separate variants and DAC-E1-S4-2 ties the row header to `history`. Both hold: `rowHeader` is always on for `history`, and any other variant turns it on with the `rowHeader` prop (DEC-0307), so Recent downloads renders `compact` with a row header and the `history` assertion of TC-COMP-018 stands.
