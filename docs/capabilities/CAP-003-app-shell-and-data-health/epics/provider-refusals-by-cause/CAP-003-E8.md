# Provider Refusals Reported by Cause

**EPIC ID:** CAP-003-E8
**Capability:** CAP-003
**Summary:** When the market data provider refuses a download, tell the owner why and what fixes it. On 2026-11-07 production recorded a plan not entitled to company financials and a rate limit alike as `[unavailable] … The provider failed 3 consecutive attempts.`, so *Needs fixing* offered a download for a refusal no download can fix (follow-up F1 of CAP-002's release; capability §1, §2 *Provider refusals reported by cause*). This EPIC delivers system design §3.6 end to end, from the provider request to the fix the owner reads. In the ingestion container, `massive-client` recognises a plan refusal (`403` "not entitled") and sends it once, and recognises a `429` as throttling rather than a failed attempt; `rate-limit-governor` waits throttling out against one wait budget per stock, checked before each wait, and names it `ProviderRateLimited` when the budget is spent; `acquisition-runner` starts each stock's budget at its heartbeat checkpoint and records both refusals as `failed` under their own reason kinds, `not_entitled` and `rate_limited`, while the download goes on and finishes with its recorded outcome. In the interface, `data-health-reader` reads each failure's cause from the kind its stored reason leads with and stops counting a plan refusal as retryable, `data-health-api` and `owner-shell`'s `ProblemPage` type carry that cause to the browser, and `ui-components`' one `failureRecovery` mapping gives *Needs fixing* and the download detail the same fix per cause: the provider plan for a plan refusal, never a download; a later download, with the request rate to check, for a rate limit. No outcome value, column, migration, endpoint or provider request is added, and CAP-001's approved designs are not reopened (AGT-SCOPE-002).
**Actors:** Owner-operator; Massive REST API (external, answering `403` "not entitled" and `429`); `massive-client` (`classify_for_governor`, `classify_error_body`, `compose_failure_reason`, `start_instrument()`); `rate-limit-governor` (`start_throttle_budget()`, `execute`); `acquisition-runner` (top-of-stock checkpoint, `classify_provider_error`); `run-journal` (`heartbeat`, `cancellation_requested`, `finalise`, unchanged); `market-data-store` (`run_instrument_result.reason`, unchanged schema); `data-health-reader` (`cause_of`, `_retryable`); `data-health-api` (`FailureResponse.cause`); `owner-shell` (`shell-types.ts`, `shell-client.ts`); `ui-components` (`failure-recovery.ts`); `data-health-ui` (*Needs fixing* rows); `owner-web-app` (download detail, reading the delivered `GET /api/acquisition-runs/{id}` unchanged).

## Goals

- Send a request the owner's plan is not entitled to once, never retried, and record it per data type as `failed` with the reason kind `not_entitled`, while the plan's other data types and the remaining stocks are still downloaded.
- Treat a `429` as throttling that never costs an attempt, wait it out against one wait budget per stock that is checked before each wait and never crossed, and past it record the data type as `failed` with the reason kind `rate_limited`.
- Start each stock's throttle budget at the checkpoint where the runner refreshes its heartbeat, so a download waiting out a rate limit stays inside the delivered staleness window and finishes with its recorded outcome, never reclaimed as abandoned.
- Read each failure's cause from the kind its stored reason leads with, keep a plan refusal in the problem set and every count, and stop it alone making a row retryable.
- Give *Needs fixing* and the download detail one mapping from a failure's outcome and cause to its fix, with UX design v2's words, so a plan refusal names the provider plan and never offers a download and a rate limit offers a later download with what to check.
- Prove the provider side through the real SDK and urllib3 path and the default timing set, never a patched client raising what the real SDK cannot.

## Non-Functional Requirements

- **Timing and liveness** (AC-30; system design §3.6 notes 3, 4): one throttle wait budget per stock, `FACTORFLOW_MASSIVE_MAX_THROTTLE_WAIT_SECONDS` (300 s); the throttle sleeps between two `start_throttle_budget()` calls total at most 300 s, jitter included; under persistent throttling every interval between two heartbeats, and between the last heartbeat and `finalise`, stays below `FACTORFLOW_RUN_STALE_AFTER_SECONDS` (900 s); no timing value, default or invariant changes (`runtime-config` §2.2a invariant 2, `(3 × 30 × 4) + 300 = 660 < 900`).
- **Provider load** (AC-29; `massive-client` §5): a plan refusal costs one request per refused data type per stock instead of `max_attempts` (3). A throttled stock may take up to one budget longer; under throttling that persists for a whole download that is up to one budget per followed stock (about 250 hours at 3,000 stocks), a consequence system design open question 14 leaves with the owner. Cancelling still takes effect after the current stock.
- **Read cost** (AC-28 unchanged): the cause is read in Python from the reason each problem row already fetches; no query, index or SQL text changes (`data-health-reader` §2.4), so E2's volume bound on `GET /api/data-health` is untouched.
- **Security** (AGT-PROHIB-003; SEC-INP-001; SEC-DAT-001; CAP-001 AC-13): no provider free text in a stored reason, since `not_entitled`'s description is fixed and never passed to `redact` and `rate_limited`'s is the governor's own text; the credential's value never appears in a reason; `_safe_fields` still reads only `status`, `message`, `error` and `request_id`; the cause is matched only against the closed table of six kinds at the start of the reason, so no provider text can choose it; reasons render as text. The `429` rule matches only urllib3's `429` `ResponseError`, the SDK's `retries=0` and the redirect refusal are kept, so the redirect and proxy controls of DEC-0038, DEC-0041 and DEC-0042 are untouched. All data is Internal; no PII.
- **Supply chain** (SEC-DEP-001, SEC-DEP-003): no new package; `urllib3` is already imported by `client.py` and locked at 2.7.0.
- **Data and rollback** (OPS-MIG-003; system design §4.4, constraint 17 (d)): no persistent-schema change; rollback is a redeploy of the previous image with no data step, and rows written with the new kinds stay readable as reason text.
- **Upgrade disclosure** (constraint 17): the change upgrades release 0.2.0 (`factorflow:0.2.0-829c9e1`) and changes observable behaviour: throttled stocks wait instead of failing within seconds, a plan refusal costs one request, and two new reason kinds appear while older rows keep `[unavailable]`.
- **Design system** (AC-26): each new fix is one `--text-xs` line under its failure, like the delivered fix line, with no new component, variant or token and no literal outside the theme.
- **Test fidelity** (constraint 16 (e)): every `429` and `403` row runs through `tests/unit/massive_transport_fakes.py` with production `MassiveSettings` and one `FakeClock` passed as both `monotonic` and `now`, so boundary waits are exact.

## EPIC Acceptance Criteria

### From Capability

- [AC-29] When the provider refuses a data type because the owner's plan is not entitled to it, the product MUST send that request once and MUST record the refusal under its own reason; its *Needs fixing* row MUST name the provider plan as the fix and MUST NOT offer a download as its fix.
- [AC-30] A provider rate limit MUST NOT count as a failed attempt; when it persists past the wait budget for one stock, the product MUST record it under its own rate-limit reason, and the download MUST still finish with its recorded outcome, never abandoned.
- [AC-13] Each *Needs fixing* row MUST offer the recovery action that applies. This EPIC delivers the recovery for a failure whose cause is a plan refusal or a rate limit; every other recovery is E6's.
- [AC-14] A stock the provider does not recognise MUST keep stopping following it and following a different symbol as its fixes, and MUST NOT be offered a download, whatever cause its reason carries.
- [AC-16] A plan refusal and a rate limit MUST stay in the one problem set the *Needs fixing* header and the Data health rail chip count.
- [AC-17] The download detail's fix by cause MUST read the delivered `GET /api/acquisition-runs/{id}` response unchanged, and every action on that screen MUST keep its outcome.
- [AC-26] The new fix lines MUST be built from `ui-components` and consume theme tokens only.

## Open Questions

- **Should an unrecognised provider refusal also be sent once?** System design open question 12: DAC-E8-3 keeps the delivered retry and pins it. A yes is a new capability criterion. *Owner: capability owner. Blocks: nothing in this EPIC.*
- **Persistent throttling now costs up to one budget per stock** (system design open question 14), about 250 hours over 3,000 stocks if the provider throttles every request; short-circuiting a refused endpoint or a run-level bound is not designed. *Owner: capability owner. Blocks: nothing in AC-29 or AC-30.*
- **The staleness derivation's attempt term predates this change** (system design open question 15): only the throttle term is touched, and it stays one budget per stock. *Owner: capability owner. Blocks: nothing here.*
- **The two cross-capability rules are not yet decision records** (system design open question 16): the per-stock throttle budget in a delivered component, and the stored reason's leading kind as a read contract between `massive-client` and `data-health-reader`. *Owner: capability owner. Blocks: nothing.*
- **The production `403` body was not captured** (system design assumption 9; `massive-client` §14 question 3), so DAC-E8-1 reads both text fields and `request_id` when present. *Owner: capability owner. Blocks: nothing.*
- **The download detail's summary card keeps offering a download** when every failure in it is a plan refusal, because the run-detail response carries counts, not causes (`owner-web-app` §14 question 3). *Owner: capability owner. Blocks: nothing in AC-29.*
- **Charging the retry's permit wait to the budget** is `rate-limit-governor` §2.3's reading of "every throttle wait"; DAC-E8-5 follows it. *Owner: capability owner. Blocks: nothing.*
