# One Throttle Wait Budget per Stock, Checked Before Each Wait, and ProviderRateLimited

## User Story
As an owner-operator, I want the time spent waiting out a rate limit bounded per stock and checked before each wait, and named as a rate limit when it is spent, so that a throttled download stays inside its staleness window and its failures say why.

## Description
Changes the governor's throttle path (rate-limit-governor CAP-003 §2.1 to §2.3; system design §3.6 note 3, §4.2 *Per-stock throttle budget*, constraint 16 (b)) and adds the error it raises (massive-client CAP-003 §2.4, §2.5).

In `src/factorflow/ingestion/massive/errors.py`: `ProviderRateLimited(ProviderUnavailable)` with the design's docstring, its `_ERROR_KIND_BY_TYPE` row `rate_limited` (variable segment redacted then bounded, as delivered), `__all__`; `src/factorflow/ingestion/massive/__init__.py` re-exports it. The lookup is by exact class, so `ProviderRateLimited` composes `rate_limited`, never `unavailable`.

In `src/factorflow/ingestion/rate_limit.py`: `self._throttle_spent = 0.0` set at construction; `start_throttle_budget()` sets it to zero; `execute`'s `THROTTLED` branch computes the delay (stated delay, or the boundary wait with jitter, as delivered), raises `ProviderRateLimited(_THROTTLE_BUDGET_SPENT_MESSAGE) from exc` without sleeping when `self._throttle_spent + delay > max_throttle_wait_seconds`, otherwise records `throttled_at = monotonic()` and sleeps; after the next permit is acquired the elapsed `monotonic() - throttled_at` is charged to `_throttle_spent` (the sleep plus any permit wait the retry needs, §2.3). The `RETRYABLE` attempt bound, backoff, the `FATAL` re-raise, pacing and the stated-delay path are unchanged; attempt exhaustion still raises plain `ProviderUnavailable` with the delivered message. Docstrings say the budget is per stock.

Nothing calls `start_throttle_budget()` yet: `MassiveClient.start_instrument()` is CAP-003-E8-S3's and the runner's per-stock call is CAP-003-E8-S4's. Until then the budget starts at zero at construction and spans the client's life, the conservative reading of §3. Production behaviour does not change with this story alone, because a `429` still reaches the governor as `RETRYABLE` until CAP-003-E8-S3 classifies it `THROTTLED`.

## Technical Details

### API Contract
- No HTTP surface. In process: `RateLimitGovernor.start_throttle_budget() -> None` (new); `RateLimitGovernor.execute(send, classify, stated_delay_seconds=None)` may now raise `ProviderRateLimited` (rate-limit-governor §11).

### Data Changes
- None. `FACTORFLOW_MASSIVE_MAX_THROTTLE_WAIT_SECONDS` keeps its default (300 s) and now bounds one stock; no new variable, default or invariant (`runtime-config` §2.2a invariant 2, `(3 × 30 × 4) + 300 = 660 < 900`, untouched).

### Implementation
- Python 3.12, pytest without a container or network, `tests/unit/governor_fakes.py` (`FakeClock`, `FakeSleeper`, `FlakySender`, `SequenceJitter`) (tech stack v7).
- Files: `src/factorflow/ingestion/rate_limit.py`, `src/factorflow/ingestion/massive/errors.py`, `src/factorflow/ingestion/massive/__init__.py`; `tests/unit/test_governor_retry.py` (two delivered expectations changed, rows added), `tests/unit/test_massive_failure_reasons.py`, `tests/unit/test_massive_error_classification.py` (subclass row), `tests/unit/test_outcomes.py`.
- One float of instance state, no lock: one governor per client and one runner per process (§3). Rollback: redeploy the previous image; the governor holds no persistent state.

### Validation

### Dependencies
