# failureRecovery: the One Mapping from a Failure's Outcome and Cause to Its Fix

## User Story
As an owner-operator, I want every screen that shows a failed download to choose its fix from one place, by the failure's cause, so that *Needs fixing* and the download detail never disagree and a plan refusal is never offered a download.

## Description
Creates `web/src/components/patterns/failure-recovery.ts` and `failure-recovery.test.ts` (ui-components v2 §2.7a, §7, §8 criteria 8, 9; system design §3.6 notes 6, 7). The module exports, as §2.7a gives them: `FAILURE_CAUSES` (the six kinds, `as const`), `FailureCause`, `failureCause(reason: string | null): FailureCause | null` (the anchored `^\[(<six kinds>)\] ` rule, the same rule `data-health-reader` applies on the server), `PLAN_FIX_TEXT`, `RATE_LIMIT_FIX_TEXT`, the `FailureFix` union (`download_again`, `stop_following`, `provider_plan` with `text`, `download_later` with `text`), `failureRecovery(outcome, cause)` and `offersDownload(fix)`. It renders nothing and imports nothing from `web/src/app/`, so `owner-shell`'s type-only import of `FailureCause` (CAP-003-E8-S8) makes no runtime cycle.

The two existing fixes keep each screen's own words (`download_again`, `stop_following` carry no text); only the two new fixes' words live here, word for word UX design v2 §1.4 and §1.8, with `FACTORFLOW_MASSIVE_REQUESTS_PER_MINUTE` as plain text (ui-components §2.7a). The screens that consume this module are CAP-003-E8-S9 (*Needs fixing*) and CAP-003-E8-S10 (the download detail).

Source: component-design-ui-components.md 1, 2.1, 2.7a, 7 (*Fix by cause*, *Agrees with `retryable`*, *Cause from the reason*, *Plan fix offers no download*, *Fix words*), 8 criteria 8, 9, 14 question 3; UX design v2 §1.4, §1.8; epic CAP-003-E8 DAC-E8-15, DAC-E8-16.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC
- [AC-29] A plan refusal's fix MUST name the provider plan and MUST NOT offer a download.
- [AC-30] A rate limit's fix MUST be a later download.
- [AC-14] A stock the provider does not recognise MUST keep its fixes and MUST NOT be offered a download, whatever cause its reason carries.
- [DAC-E8-15] `web/src/components/patterns/failure-recovery.ts` MUST hold the only mapping from a failure to its fix: `failureCause(reason)` with the reader's anchored rule; `failureRecovery(outcome, cause)` returning `stop_following` for every `not_found` whatever its cause, `provider_plan` with `PLAN_FIX_TEXT` for `failed` and `not_entitled`, `download_later` with `RATE_LIMIT_FIX_TEXT` for `failed` and `rate_limited`, and `download_again` for `failed` with any other cause or `null`; over every outcome and every cause including `null`, `offersDownload(failureRecovery(o, c))` MUST equal `o === "failed" && c !== "not_entitled"`, the server's `retryable` rule. (traces to: AC-29, AC-30, AC-14)
- [DAC-E8-16] `PLAN_FIX_TEXT` MUST equal *Your Massive plan doesn't include this data, so downloading again won't help. Add it to your plan with Massive; the next download after that gets it.* and `RATE_LIMIT_FIX_TEXT` MUST equal *Download again later; data already stored is never duplicated or overwritten. If this keeps happening, check that FACTORFLOW_MASSIVE_REQUESTS_PER_MINUTE is no higher than your Massive plan's request limit; restart FactorFlow after changing it.*, the variable name as plain text; `PLAN_FIX_TEXT` MUST contain *plan* and neither *Download again* nor *Download now*. (traces to: AC-29, AC-30)
