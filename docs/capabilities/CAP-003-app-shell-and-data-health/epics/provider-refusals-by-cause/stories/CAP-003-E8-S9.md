# Needs Fixing States Each Failure's Fix by Its Cause

## User Story
As an owner-operator, I want *Needs fixing* to tell me, per failure, whether my Massive plan or a later download fixes it, so that I am never offered a download for a refusal no download can fix.

## Description
Routes the *Needs fixing* row's fix through `ui-components`' `failureRecovery` (data-health-ui v2 §2.5, §3, §10 *Version 2 copy*; UX design v2 §1.4; system design §3.4 note 9, §3.6 note 7). In `web/src/screens/data-health/problem-row.tsx` (CAP-003-E6-S3's file), each failure's fix is `failureRecovery(failure.outcome, failure.cause)`, never a mapping of this screen's own:

- `download_again`: E6-S3's *Download again to retry; data already stored is never duplicated or overwritten.* with no per-row control, unchanged;
- `provider_plan` (cause `not_entitled`): `fix.text` (`PLAN_FIX_TEXT`) as one `--text-xs` line, with no per-row control and no download offered;
- `download_later` (cause `rate_limited`): `fix.text` (`RATE_LIMIT_FIX_TEXT`) as one `--text-xs` line, with no per-row control, the header's **Download now** being the action;
- `stop_following` (outcome `not_found`): E6-S3's **Stop following**, **Follow a different symbol** and their sentence, unchanged.

For `provider_plan` and `download_later` the what-failed line ends at *{reason}*: it reads *Downloading {data type} failed: {reason}* without *, {attempts} attempts*. For every other *Failed* failure it keeps E6-S3's *Downloading {data type} failed: {reason}, {attempts} attempts*. The header's **Download now** rule (shown only when a loaded row is `retryable`) is E6-S3's and is not changed: the server's `retryable` already excludes plan refusals (CAP-003-E8-S6, E8-S7), and this story proves the resulting behaviour.

**Ownership (backlog review v5 FINDING-1).** CAP-003-E6-S3 v2 renders the `download_again` and `stop_following` fixes and the header rule, and renders the *Download again* line for every *Failed* failure, because it lands before the failure type carries `cause`. This story owns DAC-E6-8 v3's two exceptions, which it hands to DAC-E8-17: it replaces E6-S3's outcome-only fix choice with `failureRecovery` and adds rows to E6-S3's `problem-row.test.tsx` and `needs-fixing.test.tsx`. E6-S3's existing assertions keep passing, because E6-S3 v2's fixtures use `failed` reasons beginning `[unavailable] ` (or none) and assert the `attempts` value they serve. No copy for the two new fixes is added to `copy.ts`.

**Attempt counts (backlog review v5 FINDING-4).** The delivered writer never records `attempts`, so the column reads its default, 1 (`0004_runs.sql` line 41; specification review v5 FINDING-29). This story adds no reliance on it: it removes the count from the two new causes' lines and leaves the other lines showing the served value as E6-S3 renders it; tests assert the value their fixture serves, never 3.
