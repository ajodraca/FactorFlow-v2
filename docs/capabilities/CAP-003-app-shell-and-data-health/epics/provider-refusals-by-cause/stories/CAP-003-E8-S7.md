# data-health-api Serves Each Failure's Cause

## User Story
As an owner-operator, I want each failure's cause served with the problem rows, so that the interface can choose a failure's fix by its cause without reading provider text.

## Description
Adds `cause` to `data-health-api`'s failure model (data-health-api v2 §2.4; system design §4.2 `GET /api/data-health`). In `src/factorflow/api/data_health_models.py` (CAP-003-E2-S4's file): the `FailureCause` `Literal` of the six kinds and `FailureResponse.cause: FailureCause | None`, a required field placed after `outcome` as §2.4 shows it, always serialised and `null` when the reader's `cause` is `None`; `from_reader` passes the reader's `cause` through. `retryable` is already the reader's value passed through, so the new rule (CAP-003-E8-S6) reaches the response with no change here. No route, parameter, status code or other field changes, on `GET /api/data-health` or `GET /api/data-health/problems`.

**Ownership (backlog review v5 FINDING-1).** CAP-003-E2-S4 v2 builds the models without each failure's `cause`, as its refined DAC-E2-S4-1 states, because E2-S1's reader carries none. This story owns `FailureCause` and `FailureResponse.cause` and extends the DAC-E2-S4-1 assertion that every §4.2 field is present to `failures[].cause`. It adds a row to `tests/integration/test_api_data_health.py`, which CAP-003-E2-S6 creates.

**Fixtures this story changes (backlog review v6 FINDING-11).** With `cause` required, every `FailureResponse` constructed directly in CAP-003-E2-S4's `tests/unit/test_api_data_health_models.py` fails Pydantic validation until it carries `cause`, and every expected body that spells a failure's fields in full, in E2-S4's `tests/unit/test_api_data_health_routes.py` or CAP-003-E2-S6's `tests/integration/test_api_data_health.py`, lacks the now-serialised `"cause"`. This story adds `cause` to each, `None` (`null`) unless the test exercises a cause, and changes no other assertion; the expected files are confirmed by `uv run pytest` when the story is planned. CAP-003-E2-S5's no-secrets test needs nothing here: its `stub_reader_functions` builds reader values, which CAP-003-E8-S6 already gave `cause`, and it asserts only the status and the key's absence.

Source: component-design-data-health-api.md 1, 2.4 (*`cause`*), 7 (*Cause serialised*, *Plan refusal through the route*), 8 criterion 7; system design §4.2; epic CAP-003-E8 DAC-E8-13.

## Technical Details

### API Contract
- `GET /api/data-health` and `GET /api/data-health/problems`: unchanged except that each `problems.rows[].failures[]` (and each `rows[].failures[]`) gains `"cause": "not_found" | "credential_rejected" | "unavailable" | "contract_violation" | "not_entitled" | "rate_limited" | null`, always present. `retryable` is unchanged in shape; its value follows the reader's rule.
- Auth: none; loopback bind and the delivered Host and Origin middleware (DEC-0208). Errors: unchanged (`422 validation_error`, `400 host_not_allowed`, `500 internal_error`).
