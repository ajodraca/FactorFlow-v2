# The Runner Starts Each Stock's Budget at Its Heartbeat, Proven End to End at the Default Timing Set

## User Story
As an owner-operator, I want each stock's throttle budget to start where its heartbeat is refreshed, and both refusals proven through the real runner, so that a download waiting out a rate limit finishes with its recorded outcome and is never reclaimed as abandoned.

## Description
Adds the stock boundary to `acquisition-runner` and proves system design §3.6 end to end through the runner (acquisition-runner CAP-003 §2.2, §2.3, §6, §7; system design §3.6 notes 4, 5, §4.2 *Stock boundary*, constraints 16 (e), 17). In `src/factorflow/ingestion/runner.py`, inside `execute_claimed`'s loop, after the delivered `heartbeat` and `cancellation_requested` checks and before the symbol lookup, one call `self._client.start_instrument()` with the design's comment. So a stock that is never fetched starts no budget, and all four of a stock's data types share one budget.

Writes `tests/integration/test_runner_provider_refusals.py` (pytest, `testcontainers[postgres]`, marked `postgres`), the end-to-end proof of both refusals with the real `MassiveClient` and governor over `tests/unit/massive_transport_fakes.py`, and the one test at the default timing set that system design constraint 16 (e) requires.

**Upgrade notes (DAC-E8-19; backlog review v5 FINDING-3).** The repository's operator-facing upgrade documentation is the `README.md` section *Deploying and operating FactorFlow*, whose *Upgrade, backup and rollback* subsection is the procedure; `docs/releases/` holds release manifests that `$release-readiness` writes, which no story authors. This story adds one subsection, `### Upgrading from 0.2.0: provider refusals reported by cause`, immediately after *Upgrade, backup and rollback*, written once for the three ingestion changes (CAP-003-E8-S1 to S4) because this is the story that completes them. The changes' design upgrade sections (`massive-client` §6, `rate-limit-governor` §6, `acquisition-runner` §6) already exist and are not edited.

`journal.py`, `reclaim.py`, `writer.py`, `plan.py`, `ingestion_main.py` and every timing value are untouched. The `ProviderNotEntitled` outcome mapping landed with CAP-003-E8-S1 and `ProviderRateLimited`'s with CAP-003-E8-S2, so `outcomes.py` is not edited here.

Source: component-design-acquisition-runner.md 2.1 to 2.3, 3, 4, 6, 7, 8; component-design-massive-client.md 6, 7 (harness); component-design-rate-limit-governor.md 2.4, 6, 8 criterion 6; system design §3.6 notes 4, 5, constraints 16 (d), (e), 17 (a) to (d), open questions 13 (answered), 14; epic CAP-003-E8 DAC-E8-7 to DAC-E8-10, DAC-E8-19, DAC-E8-20.

## Technical Details

### API Contract
- No HTTP surface. Consumed in process: `MassiveClient.start_instrument()` (CAP-003-E8-S3), `MassiveClient.fetch_*` raising `ProviderNotEntitled` or `ProviderRateLimited`, `run-journal` `heartbeat`, `cancellation_requested`, `finalise` unchanged (acquisition-runner §11).

### Data Changes
- None: no outcome value, column, index, migration or timing value (constraint 16 (d); `runtime-config` §2.2a invariant 2, `660 < 900`, untouched).

### Implementation
- Python 3.12, pytest with `testcontainers[postgres]` (marker `postgres`), `tests/unit/massive_transport_fakes.py` and `tests/unit/governor_fakes.py` (tech stack v7).
- Files: `src/factorflow/ingestion/runner.py` (one call and its comment); `tests/integration/test_runner_provider_refusals.py` (new); `README.md` (one subsection).
- Performance: one in-process call per stock, no query added; a throttled stock may take up to one budget (300 s) longer (system design open question 14, the owner's).
- Rollback: redeploy the previous image; rows with the new kinds stay readable, and an older runner resumes against them (acquisition-runner §6).

### Validation
`uv run pytest` (or `uv run pytest -m 'not postgres'` when no container runtime is available, reported as an exclusion; the rows of DAC-E8-S4-2 to DAC-E8-S4-4 are `postgres` rows and must run before review), `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src` (tech stack v7 validation commands).

### Dependencies
- **CAP-003-E8-S3**, `MassiveClient.start_instrument()` and the `429` classification the persistent-throttle rows need.
- **CAP-003-E8-S2**, the per-stock budget and `ProviderRateLimited`, which DAC-E8-S4-3 and DAC-E8-S4-4 bound and record.
- **CAP-003-E8-S1**, `ProviderNotEntitled`, its `[not_entitled]` reason and its outcome mapping, which DAC-E8-S4-2 records.
- No E1 to E7 story (owner decision, Alvaro de Jodra, 2026-11-07: provider side first, recorded in `backlog.md` *Sequencing*). This story completes the provider side.
- **Lands and releases with CAP-003-E8-S3** (owner decision, Alvaro de Jodra, 2026-11-08; backlog review v6 FINDING-13): one pull request or, if merged separately, one release, with no release built from a commit that holds E8-S3 without this story. Without this story's per-stock `start_instrument()` call, E8-S3's throttle budget would span the ingestion process, because the client is cached per credential across downloads, and once spent every later throttled request would fail after one send (CAP-003-E8-S3).
