# Tasks: CAP-002-E1-S5 — Universe from a Filter Result: Snapshot with Provenance

**Story**: `docs/capabilities/CAP-002-universe-and-factor-classification/epics/universe-definition-and-maintenance/stories/CAP-002-E1-S5.md`
**Component**: `FactorFlow-v2` (module `universe-service`, filter-snapshot write)
**Branch**: `usr/alvaro-de-jodra/CAP-002-E1-tasks`
**Date**: 2026-10-17

## Summary

Add `create_from_filter(conn, name, set_id, thresholds) -> Universe` to `src/factorflow/universes/service.py`, the file CAP-002-E1-S3 creates and S4 extends. Inside `with conn.transaction():` and after `pg_advisory_xact_lock(UNIVERSE_WRITE_LOCK_KEY)`, it trims the name, reads the current complete set through the reader's `current_set(conn)` and raises `ClassificationSetChanged(set_id, current_set_id_or_None)` unless that set is the named one, calls the reader's `evaluate_filter(conn, set_id, thresholds)` with the whole `Thresholds` object (twelve bounds, `hide_incomplete`, symbol prefix) and raises `EmptyUniverse` when it returns nothing, refuses a name held by an active universe, then appends one `created` event carrying `filter_provenance = {set_id, classification_date, thresholds (only the bounds set), hide_incomplete (always), symbol (null without a search)}` followed by one `member_added` per matching instrument in symbol order, and returns the replayed `Universe`. The `Origin` read back by `get_universe` (S2's `origin_from_provenance`) therefore equals the provenance, and later classification sets cannot move the members because membership is replayed from events only. The function applies no filter predicate of its own and defines no filter type (DEC-0076, DEC-0085). It reuses S3's helpers (`_take_lock`, `_normalise_name`, `_name_in_use`, `_INSERT_UNIVERSE_SQL`, `_INSERT_EVENT_SQL`); S4 is a sibling, not a prerequisite. The API route that maps the exceptions to HTTP is CAP-002-E1-S6.

### Open Gaps

- **JSON representation of the bounds inside `filter_provenance` (PROVISIONAL — awaiting owner confirmation (2026-10-18), no decision record; cross-plan review E1-F16).** Design 2.4 (`80`, `0`) and the research-store section 2.3 example (`80`) show bounds only as integral JSON numbers; the research-store `COMMENT ON COLUMN universe_event.filter_provenance` names no JSON type. No artifact states the JSON type of a non-integral bound, and `psycopg`'s default JSON encoder rejects `Decimal`. Adopted: `_json_default` (T011) writes a `Decimal` equal to its integral value as a JSON integer (`int(value)`) and any other `Decimal` as a JSON number through `float(value)`. S2's `origin_from_provenance` reads every bound back as `Decimal(str(value))` (S2 T006), and S7 renders event bounds through `String(value)`. Derivation: the design's example fixes the JSON-number form for integral bounds. For a non-integral `Decimal`, a float is the only JSON number the standard library's `json.dumps` `default` hook can emit: the hook returns a Python object, so a `Decimal` becomes either a float or a string. Consequence against design 2.4 ("`filter_provenance` is the filter as evaluated"): `classification-api` accepts any finite decimal score bound with no precision cap (classification-api design threshold table, constraint 15). Percentile bounds are uncapped in precision too: any decimal in 0 to 100 (classification-api threshold table; constraint 15). `numeric(9, 6)` is the stored percentile column, not the bound. So a non-integral bound of either kind is stored as the nearest double, and can read back different from the `Decimal` that `evaluate_filter` used when it has more than 15 significant digits or its magnitude is below the smallest normal double (about `2.2E-308`, where doubles lose precision and then underflow to zero) (e.g. `80.00000000000000001` reads back as `80.0`; `1.23456789012345E-320` as `1.2347E-320`; `1E-400` as `0.0`). A non-integral bound of 15 or fewer significant digits whose magnitude is at least about `2.2E-308` reads back numerically equal. Alternatives for the owner: (a) decimal strings (`"0.5"`), which are exact and already read correctly by S2's `Decimal(str(value))` and S7's `String(value)`, but differ from the design's numeric example; (b) an exact JSON number written from `str(Decimal)`, which matches the example and is exact in the stored jsonb. It needs a serialiser other than the `json.dumps` `default` hook. psycopg's default jsonb loader (`json.loads`) still parses a non-integral number as a float, so the read-back through S2's `origin_from_provenance` is exact only if S2's read path also loads with `parse_float=Decimal` (or reads the jsonb as text). In this plan, either alternative changes `_json_default` (T011) and T010(b)'s expected encoding; (b) also changes S2's jsonb load. Confirm the choice before S5 is coded: `universe_event` is append-only, so provenance written under one encoding is never rewritten. T010 pins the representative values. Follow-up: the research-store COMMENT and universe-service 2.4 name the JSON type (number or string) at their next revisions.
