# Tasks: CAP-002-E1-S6 — Universes Router, Request Models, Error Mapping and Mount in the Application

**Story**: `docs/capabilities/CAP-002-universe-and-factor-classification/epics/universe-definition-and-maintenance/stories/CAP-002-E1-S6.md`
**Component**: `FactorFlow-v2` (module `classification-api`, universes half)
**Branch**: `usr/alvaro-de-jodra/CAP-002-E1-tasks`
**Date**: 2026-10-17

## Summary

Expose the universe operations as the nine local HTTP operations of `classification-api` section 11: `GET/POST /api/universes`, `GET/PATCH/DELETE /api/universes/{id}`, `GET /api/universes/{id}/events`, `POST /api/universes/{id}/members`, `DELETE /api/universes/{id}/members/{symbol}`. The story creates `src/factorflow/api/routes/universes.py`, the new `src/factorflow/api/classification_models.py` (request models and the response models the universes routes return) and `src/factorflow/api/classification_bounds.py` (`MAX_UNIVERSE_NAME_LENGTH` without a value, `MIN_COMPARE_SYMBOLS`, `MAX_COMPARE_SYMBOLS`), and edits the one delivered file it owns, `src/factorflow/api/app.py`, by adding the `universes` import and `app.include_router(universes.router)`. Routes validate (bounds before the service is called), delegate to `factorflow.universes.service` and the reader, map the service's typed exceptions to the stable `{"error": {code, message, resource, request_id}}` envelope, and shape responses. They hold no universe rule. Tests build the app through `create_app()` so the mount, the Host and Origin middleware and the request id are exercised (DEC-0086).

  - TC-INT-017, which is not mapped to this story, accepts "422 empty_universe or validation_error" and holds.

- **How `UniverseResponse.members[].factors` and `set` are filled (PROVISIONAL — awaiting owner confirmation (2026-10-17)).** Design 2.7 and system design 4.2 require each member's classification from the current set and a `set` block, but no artifact names the read that supplies them. The plan reads `reader.list_classifications(conn, ListFilters(universe_id=id, limit=MAX_PAGE_SIZE))` page by page to exhaustion (6 queries at 3000 members), takes `set` from the first page, and sets a member's `factors` to `null` when the reader has no row for it (a past `as_of` member since removed, or no set yet). Derivation: the reader already scopes by universe and keeps retired members (DEC-0073, DEC-0079 (b)), so no second classification query exists; `MAX_PAGE_SIZE` is the first capability's bound; `null` is the smaller choice than inventing a placeholder cell. Follow-up: classification-api 2.7 may name the read and the null case.
- **Owner-directed fix (cross-plan review 2026-10-18, E1-F05):** `MemberResponse.name` is `str | None`, taken from the reader's `StockRow.name` for that member and `null` when the reader returns no row for it, the same rule as `factors` (PROVISIONAL — awaiting owner confirmation (2026-10-17)) — classification-api design 2.7 lists `members[].name` but no artifact names its source. Universe-service design 2.3's `Member` and the `membership_as_of.sql` S2 copies verbatim (DEC-0093) carry only `instrument_id`, `symbol`, `lifecycle` and `member_since`, and the `api/` modules hold no SQL (T020), so the reader's `StockRow.name` (reader design 2.3, 2.5), already read for the cells, is the only designed source. The reader returns no row for a member when no complete set exists, when the instrument has no row in the current set, and, on an `as_of` read, for a member removed since that date (its universe scope is today's membership, reader design 2.5); such a member gets `name: null` and `factors: null`. For the last case this falls short of UX design 1.4 and reader design section 14 question 3 (scores for a past membership come from the current set): a since-removed member that is still followed has current-set cells the response does not carry. The alternative, a second unscoped `reader.list_classifications` read on `as_of` requests to fill those members, is left to the owner: it adds a paged read of up to the whole followed roster per as-of view and still leaves the no-set case and since-removed members no longer followed at `null`, so consumers need the null handling either way. Decision: DEC-0097 (amended 2026-10-18). Follow-up: classification-api 2.7 may state the member name source and its null case, or universe-service 2.3 may add `name` to `Member` and `membership_as_of.sql` (an approved-design change, the owner's).
