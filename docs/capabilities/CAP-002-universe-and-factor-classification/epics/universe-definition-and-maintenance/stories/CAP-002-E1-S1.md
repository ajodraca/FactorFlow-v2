# Migration 0005: universe and universe_event Tables

## User Story

As an owner-operator, I want the universe tables created by a forward-only migration with append-only enforcement, so that every later universe write and replay has a store whose history cannot be rewritten.

## Description

Delivers `src/factorflow/db/migrations/0005_universes.sql` creating `universe` and `universe_event` exactly as `component-design-research-store.md` section 2.3 specifies, with the CHECK constraints, the one-`created` and one-`retired` partial unique indexes and the event-log indexes that section names. Module: `research-store` (migration `0005` only; `0006` is CAP-002-E2-S1).

This story also creates the shared guard `tests/unit/test_research_sql_is_append_only.py` (asserting over `universe_event` now; CAP-002-E2-S1 extends it to the three classification tables) and `tests/integration/test_research_migrations_apply.py` (applying `0005` on a store holding `0001` to `0004`; CAP-002-E2-S1 extends it for `0006`).

Source: `component-design-research-store.md` sections 2.3, 2.5, 6, 7.

Packaging (backlog review v4 FINDING-13; DEC-0088): this story also adds `universes/sql/*.sql` to `[tool.setuptools.package-data]` in `pyproject.toml`, so the statements the `universe-service` stories (CAP-002-E1-S2 to E1-S5) load at import ship in the release image, which installs non-editably (`pip install --no-deps .`). It creates the shared guard `tests/unit/test_package_data_ships_sql.py`, asserting that every `sql/` directory under `src/factorflow/` is covered by a package-data glob (CAP-002-E2-S1 extends it for `classification/sql`). CAP-001 made this edit twice after the fact (`4d7473d`, `c8dd959`); `pyproject.toml` is the tenth delivered file CAP-002 edits, beside DEC-0084's nine.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-3] The user MUST be able to hold more than one named universe at a time, and a stock MUST be able to belong to more than one universe.
- [AC-6] Removing a member or retiring a universe MUST retain the dated record of membership, and the user MUST be able to see which stocks belonged to a universe on any past date.
- [DAC-E1-10] No statement issued by this EPIC's components against `universe` or `universe_event` MAY be an `UPDATE` or `DELETE`; a repository test MUST assert it over every `.sql` file and Python source under the tree. (traces to: AC-6)

### Derived

- [DAC-E1-S1-1] Given a store holding `0001` to `0004` with instruments, bars, statements and a run, When the migrator applies `0005`, Then `applied_migrations` records version 5 and no CAP-001 row changes. (traces to: AC-6)
- [DAC-E1-S1-2] Given an `event_type` outside the allowed set, a `member_added` without `instrument_id`, a `created` without `name`, a `renamed` carrying `filter_provenance`, or an untrimmed or empty name, When it is inserted, Then the named CHECK constraint refuses it. (traces to: AC-6)
- [DAC-E1-S1-3] Given a universe that already has a `created` (or a `retired`) event, When a second one is inserted, Then the partial unique index refuses it. (traces to: DAC-E1-7)
- [DAC-E1-S1-4] Given every Python source and `.sql` file under `src/factorflow/`, When the static guard runs, Then no `UPDATE`, `DELETE FROM` or upsert names `universe_event`. (traces to: DAC-E1-10)
- [DAC-E1-S1-5] Given the committed migration text, When `tests/unit/test_migration_0005_matches_design.py` runs, Then every table, column, constraint and index named in research-store section 2.3 is present, following `test_migration_0001_matches_design.py`. (traces to: AC-3)
- [DAC-E1-S1-6] Given a second migrator run after `0005` is applied, When it runs, Then it applies nothing and exits 0. (traces to: AC-6)
- [DAC-E1-S1-7] Given `pyproject.toml` as committed, When `tests/unit/test_package_data_ships_sql.py` runs, Then every `sql/` directory under `src/factorflow/` — `coverage/sql/`, `universes/sql/` and any added later — matches a `[tool.setuptools.package-data]` glob, so a non-editable install carries every `.sql` a module reads at import. (traces to: AC-3)

## Technical Details

### Implementation

- `src/factorflow/db/migrations/0005_universes.sql`: plain SQL, one file one transaction, no `BEGIN` or `COMMIT`, additive only (OPS-MIG-001); no delivered table, column or index is altered.
- `pyproject.toml`: `universes/sql/*.sql` appended to the `factorflow` package-data list; nothing else in the file changes.
- Files: `tests/unit/test_research_sql_is_append_only.py`, `tests/unit/test_package_data_ships_sql.py`, `tests/unit/test_migration_0005_matches_design.py`, `tests/integration/test_research_constraints.py` (universe cases), `tests/integration/test_research_migrations_apply.py` (`0005` cases).
- The delivered `src/factorflow/db/migrations/README.md` file table is not edited by this story unless the checker requires it.

### Data Changes

- New tables `universe` and `universe_event` with indexes as in research-store section 2.3.

### Testing

`pytest` with `testcontainers[postgres]`, marked `postgres`, for constraint and apply tests; the static guards run without a container.

### Validation

`uv run pytest -m postgres`, `uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`.

### Dependencies

- None. This story can start against the approved designs alone.
