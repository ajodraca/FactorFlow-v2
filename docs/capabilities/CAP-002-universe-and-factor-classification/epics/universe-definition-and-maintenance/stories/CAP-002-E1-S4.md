# Universe Maintenance: Rename, Remove a Member and Retire

## User Story

As an owner-operator, I want to rename a universe, remove members and retire the universe without editing the data store, so that a universe can be maintained over time while its history stays intact.

## Description

Adds `rename`, `remove_member` and `retire` to `src/factorflow/universes/service.py`. Each appends one dated event and takes the same write lock. Removing the last member is refused in favour of retirement; a retired universe refuses every further write but stays readable.

Source: `component-design-universe-service.md` sections 2.3, 2.4, 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-4] The user MUST be able to add and remove members, rename a universe and retire a universe without editing the data store directly, and renaming MUST NOT change the universe's history.
- [AC-5] The product MUST refuse to create or save a universe with no members, and MUST refuse to remove a universe's last member.
- [AC-6] Removing a member or retiring a universe MUST retain the dated record of membership, and the user MUST be able to see which stocks belonged to a universe on any past date.
- [DAC-E1-4] Universe names MUST be unique among active universes after trimming; a retired universe's name MAY be reused by a later create or rename. (traces to: AC-4)
- [DAC-E1-7] Removing a universe's sole member MUST be refused with `last_member`, offering retirement as the alternative; retiring MUST append one `retired` event, after which the universe's members and events remain readable and every further write to it is refused with `universe_retired`. (traces to: AC-5, AC-6)
- [DAC-E1-10] No statement issued by this EPIC's components against `universe` or `universe_event` MAY be an `UPDATE` or `DELETE`; a repository test MUST assert it over every `.sql` file and Python source under the tree. (traces to: AC-6)

### Derived

- [DAC-E1-S4-1] Given a rename, When it is applied, Then `universe_id`, every earlier event and every membership are unchanged and exactly one `renamed` event is appended. (traces to: AC-4)
- [DAC-E1-S4-2] Given a universe with one current member, When `remove_member` runs on it, Then `LastMember` is raised offering retirement and nothing is written. (traces to: DAC-E1-7)
- [DAC-E1-S4-3] Given a removed member, When history is read, Then both the `member_added` and `member_removed` events remain and the stock is absent from current members. (traces to: AC-6)
- [DAC-E1-S4-4] Given `retire`, When it succeeds, Then one `retired` event is appended and `get_universe` returns `lifecycle: retired` with members and events readable. (traces to: DAC-E1-7)
- [DAC-E1-S4-5] Given a retired universe, When `retire`, `add_members`, `remove_member` or `rename` is called, Then `UniverseRetired` is raised. (traces to: DAC-E1-7)
- [DAC-E1-S4-6] Given a symbol that is not a current member, When `remove_member` runs, Then a typed not-a-member error is raised and nothing is written. (traces to: AC-4)
- [DAC-E1-S4-7] Given the new SQL statements, When the safety scan runs, Then none is an `UPDATE` or `DELETE` and every one is parameterised. (traces to: DAC-E1-10)

## Technical Details

### Implementation

- Python in `src/factorflow/universes/service.py`; tests in `tests/integration/test_universe_maintenance.py` and the existing `tests/unit/test_universe_sql_safety.py` scan.
- The not-a-member error name is the component design's typed exception for a missing member; no new exception family is introduced beyond section 2.3.

### Data Changes

None.

### Validation

`uv run pytest -m postgres`, `uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`.

### Dependencies

- **CAP-002-E1-S3**, `service.py`, its exceptions, the write lock and `get_universe`, which these functions extend.
