# Universe Members and History Tabs with As-Of View and Remove Dialog

## User Story

As an owner-operator, I want to see a universe's members with their scores, view membership on a past date and read its history, so that I can verify what a universe held and when.

## Description

Delivers `web/src/screens/research/universes/detail/members-tab.tsx`, `history-tab.tsx` and `remove-dialog.tsx`. The members tab is the shared virtualised results table scoped to the universe, with *Members as of* and the Remove action; the history tab lists the universe's events newest first. A retired instrument stays in the table with *Not followed* on every factor. The detail index that mounts these tabs is CAP-002-E1-S9.

Source: `component-design-classification-ui.md` sections 2.5, 2.7, 7; `ux-design.md` section 1.4.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-4] The user MUST be able to add and remove members, rename a universe and retire a universe without editing the data store directly, and renaming MUST NOT change the universe's history.
- [AC-5] The product MUST refuse to create or save a universe with no members, and MUST refuse to remove a universe's last member.
- [AC-6] Removing a member or retiring a universe MUST retain the dated record of membership, and the user MUST be able to see which stocks belonged to a universe on any past date.
- [AC-15] A stock retired from acquisition MUST NOT be classified or counted in any peer set, and MUST be shown in its universes as not classified because it is retired. (membership side: a retired instrument remains a member and is never excluded from a universe for that reason)
- [DAC-E1-7] Removing a universe's sole member MUST be refused with `last_member`, offering retirement as the alternative; retiring MUST append one `retired` event, after which the universe's members and events remain readable and every further write to it is refused with `universe_retired`. (traces to: AC-5, AC-6)
- [DAC-E1-8] Membership as of a given America/Chicago date MUST equal exactly the members implied by every `member_added`/`member_removed` event recorded on or before that date; a date before the universe's `created` event MUST return no members, flagged `as_of_before_creation`, with the creation date. (traces to: AC-6)
- [DAC-E1-9] A symbol acquisition covers but whose `instrument.lifecycle` is `retired` MAY be added or MAY already be a member; it MUST remain a member, replaying with `lifecycle: retired`, rather than being excluded for that reason. (traces to: AC-15)

### Derived

- [DAC-E1-S8-1] Given *View members as of this event* or a typed date, When chosen, Then the table requests `as_of` and the label states it; a malformed date is a field error. (traces to: DAC-E1-8)
- [DAC-E1-S8-2] Given a date before creation, When the as-of view loads, Then the did-not-exist sentence with the creation date renders. (traces to: DAC-E1-8)
- [DAC-E1-S8-3] Given a retired instrument that remains a member, When the table renders, Then it shows Not followed on every factor and never appears under All followed stocks. (traces to: DAC-E1-9)
- [DAC-E1-S8-4] Given the sole member, When Remove is activated, Then it is `blocked` with a Retire action adjacent; `last_member` keeps the dialog with a Retire action. (traces to: DAC-E1-7)
- [DAC-E1-S8-5] Given Remove, When the dialog opens, Then it uses the `confirm` variant (never `destructive`), states that history stays and puts initial focus on Cancel. (traces to: AC-6)
- [DAC-E1-S8-6] Given the history tab, When it renders, Then events are newest first and a rename shows both names. (traces to: AC-4)
