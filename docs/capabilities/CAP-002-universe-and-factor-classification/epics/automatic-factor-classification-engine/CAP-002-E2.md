# Automatic Factor Classification Engine

**EPIC ID:** CAP-002-E2
**Jira Key:** N/A
**Capability:** CAP-002
**Summary:** Turn every acquisition run that ends succeeded or partial into one whole, honest classification set, without the owner asking: derive every value, growth and momentum input for each actively acquired stock with the date it was known, score and rank each factor only against the peer set of stocks whose inputs for it are all present and current, and mark a result possibly restated when it rests on backfilled fundamentals. Nothing is overwritten, nothing incomplete is shown, and the arithmetic runs as reviewable PostgreSQL window functions rather than a numeric library. A run that ends failed, cancelled or abandoned never produces a set, and a build that fails anywhere leaves no partial row, only a recorded reason.
**Actors:** classification-scheduler, factor-engine, research-store, market-data-store (read-only)
**Estimate:** XL
**Out of Scope:** Serving, sorting, filtering or rendering the computed classifications (E3, E4, E5); writing or reading universe membership (E1); deciding which Massive payload keys supply the seven factor line items, which is the owner's open question this EPIC cannot resolve.
**Dependencies:** None within CAP-002 for starting the work against the documented contract. CAP-001's `instrument`, `daily_bar`, `fundamental_observation`, `corporate_action`, `acquisition_state` and `acquisition_run` tables are `requires-runtime` per capability section 5.1, so this EPIC is designable and almost entirely buildable now; final verification of the value and growth inputs needs a real acquisition run and the owner's answer on the payload-key mapping (open question below).
**Links:** system-design.md section 3.1 (steps 4 to 31), 4.4 (`classification_set`, `classification_set_factor`, `factor_input`, `factor_classification`); component-design-factor-engine.md sections 2.2 to 2.6; component-design-classification-scheduler.md sections 2.2 to 2.5; component-design-research-store.md section 2.4 (migration `0006`).

## Goals

- Create exactly one `classification_set` per qualifying run (`succeeded` or `partial`), and never for a run that ends `failed`, `cancelled` or `abandoned`.
- Derive every value, growth and momentum input exactly as the capability's factor definitions fix, with its `as_of` and `known_on` dates, deciding `present`, `missing`, `outdated` or `not_computable` per input.
- Form each factor's peer set from every active instrument whose inputs for that factor are all present, and score and rank a factor only when at least 30 stocks qualify.
- Mark a value or growth classification possibly restated when any fundamental behind it was backfilled.
- Commit a whole set in one transaction, or roll back to a `failed` set carrying its reason; never leave a reader able to see half of one.
- Finish a build for up to 3000 instruments inside the 5-minute budget, with the poll interval the only latency the detection step adds.
- Recover from a build interrupted by an application restart, so one crash cannot wedge classification for good.

## Non-Functional Requirements

- **Reliability:** at most one `classification_set` may be `building` at a time, enforced by a partial unique index, not by process state, so a second application process started by mistake could not build concurrently either.
- **Timeliness (AC-11):** a local `statement_timeout` bounds a build to the configured budget (default 300 seconds, DEC-0067, PROVISIONAL); the poll interval is 5 seconds by default (DEC-0054, PROVISIONAL, reused from the owner's idle-poll decision).
- **Correctness:** the composite and every input are computed with PostgreSQL window functions (`avg`, `stddev_samp`, `percent_rank`) and no numeric library (DEC-0052, PROVISIONAL), so the arithmetic is reviewable SQL.
- **Point-in-time integrity (C5, AC-19):** `factor_input`, `factor_classification` and `classification_set_factor` are append-only; every input is selected as it exists during the build's own transaction, and nothing recorded later changes a committed set.
- **Recoverability:** a `building` set orphaned by an application restart is recorded `failed` at scheduler start before any new claim is attempted (DEC-0067, PROVISIONAL — a mitigation for a system-design gap the owner has not yet assessed; see Open Questions), after which the next qualifying run proceeds normally.

## EPIC Acceptance Criteria

### From Capability

- [AC-7] Every value, growth and momentum classification MUST be computed from exactly the inputs, periods and equal weights defined for that factor in Section 2.
- [AC-8] A stock's classification on a factor MUST be measured against all actively acquired stocks that qualify on that factor, and MUST be identical in every universe the stock belongs to.
- [AC-9] Every classified factor MUST be shown as a standardised score together with a percentile rank from 0 to 100. (compute side: the score and percentile this EPIC writes)
- [AC-10] Classifications MUST be brought up to date without user action after every acquisition run that ends as succeeded or partial, and MUST NOT be recomputed after a run that ends as failed, cancelled or abandoned.
- [AC-11] Classifications for up to 3000 actively acquired stocks MUST be up to date within 5 minutes of the acquisition run ending.
- [AC-12] The product MUST NOT show a score or percentile on a factor for a stock unless every input that factor needs is present and current, and MUST instead show the stock as not classified on that factor with the missing or outdated input named.
- [AC-13] An input MUST be treated as outdated when it is a fundamental whose latest reported period ended more than 6 months before the classification date, or a price that is not from the latest trading day the product holds.
- [AC-14] When fewer than 30 stocks qualify on a factor, the product MUST NOT show scores or percentiles on that factor, and MUST state that there are not enough stocks to rank and how many qualified.
- [AC-15] A stock retired from acquisition MUST NOT be classified or counted in any peer set, and MUST be shown in its universes as not classified because it is retired. (compute side: exclusion from every peer set)
- [AC-19] Data acquired for an earlier period MUST NOT change any classification already recorded, and MUST NOT make a classification appear to have been known before the date it was produced.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (build side: the set never appears half-written, and a failure records its reason)
- [AC-23] A value or growth classification MUST be marked as possibly reflecting restated data when any fundamental behind it was acquired as historical backfill, for a period already reported before acquisition of that stock began, and the mark MUST be retained with that classification in its history.

### Derived

- [DAC-E2-1] Each of the eight named inputs MUST be derived exactly per the trailing-twelve-month sums, prior-year comparison, most-recent balance sheet, and read-time split-and-dividend adjustment of unadjusted bars this capability's factor definitions and the system design fix, with no step the capability does not define. (traces to: AC-7)
- [DAC-E2-2] A factor's peer set MUST be exactly the active instruments whose inputs for that factor are all `present`; a stock's score and percentile on a factor MUST be identical whether or not it belongs to any universe. (traces to: AC-8)
- [DAC-E2-3] The composite MUST be formed by z-scoring each input over the peer set with the sample standard deviation, averaging with equal weight, re-standardising, and ranking with `percent_rank() × 100`; zero dispersion in any step MUST contribute zero rather than dividing by zero. (traces to: AC-9)
- [DAC-E2-4] `classification_set.run_id` MUST be unique so a run acquires at most one set; a run in `failed`, `cancelled` or `abandoned` MUST never acquire one, even if it wrote observations before stopping. (traces to: AC-10)
- [DAC-E2-5] A build over 3000 active instruments MUST complete within the AC-11 budget less the detection latency of one poll interval, verified by a volume test under the `slow` marker rather than asserted at runtime. (traces to: AC-11)
- [DAC-E2-6] A fundamental input MUST be `outdated` when its latest reported period ended more than 6 months before the classification date; a price-dependent input MUST be `outdated` when the stock's latest bar precedes the latest trading day held across active instruments. (traces to: AC-13)
- [DAC-E2-7] A factor MUST be ranked only when at least 30 stocks qualify; below that, every active stock MUST be `not_classified` with reason `not_enough_stocks` and the qualifying count stated. (traces to: AC-14)
- [DAC-E2-8] A retired instrument MUST be excluded from every peer set and recorded `not_classified` with reason `retired` on all three factors, with no `factor_input` rows written for it. (traces to: AC-15)
- [DAC-E2-9] Every input used by a classification set MUST be selected exactly as it existed when that set's build transaction ran; a fundamental or price recorded after a set completes MUST NOT alter any row of that set. (traces to: AC-19)
- [DAC-E2-10] A `classification_set` MUST transition to `complete` in the same transaction as its last classification row, or to `failed` with the exception class and message as its reason in a new transaction with every row of that attempt rolled back; no reader may ever observe a partially written set. (traces to: AC-20)
- [DAC-E2-11] A value or growth classification built on any statement whose `provider_filing_date` precedes the instrument's first fundamentals `observed_on` MUST carry `restated_possible`, appended with the classification and never with a momentum classification. (traces to: AC-23)
- [DAC-E2-12] A `classification_set` left `building` by an interrupted application process MUST be recorded `failed`, with a fixed interruption reason, at the next scheduler start and before any new claim is attempted, so classification can resume without the owner touching the data store. (traces to: AC-20; mitigation for a surfaced system-design gap, DEC-0067, PROVISIONAL)

- **The build timeout default (300 seconds) and the poll cadence (5 seconds)** are reused defaults the owner may uphold or replace (DEC-0067, DEC-0054, both PROVISIONAL). *Owner: capability owner. Blocks: nothing.*
