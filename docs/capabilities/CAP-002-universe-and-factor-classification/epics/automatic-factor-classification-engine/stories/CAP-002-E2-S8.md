# Classification Settings, Qualifying-Run Claim and Interrupted-Build Reclaim

## User Story

As an owner-operator, I want a set created automatically for each qualifying run and an interrupted build recorded failed at start, so that classification resumes without touching the data store.

## Description

Delivers `src/factorflow/classification/settings.py` (`ClassificationSettings`, `FACTORFLOW_CLASSIFICATION_*`, defaults 5 and 300), `src/factorflow/classification/scheduler.py` functions `claim_next_set` and `reclaim_interrupted_sets`, and `sql/qualifying_run.sql`, `sql/claim_set.sql`, `sql/reclaim_interrupted.sql`. Poll default 5 seconds (DEC-0054) and build timeout 300 seconds (DEC-0067) are provisional owner-upholdable defaults.

The loop itself is CAP-002-E2-S9.

Source: `component-design-classification-scheduler.md` sections 2.1, 2.3, 2.4, 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Classifications MUST be brought up to date without user action after every acquisition run that ends as succeeded or partial, and MUST NOT be recomputed after a run that ends as failed, cancelled or abandoned.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (build side: the set never appears half-written, and a failure records its reason)
- [DAC-E2-4] `classification_set.run_id` MUST be unique so a run acquires at most one set; a run in `failed`, `cancelled` or `abandoned` MUST never acquire one, even if it wrote observations before stopping. (traces to: AC-10)
- [DAC-E2-12] A `classification_set` left `building` by an interrupted application process MUST be recorded `failed`, with a fixed interruption reason, at the next scheduler start and before any new claim is attempted, so classification can resume without the owner touching the data store. (traces to: AC-20; mitigation for a surfaced system-design gap, DEC-0067, PROVISIONAL)

### Derived

- [DAC-E2-S8-1] Given runs in `failed`, `cancelled`, `abandoned`, `running` or `requested`, When claims are attempted, Then none is claimed; `succeeded` and `partial` are. (traces to: AC-10)
- [DAC-E2-S8-2] Given three qualifying runs, When claimed over three iterations, Then they are claimed in `ended_at` order and a run with a set is never claimed again. (traces to: DAC-E2-4)
- [DAC-E2-S8-3] Given a set `building`, When a claim is attempted, Then it returns `None` and inserts nothing. (traces to: AC-10)
- [DAC-E2-S8-4] Given a claim at 23:30 America/Chicago, When the set is stamped, Then the classification date is the Chicago date, not the next UTC date (STD-UI-5). (traces to: AC-10)
- [DAC-E2-S8-5] Given a `failed` set for run A, When claims continue, Then no new set is created for A while a later qualifying run B is claimed. (traces to: DAC-E2-4)
- [DAC-E2-S8-6] Given a `building` row with no classification rows, When `reclaim_interrupted_sets` runs, Then it becomes `failed` with the fixed interruption reason and the next qualifying run is claimable; `complete` and `failed` sets are unchanged. (traces to: DAC-E2-12)
- [DAC-E2-S8-7] Given `FACTORFLOW_CLASSIFICATION_POLL_INTERVAL_SECONDS=0.5` or a poll interval not less than the timeout, When settings load, Then they fail naming the variable and not its value. (traces to: AC-10)
