# Factor Engine Build Transaction: Constants, Set Context, Completion, Failure and Timeout

## User Story

As an owner-operator, I want a classification build that commits one whole set or records a failed one with its reason, so that no reader can ever see half a set.

## Description

Delivers the build spine of `factor-engine`: `src/factorflow/classification/__init__.py`, `constants.py` (`MIN_PEER_SET_SIZE = 30`, `FUNDAMENTALS_STALE_AFTER_MONTHS = 6`, `MOMENTUM_LAG_MONTHS = 1`, `MOMENTUM_WINDOWS_MONTHS`, `FACTORS`, `INPUT_NAMES`), `line_items.py` (the seven line items, each `REQUIRES_INPUT` until the owner answers), `engine.py` (`build(conn, set_id, timeout_seconds) -> BuildResult`), `sql/set_context.sql`, `sql/complete_set.sql`, `sql/fail_set.sql`.

`build` runs the set's stages in one transaction with a local `statement_timeout`; stages are added by CAP-002-E2-S3, S4, S5 and S6. On any failure it rolls back every row of the attempt and records the set `failed` with the exception class and message in a new transaction.

Open owner question carried: `[REQUIRES INPUT]` for the Massive payload keys, signs and quarterly availability of the seven line items (system design section 8 question 1). This story ships `line_items.py` with each key unresolved and a unit test that fails until every key is resolved; tests pass their own fixture keys to the engine.

Source: `component-design-factor-engine.md` sections 2.1, 2.3, 2.6, 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Classifications MUST be brought up to date without user action after every acquisition run that ends as succeeded or partial, and MUST NOT be recomputed after a run that ends as failed, cancelled or abandoned.
- [AC-11] Classifications for up to 3000 actively acquired stocks MUST be up to date within 5 minutes of the acquisition run ending.
- [AC-15] A stock retired from acquisition MUST NOT be classified or counted in any peer set, and MUST be shown in its universes as not classified because it is retired. (compute side: exclusion from every peer set)
- [AC-19] Data acquired for an earlier period MUST NOT change any classification already recorded, and MUST NOT make a classification appear to have been known before the date it was produced.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (build side: the set never appears half-written, and a failure records its reason)
- [DAC-E2-4] `classification_set.run_id` MUST be unique so a run acquires at most one set; a run in `failed`, `cancelled` or `abandoned` MUST never acquire one, even if it wrote observations before stopping. (traces to: AC-10)
- [DAC-E2-9] Every input used by a classification set MUST be selected exactly as it existed when that set's build transaction ran; a fundamental or price recorded after a set completes MUST NOT alter any row of that set. (traces to: AC-19)
- [DAC-E2-10] A `classification_set` MUST transition to `complete` in the same transaction as its last classification row, or to `failed` with the exception class and message as its reason in a new transaction with every row of that attempt rolled back; no reader may ever observe a partially written set. (traces to: AC-20)

### Derived

- [DAC-E2-S2-1] Given an injected failure after inputs are written, When `build` runs, Then the four classification tables hold zero rows for the set and the set is `failed` with the exception class in `failure_reason`. (traces to: DAC-E2-10)
- [DAC-E2-S2-2] Given the set was already marked `failed` by another writer, When `build` tries to complete it, Then `complete_set.sql` (guarded by `state = 'building'`) updates no row, `build` raises inside the transaction, rolls back and writes nothing. (traces to: DAC-E2-10)
- [DAC-E2-S2-3] Given `timeout_seconds` of 0.001 against a populated store, When `build` runs, Then the set is `failed` with a timeout reason and no rows (DEC-0067). (traces to: AC-11)
- [DAC-E2-S2-4] Given a run, When `set_context.sql` resolves it, Then it returns the classification date, the latest trading day held across active instruments and the active roster, selecting rows as they exist in the build's own transaction. (traces to: DAC-E2-9)
- [DAC-E2-S2-5] Given a `LINE_ITEMS` key still `REQUIRES_INPUT`, When inputs are derived, Then they are `missing` with `detail.cause = line_item_mapping_unresolved` and momentum still classifies; `test_line_items_resolved.py` fails until every key is resolved. (traces to: AC-7)
- [DAC-E2-S2-6] Given anything under `classification/`, When the safety test runs, Then nothing imports `factorflow.ingestion.massive`, every statement is parameterised and no `UPDATE` or `DELETE` names an observation or history table. (traces to: AC-19)
