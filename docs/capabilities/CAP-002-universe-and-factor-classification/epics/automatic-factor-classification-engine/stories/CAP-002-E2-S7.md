# Whole-Build Proof: No Backdating and the 3000-Instrument Volume Test

## User Story

As an owner-operator, I want proof that a completed set never changes and that a 3000-stock build fits the budget, so that the five-minute promise and point-in-time integrity are verified, not asserted.

## Description

Adds `tests/integration/test_engine_volume.py` (`slow` marker: 3000 instruments, 273 bars and 8 quarters each, completing within 295 seconds and writing 24,000 inputs and 9,000 classifications) and the no-backdating case of `tests/integration/test_engine_transaction.py`. Tuning of SQL discovered by the test is made in the stage files it names.

Source: `component-design-factor-engine.md` sections 5, 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-11] Classifications for up to 3000 actively acquired stocks MUST be up to date within 5 minutes of the acquisition run ending.
- [AC-19] Data acquired for an earlier period MUST NOT change any classification already recorded, and MUST NOT make a classification appear to have been known before the date it was produced.
- [DAC-E2-5] A build over 3000 active instruments MUST complete within the AC-11 budget less the detection latency of one poll interval, verified by a volume test under the `slow` marker rather than asserted at runtime. (traces to: AC-11)
- [DAC-E2-9] Every input used by a classification set MUST be selected exactly as it existed when that set's build transaction ran; a fundamental or price recorded after a set completes MUST NOT alter any row of that set. (traces to: AC-19)

### Derived

- [DAC-E2-S7-1] Given 3000 instruments, When `build` runs, Then it completes within 295 seconds and writes 24,000 inputs and 9,000 classifications. (traces to: DAC-E2-5)
- [DAC-E2-S7-2] Given a completed set, When a backfilled statement is inserted afterwards, Then every row of that set is unchanged and the next set sees the statement. (traces to: DAC-E2-9)
