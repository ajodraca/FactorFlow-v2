# Classification Loop: Dispatch Off the Event Loop, Restart Reclaim and Build Pass-Through

## User Story

As an owner-operator, I want the scheduler loop that claims qualifying runs and builds their sets without my action, so that classifications are current after every succeeded or partial run.

## Description

Adds `run_classification_loop` to `src/factorflow/classification/scheduler.py`. It runs `reclaim_interrupted_sets` once before the first claim, claims through an injected dispatcher off the event loop, builds through `engine.build`, waits `poll_interval_seconds` between idle iterations and never sleeps after a build, and continues after an iteration failure. It warns once per unresolved line item at start. The lifespan task that calls it is created by CAP-002-E3-S6.

Source: `component-design-classification-scheduler.md` sections 2.4, 2.5, 7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Classifications MUST be brought up to date without user action after every acquisition run that ends as succeeded or partial, and MUST NOT be recomputed after a run that ends as failed, cancelled or abandoned.
- [AC-11] Classifications for up to 3000 actively acquired stocks MUST be up to date within 5 minutes of the acquisition run ending.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (build side: the set never appears half-written, and a failure records its reason)
- [DAC-E2-4] `classification_set.run_id` MUST be unique so a run acquires at most one set; a run in `failed`, `cancelled` or `abandoned` MUST never acquire one, even if it wrote observations before stopping. (traces to: AC-10)
- [DAC-E2-12] A `classification_set` left `building` by an interrupted application process MUST be recorded `failed`, with a fixed interruption reason, at the next scheduler start and before any new claim is attempted, so classification can resume without the owner touching the data store. (traces to: AC-20; mitigation for a surfaced system-design gap, DEC-0067, PROVISIONAL)

### Derived

- [DAC-E2-S9-1] Given injected `wait_fn`, `dispatch_fn` and `stop_event`, When the loop runs under `asyncio.run`, Then claim and build go through the dispatcher and idle iterations wait the poll interval. (traces to: AC-10)
- [DAC-E2-S9-2] Given a raising claim, When the loop iterates, Then the exception is logged with `exception` and the loop continues (OPS-ERR-001). (traces to: AC-10)
- [DAC-E2-S9-3] Given loop start, When it begins, Then `reclaim_interrupted_sets` is dispatched before the first claim and never again. (traces to: DAC-E2-12)
- [DAC-E2-S9-4] Given `build_timeout_seconds` too short for the store, When the loop builds, Then the timeout reaches the engine and the set is `failed` with a timeout reason. (traces to: AC-11)
- [DAC-E2-S9-5] Given `factorflow.ingestion_main`, When imports are inspected, Then it imports nothing under `factorflow.classification`. (traces to: AC-10)
