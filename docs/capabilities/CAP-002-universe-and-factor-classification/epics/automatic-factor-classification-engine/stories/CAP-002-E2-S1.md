# Migration 0006: Classification Set, Peer Set, Input and Classification Tables

## User Story

As an owner-operator, I want the classification tables created by a forward-only migration with their invariants enforced by the store, so that a set can never be half-visible and history cannot be rewritten.

## Description

Delivers `src/factorflow/db/migrations/0006_classifications.sql` creating `classification_set`, `classification_set_factor`, `factor_input` and `factor_classification` as `component-design-research-store.md` section 2.4 specifies: the partial unique index allowing one `building` set, the unique `run_id`, the terminal-shape and classification-shape CHECKs, the input-name-matches-factor check and the score and percentile indexes the reader sorts on.

Extends the shared files created by CAP-002-E1-S1: `tests/unit/test_research_sql_is_append_only.py` (adds the three append-only classification tables and the rule that every `UPDATE classification_set` carries a `state = 'building'` guard) and `tests/integration/test_research_migrations_apply.py` (adds `0006`, idempotence and the dump and restore round trip). It hard-depends on CAP-002-E1-S1 because migration filenames take "no gaps" (`migrations/README.md`) and `0006` applies after `0005`.

Source: `component-design-research-store.md` sections 2.4, 2.5, 6, 7.

Ordering decision: DEC-0087.

Packaging (backlog review v4 FINDING-13; DEC-0088): this story also adds `classification/sql/*.sql` to `[tool.setuptools.package-data]` in `pyproject.toml` and extends `tests/unit/test_package_data_ships_sql.py` (created by CAP-002-E1-S1) to cover it, so the factor-engine, scheduler and reader statements that CAP-002-E2-S2 onward and E3 load at import ship in the release image.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-10] Classifications MUST be brought up to date without user action after every acquisition run that ends as succeeded or partial, and MUST NOT be recomputed after a run that ends as failed, cancelled or abandoned.
- [AC-19] Data acquired for an earlier period MUST NOT change any classification already recorded, and MUST NOT make a classification appear to have been known before the date it was produced.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (build side: the set never appears half-written, and a failure records its reason)
- [DAC-E2-4] `classification_set.run_id` MUST be unique so a run acquires at most one set; a run in `failed`, `cancelled` or `abandoned` MUST never acquire one, even if it wrote observations before stopping. (traces to: AC-10)
- [DAC-E2-10] A `classification_set` MUST transition to `complete` in the same transaction as its last classification row, or to `failed` with the exception class and message as its reason in a new transaction with every row of that attempt rolled back; no reader may ever observe a partially written set. (traces to: AC-20)

### Derived

- [DAC-E2-S1-1] Given a store holding `0001` to `0005` and data, When `0006` is applied, Then `applied_migrations` records 6 and no CAP-001 or `0005` row changes. (traces to: AC-19)
- [DAC-E2-S1-2] Given a second set naming an existing `run_id`, When it is inserted, Then the unique constraint refuses it. (traces to: DAC-E2-4)
- [DAC-E2-S1-3] Given a `building` set exists, When a second `building` row is inserted, Then it is refused, while a `complete` or `failed` row beside it is allowed. (traces to: DAC-E2-10)
- [DAC-E2-S1-4] Given a `complete` set without `ended_at`, `latest_trading_day` or `active_instruments`, or a `failed` set without `failure_reason`, When inserted, Then it is refused. (traces to: DAC-E2-10)
- [DAC-E2-S1-5] Given a classified row with a reason, an unclassified row with a score, an `input_missing` row without `reason_input`, a `retired` row with one, or a percentile of 100.5 or -1, When inserted, Then the shape CHECK refuses it. (traces to: AC-20)
- [DAC-E2-S1-6] Given `return_3m` under `value`, or a `present` input without value, `as_of` or `known_on`, When inserted, Then it is refused. (traces to: AC-19)
- [DAC-E2-S1-7] Given a `pg_dump` of a store with one complete set and one universe, When restored into an empty database, Then the current set and membership read back unchanged. (traces to: AC-19)
- [DAC-E2-S1-8] Given `pyproject.toml` as committed, When `tests/unit/test_package_data_ships_sql.py` runs, Then `classification/sql/` is covered by a package-data glob, so the scheduler and the reader can load their statements from a non-editable install. (traces to: AC-10)

## Technical Details

### Implementation

- `src/factorflow/db/migrations/0006_classifications.sql`: additive only, one transaction, no `BEGIN` or `COMMIT`.
- `pyproject.toml`: `classification/sql/*.sql` appended to the `factorflow` package-data list; nothing else in the file changes.
- Tests: `tests/unit/test_migration_0006_matches_design.py`, `tests/integration/test_research_constraints.py` (classification cases appended), plus the three shared files named above (`tests/unit/test_package_data_ships_sql.py` included).

### Data Changes

- Four new tables and their indexes per research-store section 2.4.
