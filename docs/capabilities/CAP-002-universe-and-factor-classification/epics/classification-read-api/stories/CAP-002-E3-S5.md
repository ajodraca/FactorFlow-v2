# Classifications Router: List, Summary, Sets, Stock Evidence and History, Mounted in the Application

## User Story

As an owner-operator, I want the classification reads available as HTTP endpoints, so that the interface can show scores, evidence and history.

## Description

Delivers `src/factorflow/api/routes/classifications.py` (`GET /api/classifications`, `/summary`, `/sets`, `/sets/{set_id}`, `/stocks/{symbol}`, `/stocks/{symbol}/history`), the classification models added to `src/factorflow/api/classification_models.py` and the error mapping for classification errors, and adds `app.include_router(classifications.router)` to `src/factorflow/api/app.py`.

Ordering decision: as in CAP-002-E1-S6, the router is mounted in the story that builds it, so this story's route and integration tests run through `create_app()` (DEC-0086). `/summary` is declared before `/stocks/{symbol}` and `/sets/{set_id}` so the literal segment is never captured. The scheduler start and no-secrets extension remain in CAP-002-E3-S6.

Source: `component-design-classification-api.md` sections 2.1, 2.3 (`include_router` only), 2.4 to 2.7.

## Acceptance Criteria (Given/When/Then)

### From Capability / EPIC

- [AC-9] Every classified factor MUST be shown as a standardised score together with a percentile rank from 0 to 100. (serve side: the read this EPIC returns)
- [AC-13] An input MUST be treated as outdated when it is a fundamental whose latest reported period ended more than 6 months before the classification date, or a price that is not from the latest trading day the product holds. (the current-stock summary rule derived from this)
- [AC-16] The user MUST be able to sort stocks by any factor's score or percentile, filter them with thresholds on one or more factors at once, and view chosen stocks side by side, both across all classified stocks and within a single universe.
- [AC-17] For any classification, the user MUST be able to see the inputs it was built from and the date on which each input was known.
- [AC-18] Every classification MUST be retained with the date it was produced and MUST NOT be overwritten, and the user MUST be able to see a stock's earlier classifications.
- [AC-20] Until a new set of classifications is complete, the product MUST show the previous set marked as not reflecting the latest acquisition, and MUST NOT show a half-finished set as current. When classification fails, the product MUST also show the failure and its reason. (serve side)
- [AC-21] The user MUST be able to see when the current classifications were produced and which acquisition run they reflect.
- [AC-22] Before any classification has been produced, the product MUST state that no stocks have been classified rather than presenting an empty list as complete.
- [DAC-E3-7] Compare MUST accept 2 to 6 symbols, never fewer or more, and MUST return every requested symbol that names a known instrument, with an unrecognised one reported in `unknown_symbols` rather than silently dropped. (traces to: AC-16)
- [DAC-E3-11] The summary and the list read MUST carry the same `set` and `later` shape, including before any set exists, so every consumer — this capability's screens and the future shell capability's — reads one rule. (traces to: AC-20, AC-22)

### Derived

- [DAC-E3-S5-1] Given `GET /api/classifications/summary`, When called, Then it is routed to the summary handler, not captured by a path parameter. (traces to: AC-20)
- [DAC-E3-S5-2] Given compare with fewer than `MIN_COMPARE_SYMBOLS` (2) or more than `MAX_COMPARE_SYMBOLS` (6) symbols, When validated, Then the request is rejected before the reader is called. (traces to: DAC-E3-7)
- [DAC-E3-S5-3] Given no set exists, When the list and the summary are read, Then both carry the same `never_classified`, `set` and `later` shape. (traces to: DAC-E3-11)
- [DAC-E3-S5-4] Given a cell, When serialised, Then scores and percentiles are decimal strings at stored precision and `restated_possible` is present. (traces to: AC-9)
- [DAC-E3-S5-5] Given an unknown symbol on the evidence route, When called, Then the error envelope returns the documented code naming the operation and resource. (traces to: AC-17)
- [DAC-E3-S5-6] Given `create_app()`, When the classification routes are called through `TestClient`, Then they are mounted behind the Host/Origin and request-id middleware and ahead of the static mount. (traces to: AC-16)

## Technical Details

### API Contract

- Endpoints as above; shapes `ClassificationListResponse`, `ClassificationSummaryResponse`, `StockEvidenceResponse`, `StockHistoryResponse`, `SetListResponse`, `SetResponse` per classification-api section 2.7.
- Errors: documented envelope; no stack trace or credential in a body.

### Implementation

- Tests: `tests/unit/test_api_classifications_routes.py` (including summary route precedence), `tests/integration/test_api_classifications.py`, `tests/integration/test_api_classification_summary.py`, `tests/integration/test_api_classification_host_origin.py` (classification cases), `tests/unit/test_api_classification_error_mapping.py` (classification cases).

### Validation

`uv run pytest -m postgres`, `uv run pytest -m 'not postgres'`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`.
