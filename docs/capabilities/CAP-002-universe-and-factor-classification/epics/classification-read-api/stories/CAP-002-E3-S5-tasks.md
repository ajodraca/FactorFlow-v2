# Tasks: CAP-002-E3-S5 — Classifications Router: List, Summary, Sets, Stock Evidence and History, Mounted in the Application

**Story**: `docs/capabilities/CAP-002-universe-and-factor-classification/epics/classification-read-api/stories/CAP-002-E3-S5.md`
**Component**: `FactorFlow-v2`
**Branch**: `usr/alvaro-de-jodra/CAP-002-E3-tasks`
**Date**: 2026-10-17

## Summary

Builds the HTTP face of the classification reads. `src/factorflow/api/routes/classifications.py` serves
`GET /api/classifications` (the Research list, or a 2 to 6 symbol compare), `/summary`, `/sets`,
`/sets/{set_id}`, `/stocks/{symbol}` and `/stocks/{symbol}/history` by validating the request,
delegating to `factorflow.classification.reader` and shaping the result; it holds no classification
rule and computes nothing (AC-19, STD-UI-15). The request model for the list query and the response
models (`LaterBlock`, the list, summary, evidence, history and set responses) are added to
`src/factorflow/api/classification_models.py` beside the `FactorCellResponse`, `FactorsResponse` and
`SetBlock` that CAP-002-E1-S6 created there and this story reuses, scores and percentiles travel as
decimal strings at stored precision, and the list and summary reads share one `never_classified` /
`set` / `later` shape, including before any set exists. Classification errors map to the documented
envelope. The story mounts the router in `src/factorflow/api/app.py` with one `include_router` line, so
its route and integration tests run through `create_app()` behind the Host/Origin and request-id
middleware and ahead of the static mount (DEC-0086). The scheduler start and the no-secrets extension
stay in CAP-002-E3-S6.

### Open Gaps

1. **PROVISIONAL — awaiting owner confirmation (2026-10-17): how the route chooses `cursor_invalid` or `cursor_stale`.** API design 2.5 and TC-INT-042 fix both codes (`cursor_stale` when the cursor names another set or ordering), but the reader raises one `CursorError` for both a malformed and a mismatched cursor (CAP-002-E3-S2 plan T018) and exposes no way to tell them apart. The plan: on the list route the router tells them apart with a route-private check, T017's `_cursor_code`. A cursor is stale only when its own `set` parses as a UUID, its `sort` is a `reader.SORT_ALLOWLIST` key, its `order` is `asc` or `desc`, and the reader's public `decode_cursor` accepts the cursor against exactly those values, so the caught `CursorError` can only be a set, sort or order mismatch. Anything else is invalid, including every structural fault the reader rejects (amended by the E3-F07 owner-directed fix below). History and sets cursors carry no set, sort or order, so every `CursorError` there is `cursor_invalid`. Derivation: both artifacts fix the codes and the condition; the check meets them without editing the approved reader or CAP-001 code, at the cost of knowing three field names. Recorded as DEC-0138. Flag for the reader design (a `CursorStale(CursorError)` subclass would delete the peek) and for the API design 2.5 to say which side decides.
2. **PROVISIONAL — awaiting owner confirmation (2026-10-17): where the classification error mapping lives.** The story says CAP-002-E1-S6 provides "the error-mapping module", but no design names one, and the CAP-002-E1-S6 plan (T016) keeps its universe error mapping private to `routes/universes.py`, so no shared module is delivered. The delivered routers map inline. The plan keeps one table-driven helper private to `routes/classifications.py` (T017) and depends on E1-S6 only for models, bounds and the `app.py` edit; T001 records any shared module E1-S6 does deliver and T017 then calls it. Derivation: constraint 6 (follow existing patterns) and constraint 3 (name nothing no artifact defines); statuses and codes are fixed verbatim by design 2.5, only the location is chosen. Recorded as DEC-0139. Flag for the API design 2.1, whose placement list names no mapping module although the story does.
