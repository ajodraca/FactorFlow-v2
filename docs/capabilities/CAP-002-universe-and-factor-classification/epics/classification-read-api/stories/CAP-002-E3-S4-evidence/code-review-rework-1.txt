**IR-001: resolved.** The new test is `test_history_orders_same_day_reruns_by_ended_at_not_by_date_or_id` (`tests/integration/test_reader_history.py:411`).
- It builds three earlier complete sets plus a current set, all on 2026-10-02. After reading the generated ids, it sorts them and gives the newest `ended_at` (11:00, 10:00, 09:00) to the smallest id, so the outcome does not depend on the random UUIDs.
- The current set ends at 13:00, after all three, so it really is the one left out.
- It checks the order unpaged, paged at `limit=1` and paged at `limit=2`, so no set can repeat or go missing.
- Both surviving mutants become `classification_date DESC, set_id DESC`. Since all dates are equal, they reduce to `set_id DESC`, which returns the exact reverse of the expected order. Both are killed on every run.

**IR-002: resolved, and the wrapping is not too broad.** The fix is in `src/factorflow/classification/reader.py:826-829`.
- The `try` covers only the call to `decode_cursor` (`runs/queries.py:172-195`). That function already turns base64, JSON, non-object, version, missing-key and bad-value errors into `CursorError`.
- The only remaining sources of `TypeError` or `AttributeError` are `datetime.fromisoformat(data["ts"])` and `UUID(data["id"])` given a field of the wrong type. That is the class IR-002 names, so the wrapping cannot hide an unrelated bug.
- The original error stays attached via `from exc`, and the message wording matches `decode_cursor`'s own.
- The four new cases (`tests/unit/test_reader_paging.py:110-114`) are a non-string and a null value for each of `ts` and `id`. Each runs through both reads and also checks that no statement executed. DEC-0268 records where the fix lives and why `runs.queries` is unchanged.

**IR-005: resolved.** `tests/integration/test_reader_volume.py:121-138` and `:317` now take the column name as a parameter. Every `factor_classification` access in the history plan must be an index scan whose Index Cond names `instrument_id`. Under the `+0` mutant, the access that picks the page of sets loses its Index Cond, so the assertion fails. The existing `set_id` call site is unchanged in meaning (`:244`).

**IR-003 / IR-004: resolved by decision record.** DEC-0265 is now `class: propagating` and lists CAP-002-E3-S5 under `blocks`. DEC-0269 records the two-statement read window as accepted, as the review allowed.

**Findings**

1. **NON-BLOCKING** (`tests/integration/test_reader_history.py:421-423`): the test does not control `started_at`. The three sets start at 08:00, 08:01 and 08:02 in creation order, which is unrelated to the sorted ids. A mutant that orders history by `started_at DESC` matches the expected order with probability 1/6. That mutant is plausible, because the set list does sort by `started_at`. The other history tests seed `started_at` in `ended_at` order, so they don't catch it either. As a result, a `started_at` regression is killed with probability 5/6 (the `ORDER BY started_at` mutant), not deterministically. The docstring's "neither the date nor the id gives the order" is true, but the start time is left to chance. Fix: give `started_at` an order that differs from both `ended_at` and the ids, for example by updating `started_at` along with `ended_at`.
2. **NON-BLOCKING** (`tests/integration/test_reader_history.py:430`): the expected order equals ascending `set_id`. A mutant that orders by `set_id ASC` alone would pass this test. Other tests catch it only by chance, though keyset paging on `ended_at` likely breaks it. A non-monotone layout, such as giving the newest `ended_at` to the middle id, would close this as well.
3. **NON-BLOCKING / informational** (`src/factorflow/classification/reader.py:826`): a `ts` without a time zone is still accepted, and `/api/runs` keeps the same type-confusion gap. DEC-0268 records both as outside IR-002 and sends the `/api/runs` gap to the owner as a CAP-001 follow-up. Both are acceptable.

I found no violations of the constitution. No production behaviour changes other than the cursor error type, and the new tests follow existing patterns: seeding from stored values, and the fake connection for checks that run before any statement.

VERDICT: APPROVED
