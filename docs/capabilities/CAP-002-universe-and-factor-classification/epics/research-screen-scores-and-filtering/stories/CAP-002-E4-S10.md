# Shell Composition: Research Destination, Five Routes and Updated Shell Tests

## User Story

As an owner-operator, I want Research in the navigation rail and every CAP-002 screen reachable at its route, so that the screens built in CAP-002 are reachable in the delivered shell without changing anything else.

## Description

Edits the delivered shell at its seam (DEC-0068, DEC-0069, DEC-0084): `web/src/app/shell.tsx` gains one `DESTINATIONS` entry, Research; `web/src/app/routes.tsx` gains five `Route` elements under `/research` before the catch-all; and the four delivered tests whose navigation-item count moves from four to five (`shell.test.tsx` line 71, `shell.a11y.test.tsx` line 36, `routes.test.tsx` line 75, `shell.unreachable.test.tsx` line 58), plus `routes.test.tsx`'s route-source assertion (lines 105 to 118), which gains the five `/research` paths. No other assertion changes. The `requestJson` export is CAP-002-E4-S1's.

Ordering decision: `routes.tsx` imports each screen it routes, so this story depends on the stories that build the Research screen (E4-S9), the Universes list and detail screens (E1-S7, E1-S9) and the Compare and Stock evidence screens (E5-S1, E5-S3). The epics' prose that E1's and E5's screens depend on this story is reversed accordingly (DEC-0086; backlog review v3 FINDING-12). The screens' own component tests render without the router, so none waits on this story.

Source: `component-design-classification-ui.md` sections 2.2, 7; system design section 8 question 4.
