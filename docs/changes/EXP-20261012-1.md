# Expedited Change: A missing migrations directory refuses the start

## Request and Outcome

The owner directed this change on 2026-10-12 ("run $expedited-change for
B1–B3", then scoped to B2 alone after lane classification). It is blocker B2 of
`docs/releases/CAP-001-release-v1.md`.

Root cause: `discover()` in `src/factorflow/db/migrator.py` globs
`directory.glob("*.sql")`, and a directory that does not exist yields no files.
`run_migrations` then treats an empty list as "schema current at version 0" and
returns exit 0. In the release image built from `ef2dd7c`, `migrate_main`
resolves its migrations directory to a path that does not exist (blocker B1).
The migrator therefore exited 0 having applied nothing, and the entrypoint's
`&&` chain started the API on a store with no schema. Component design section
2.5 maps every failure to exit codes 1 to 4 so that "Migrator exits non-zero;
API never binds" (AC-16). A build that cannot find the migrations it carries is
such a failure.

Outcome: `discover()` raises `MigrationError` naming the path when the directory
does not exist. `run_migrations` already returns exit 4 for discovery errors,
before connecting to the database, so the entrypoint stops and the API never
binds. A directory that exists but holds no migrations keeps today's behaviour.

## Documentation Impact

`README.md` "Running the migrator" describes exits 1–4 as "unreachable
database, store ahead of this build, a tampered migration, or a migration that
failed partway". Exit 4 already covered discovery failures (malformed filename,
repeated version), and now also covers a missing migrations directory. Doc-sync
should add that cause to the sentence. No other component doc describes
`discover()`.
