# Expedited Change: Call the Massive ratios endpoint with its real signature

## Request and Outcome

The owner asked directly: "fix the MassiveClient defects with $expedited-change". Expedited review v1 (`EXP-20261009-1-review-v1.md`) returned `CHANGES-REQUIRED`: honouring `FACTORFLOW_MASSIVE_BASE_URL` answers `privacy-secrets` and `deployment-topology` yes and belongs in the high-risk lane (ER-001, ER-002). The owner chose to **split** the change. This record now carries only the ratios-signature fix. The base-URL part was reverted with a forward commit (see Scope and Traceability).

Defect: `_financial_page` in `src/factorflow/ingestion/massive/client.py` called all four financial SDK methods with `tickers=`, `period_end_gte=` and `period_end_lte=`. The installed SDK's `list_financials_ratios` (massive 2.8.0) accepts `ticker=` (singular), has no period parameter and no `**kwargs`, so the call raised `TypeError`. That error is classified retryable, so every instrument spent three governed attempts and its fundamentals ended `ProviderUnavailable`.

Outcome: the ratios endpoint is called with `ticker=<symbol>, raw=True` only. The three statement endpoints keep their existing, correct `tickers=`, `period_end_gte=` and `period_end_lte=` arguments. The SDK no longer rejects the request.

What this change does **not** do (ER-003): it does not restore CAP-001 AC-3 fundamentals against the live provider. Ratios results do not match the shared financial-statement model. The SDK's `FinancialRatio` carries `ticker`, `cik`, `date` and ratio values, and has none of the `tickers`, `period_end`, `filing_date`, `fiscal_year` or `timeframe` fields that `FinancialStatement` requires. So fundamentals still fail for any instrument with a non-empty ratios response. They now fail as `ProviderContractViolation` after one attempt, rather than `ProviderUnavailable` after three. The per-instrument, per-data-type `failed` outcome is the same as before, and nothing is written partially, because `fetch_financials` collects all four endpoints before any row reaches the writer. Fundamentals succeed only when the ratios response is empty. The ratios call also has no date bound, so `follow_pages` fetches every ratios page for the symbol before validation fails. Both points are follow-ups for the owner and are out of scope here (see Documentation Impact).

## Documentation Impact

For `$doc-sync`, after a passing review (ER-004). This change does not edit the design:

- `component-design-massive-client.md` section 11: the interface table says the ratios endpoint takes the same request ("as above") and has the "Same shape and constraints" as the statement endpoints. The SDK shows ratios takes `ticker`, not `tickers`, has no `period_end` or `filing_date` filter, and returns `FinancialRatio`, not the statement shape.
- The section 2.2b construction snippet (no `base=`) is now accurate for the code and stays as it is until the high-risk base-URL work changes both.
- Section 4 cites `tests/unit/test_massive_tls.py`, which does not exist. That belongs with the high-risk base-URL work, which must decide the TLS rule and its test.

Open follow-ups for the owner, outside this change's scope:

- **Ratios model.** Decide how ratios are modelled and stored, given that `FinancialRatio` does not fit `FinancialStatement`. Until then, fundamentals fail as `ProviderContractViolation` for any instrument with a non-empty ratios response. This changes the component design and `fundamental_observation` semantics, so it belongs in the standard lane.
- **Ratios date bound.** The ratios call is unbounded. Decide whether to bound it by `date`, client-side or otherwise, so each instrument does not page through its whole ratios history.
- **E2E stub fidelity.** `tests/e2e/support/massive_stub.py` accepts either `ticker` or `tickers` and serves statement-shaped ratios rows, so the e2e stack does not exercise the real ratios shape.
- **Base URL (high-risk lane).** See Scope and Traceability. E2E T008-T012 stay held until it lands.
- The `# Implements TC-INT-023` annotation (integration automation task T011) is still held. This change does not add it.
