# Expedited Change: A rejected credential fails the run instead of stopping the process

## Request and Outcome

The owner directed this change on 2026-10-11 ("Fix C first too"), before finishing CAP-001's E2E automation. Automation task T009 (TC-E2E-005) runs an acquisition against a provider that rejects the credential, and that run never ended.

Root cause, in code CAP-001-E4-S5 delivered:

- `component-design-massive-client.md` section 2.4: "`CredentialRejected` is the one provider error that is not per-instrument … the runner finalises the run as `failed` with that reason." `component-design-runtime-config.md` section 2.2b says the same ("the run fails on `CredentialRejected` with the whole run marked `failed`"), and capability flow 1 step 5 requires the run to report "that it failed and why".
- `AcquisitionRunner.execute_claimed` caught `CredentialRejected` in each of its four fetch blocks only to re-raise it. Nothing above it catches it: not `ingestion_main.execute_fn`, not `run_polling_loop`, not `main`.
- So the run was never finalised. It stayed `running` until the reclaim sweep marked it `abandoned` (900 s by default), and the uncaught exception ended the ingestion process. `journal.py` already defined `_FAILED_UPDATE_SQL`, with a `failure_reason`, but no function used it.

No test drove a rejected credential through the runner.

Outcome: on `CredentialRejected` the runner composes the credential-safe reason with `compose_failure_reason` (whose fixed text never echoes the provider's message, DAC-E3-S5-2), records the run as `failed` with that reason through a new `journal.fail_run`, writes nothing for the instrument it was reading, reads no further instrument, and returns normally. The ingestion process keeps polling. If the owner had already requested cancellation, the run ends `cancelled`, because `fail_run` applies `finalise`'s rule 1 first (AC-19).

## Eligibility and Risk

`python3 scripts/classify-lane.py --none --json` returned `expedited`, with exit 0. Every signal was answered no, so `lane_signals` is empty.

Risk is medium: the change decides how a run ends on a rejected credential, and whether the ingestion process survives one. Every write is guarded as `finalise` guards its own: the row is locked with `SELECT … FOR UPDATE` and the transition is checked by `validate_transition`, so a run that is not `running` or `cancelling` raises rather than being overwritten. Instruments committed before the rejection keep their results; each committed in its own transaction (DAC-E4-14), and the design marks the whole run `failed` regardless.

Signal answers:

- `multi-component`: no. Only FactorFlow-v2 changes.
- `acceptance-criteria`: no. No acceptance criterion or test case changes.
- `public-contract` (close call): no. No API field changes. `failure_reason` is an existing column, written for the first time; no route serves it today.
- `product-behaviour` (close call): no. The approved behaviour is the design's: a rejected credential fails the run with its reason. The process crash and the eventual `abandoned` outcome were never approved behaviour.
- `persistent-schema`: no. Existing columns only.
- `authn-authz`: no.
- `privacy-secrets` (close call): no. The change touches the handling of a credential error, but stores only the reason `compose_failure_reason` produces for `CredentialRejected`: kind, symbol, data type, request id and a fixed sentence, never the provider's message or the key. A test asserts the key does not appear.
- `deployment-topology`: no.
- `unknown-risk`: no. The blast radius is the runner's four `CredentialRejected` handlers and one new journal function.

Not in scope: the run-level `failure_reason` is not shown in the API or the interface. Exposing it is a public-contract and UX change for the standard lane; the owner chose on 2026-10-11 not to do it here, and to drive TC-E2E-002's per-instrument reasons with an unavailable provider instead.
