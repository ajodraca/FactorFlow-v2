# Expedited Change: Release version 0.2.0 for CAP-002

## Request and Outcome

During CAP-002 release readiness on 2026-11-07, the owner chose `0.2.0` as the release version. The observable outcomes:

- The package builds as `factorflow-0.2.0`. The image tag the README tells the owner to export reads `0.2.0-<short sha>`, so the CAP-002 image is `factorflow:0.2.0-<sha>`, distinct from CAP-001's `0.1.0-373d256`.
- `pyproject.toml`, the `factorflow` entry in `uv.lock`, `package.json` and `package-lock.json` all state `0.2.0`. A unit test now fails whenever they disagree.

## Eligibility and Risk

`python3 scripts/classify-lane.py --none` returned `expedited`, with no signal answered yes. The close call:

- **deployment-topology: no.** The image tag is an owner-exported variable (`FACTORFLOW_IMAGE_TAG`). `compose.yaml`, the `Dockerfile` and the runtime configuration are unchanged. Only the README's example value changes.

Risk is **low**: nothing in `src/` or `web/src/` changes. The worst failure is a mislabelled package or image.

## Scope and Traceability

These files may change:

- `pyproject.toml`: `version`.
- `uv.lock`: the `factorflow` package's `version`.
- `package.json` and `package-lock.json`: the root `version` (both places in the lock file).
- `README.md`: the `FACTORFLOW_IMAGE_TAG` example under *Deploying and operating FactorFlow*.
- `tests/unit/test_version_agreement.py`: new; it checks the four manifests agree.

The test fixtures that hard-code `0.1.0` (`tests/unit/test_deploy_smoke.py`, `tests/unit/test_compose_definition.py`) are arbitrary tag strings, not the release version, so they stay.

Traceability: the owner's direction during CAP-002 `$release-readiness`, 2026-11-07 (release version `0.2.0`); `docs/releases/CAP-001-release-v2.md` sets the image-tag convention (`factorflow:0.1.0-373d256`).
