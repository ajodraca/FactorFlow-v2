# Expedited Change: Await the never-populated focus in the Instruments empty-state test

## Request and Outcome

The owner's session directed this change on 2026-10-31 after PR 156
(CAP-002-E1-S7, which does not touch the Instruments screen) failed its Frontend
job once, in run 41221840845 attempt 1, on
`web/src/screens/instruments/empty-states.test.tsx` > "renders 'No instruments
named yet.' with the add field focused when the list has never been populated".
Attempt 2 passed. The failure was `expect(element).toHaveFocus()` with
`<body>` focused and the screen fully rendered, the add field included.

Root cause: `AddField` focuses its input in a passive `useEffect`
(`focusOnMount`, `add-field.tsx`). The test resolves `listInstruments` outside
`act()`, so React renders it at default priority in a Scheduler task. React
schedules passive effects as a separate Scheduler task after the commit. When
the render and commit take longer than Scheduler's 5 ms slice, as a cold first
render on a loaded CI runner does (the failing file took 233 ms), Scheduler
yields before running them. `findByText` resolves from the MutationObserver that
the commit triggers. Testing Library's `asyncWrapper` then waits one
`setTimeout(0)`. If that timer fires before Scheduler's next `setImmediate`
task, which happens when the event loop is starved, the synchronous
`toHaveFocus()` runs before the effect. The `getHistoryDepth` re-render is not
involved: it resolves in the same microtask flush and batches into the same
render. The `neverPopulated` derivation is not involved either: it is computed
in the same render that shows the empty-state text.

Focus is never lost in the product. The effect always runs, one Scheduler task
after the commit. Only the test's synchronous assertion is wrong, so this is a
test fix. Outcome: the test awaits focus with `waitFor`.

## Test Evidence

The reproduction harness was a copy of the test file with two additions, kept
outside the repository. It replaced `globalThis.setImmediate`, which Scheduler
captures at load, with a 3 ms `setTimeout` to simulate a starved event loop. It
also mocked `StartAction` with a 10 ms busy render so the commit exceeds
Scheduler's 5 ms slice. Each half alone produced no failure in 60 renders. A
slow render with an undelayed `setImmediate` did not fail, and a delayed
`setImmediate` with a fast render did not fail. Both together failed every time.
That confirms the mechanism above.
