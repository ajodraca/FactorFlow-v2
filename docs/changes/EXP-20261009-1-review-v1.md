# Expedited Review: EXP-20261009-1 — Version 1

## Gate Summary

**Verdict:** `CHANGES-REQUIRED`

**By severity:** CRITICAL 0 · HIGH 2 · MEDIUM 1 · LOW 1 · **total 4**

The code does what the record says. Both defects are real. The three regression tests fail on the pre-fix code for the stated reasons and pass now. Every Python validation command passes when rerun. The change still fails the lane gate. When I answered the risk signals myself, `privacy-secrets` and `deployment-topology` both came out **yes**, and `classify-lane.py` puts the change in `high-risk`, not `expedited`. Passing `base=settings.base_url` means an unvalidated, operator-supplied string now decides where the Restricted Massive credential is sent, and whether it is sent over TLS. Before this change the credential could only reach `https://api.massive.com`. This must go through the high-risk lane of the standard pipeline (ER-001, ER-002).

The author's open concern about the ratios response shape (ER-003) does not make the change unsafe. Fundamentals already failed for every instrument before the fix. After it, the same per-data-type `failed` outcome is produced and nothing is written partially. Remodelling ratios is correctly left to a follow-up, but the record overstates the result: AC-3 fundamentals are not restored against the live provider.

`python3 scripts/classify-lane.py -s privacy-secrets -s deployment-topology` returned **`high-risk`**. Either signal alone (`-s privacy-secrets`) also returns `high-risk`. The record's `classify-lane.py --none` result rests on the two "no" answers it flagged as close calls.

The record's case for `privacy-secrets: no` is that the variable is approved and its default matches the SDK's default. Both facts hold: the SDK's `RESTClient.__init__` defaults `base='https://api.massive.com'`, and `MassiveSettings.base_url` has the same default. Neither fact answers the question, which asks whether the change affects secret material. It does, because it is the change that hands control of the credential's destination to configuration:

- `src/factorflow/config/settings.py:111` declares `base_url: str` with no scheme or host validation. Compare `ApiSettings`, which actively rejects a non-loopback host.
- `component-design-massive-client.md` §4 classifies the credential as Restricted. It states "TLS (SEC-ENC-001). Every request is HTTPS." and promises `tests/unit/test_massive_tls.py`, which does not exist. Nothing asserts an `https` base.
- `SEC-ENC-001` (`docs/constitutions/security.constitution.md`, Critical) prohibits plain HTTP on any channel carrying non-Public data.
- The change's own test, `test_configured_base_url_reaches_the_real_sdk_and_its_vx_sub_client`, aims the credential-bearing client at `http://127.0.0.1:8126`. `scripts/run-e2e-server.sh` sets that `http://` base as well. The key there is a dummy, so this is not a leak today, but it shows plaintext provider transport is now a supported path.
- DEC-0025, the e2e stub decision cited as motivation, is `kind: provisional`, `owner_reviewed: false`.

Before the change, any value of `FACTORFLOW_MASSIVE_BASE_URL` was inert. The credential only ever went to the SDK's built-in HTTPS host. After it, a typo, an `http://` value or a non-Massive host sends the key there. Deciding whether `base_url` must be `https` (perhaps with a loopback-only HTTP exception for the stub) is a security design decision. It belongs to specification review in the high-risk lane, not to this bounded lane.

Not part of the gate decision, offered for the owner: defect 2 on its own (the `list_financials_ratios` argument fix and its autospecced test) touches no credential or runtime setting. As a separate change it would answer every signal "no". Splitting it out is the owner's choice. This review does not make that change.

**The ratios concern.** This is the author's open item, judged here.

`fetch_financials` collects all four endpoints before returning. `follow_pages` collects every page before any row is validated. So a ratios validation failure raises before anything reaches the writer: nothing is persisted partially. `runner.py` catches the `MassiveError`, and `outcomes.classify_provider_error` maps `ProviderContractViolation` and `ProviderUnavailable` to the same per-data-type `failed` outcome. Neither one fails the run.

Before the fix, every instrument's fundamentals failed after three governed attempts. After it, they fail only when the ratios response is non-empty, after one attempt, and succeed when it is empty. That is no regression, and it does not make the change unsafe. Remodelling ratios changes the component design and `fundamental_observation` semantics, so it is correctly left out of scope. The residual costs are in ER-003.
