**Correctness.**

- **Nothing written for the rejected instrument.** The runner writes an instrument only in the single `write_instrument_with_outcomes` transaction at the end of its iteration (`runner.py:332-340`). Each handler returns before that point, whichever of the four reads raises. So no partial row exists for that instrument. Instruments committed in earlier iterations keep their rows, as DAC-E4-14 and the record state.
- **No further instrument is read.** `return` leaves `execute_claimed` without reaching the closing `finalise`. The test asserts that `fetch_reference` was called for `["AAPL", "REJ"]` only.
- **Cancellation wins.** If cancellation was requested during the iteration, `fail_run` records `cancelled`, the same as `finalise` rule 1 (AC-19). `failure_reason` stays NULL, because `_FINALISE_UPDATE_SQL` does not set it.
- **Credential safety.** `compose_failure_reason` never interpolates a `CredentialRejected` message. The WARNING log line contains only that composed reason.
- **The process keeps polling.** `execute_fn` (`ingestion_main.py:101-128`) and `run_polling_loop` (`runner.py:404-426`) have no exception handler. Before this change the rejection escaped through both and ended the process. Now `execute_claimed` returns normally.
- **Residual, not counted as a finding.** Suppose the run is reclaimed as `abandoned` between the top-of-iteration heartbeat and the rejection. Then `validate_transition("abandoned", "failed")` raises, and the polling loop still ends. `finalise` has the same exposure, and the record discloses that a non-`running`/`cancelling` run "raises rather than being overwritten". This change introduces no new exposure.
