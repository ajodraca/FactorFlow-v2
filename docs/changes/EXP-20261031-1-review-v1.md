### Root Cause Verification

I traced each step of the record's root cause in the code, rather than taking it on trust.

1. **Focus comes from a passive effect.** `AddField` calls `inputRef.current?.focus()` in a `useEffect` keyed on `focusOnMount` (`add-field.tsx:37-41`). Nothing else in the Instruments screen calls `focus()`, `blur()` or `autoFocus`, apart from `retire-dialog.tsx`, which is not mounted here.
2. **The text and the field mount in the same commit.** `InstrumentsScreen` renders `AddField` with `focusOnMount={neverPopulated}`, and `No instruments named yet.`, under the same `screenState.kind` condition (`index.tsx:71-106`). So the `neverPopulated` derivation is not a separate render, as the record says.
3. **One batched default-priority render.** `findByText` enters RTL's `asyncWrapper`, which sets `IS_REACT_ACT_ENVIRONMENT` to false synchronously. This happens before the mocked promises' `.then` callbacks run. Both callbacks, `setHistoryDepthYears` and `setScreenState`, run in the same microtask checkpoint outside `act`. `getCurrentEventPriority` returns `DefaultEventPriority` because no `window.event` is set (`react-dom.development.js:10992`), so both updates batch into one Scheduler callback. The `getHistoryDepth` update therefore shares the render, as the record says. `vi.clearAllMocks()` in Vitest 2.1.9 clears calls only, so the factory's `mockResolvedValue` stays in force.
4. **The render does not yield, but the passive effects are a separate task.** `DefaultLane` is in `includesBlockingLane`'s `SyncDefaultLanes`, so `performConcurrentWorkOnRoot` uses `renderRootSync` (`:5670-5674`, `:25776-25777`). `commitRootImpl` schedules `flushPassiveEffects` with `scheduleCallback$1(NormalPriority, …)` (`:26806`). It flushes synchronously only for `SyncLane` (`:26973`). Outside `act`, `ReactCurrentActQueue` is null, so the callback goes to Scheduler (`:27566-27577`).
5. **Scheduler yields after 5 ms.** `workLoop` breaks when `shouldYieldToHost()` reports at least `frameYieldMs = 5` ms since the slice's `startTime`. `performWorkUntilDeadline` then reschedules with `localSetImmediate`. That function is captured at module load (`scheduler.development.js:28`, `:166`, `:485-488`, `:517-540`, `:551-564`). So when render plus commit exceed 5 ms, the focus effect runs in a later macrotask.
6. **Testing Library waits one timer.** After `findByText` resolves from the MutationObserver microtask, `asyncWrapper` awaits a `setTimeout(…, 0)` before returning (`@testing-library/react/dist/pure.js`). In Node that timer runs in the next timers phase, ahead of the next check phase, once at least 1 ms has passed. If it does, the test resumes and the synchronous `toHaveFocus()` runs before Scheduler's `setImmediate` task. That is the failure.

The record calls this condition "when the event loop is starved". It is more precise to say that at least 1 ms of wall-clock time passes before the loop's next timers phase. The mechanism is the same, so this is not counted as a finding.

**Product impact.** Focus is never lost in the product. The effect is a queued Scheduler task and always runs, which the probe confirms (0 of 60 renders unfocused after `waitFor`). Only the test's assertion timing was wrong, so a test-only fix is correct.

**Traceability.** The record cites the owner session instruction, PR 156's Frontend job, TC-COMP-133, DAC-E2-S4-6 and CAP-001-E2-S4 T010. TC-COMP-133 and DAC-E2-S4-6 exist in `tests/component/all-component-tests.md:2959` and `tests/coverage-matrix.md:191`. `CAP-001-E2-S4-tasks.md` references TC-COMP-133. The change keeps that mapping.
